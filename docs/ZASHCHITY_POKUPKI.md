# Все защиты, способные запретить покупку

Слово владельца 03.10, п.1: «одним списком: имя, значение, где в коде, как
печатается в TG; скрытых быть не должно».

Покупку проходят **три независимых решения**, и запретить её может любое.
Поэтому список разделён на три части — иначе «почему не купили» ищется в трёх
местах по очереди.

Числа ниже — значения, действующие на 03.10 00:5xZ (из отчёта деплоя 181 и
живого файла групп). Где значение берётся из окружения службы, названа
переменная: её видно в отчёте любого деплоя.

---

## Часть 1. Пределы площадки — `bloom_exec_state.can_open_detailed`

Решает, можно ли открыть позицию ВООБЩЕ. Коды машиночитаемые (они же в журнале
решений и в сверке с DBot), тексты — людям.

| Код | Значение сейчас | Переменная / где | Касается полосы |
|---|---|---|---|
| `KILL_SWITCH` | снят | файл `/etc/bloom-executor/KILL`, плюс `KILL_BY_TELEGRAM` в каталоге состояния; `bloom_exec_state.kill_active` | **да**, глушит всё |
| `KILL_SWITCH_BLOOM` | снят | файл `/etc/bloom-executor/KILL_BLOOM` | нет |
| `COUNTERS_CORRUPT` | нет | `bloom_exec_state`, проверка счётчиков | да |
| `PAUSED_API_ERRORS` | 5 подряд | `api_error_streak_max`, счётчик `api_error_streak` | да |
| `PAUSED_UNSOLD` | 3 подряд | `unsold_streak_max`, счётчик `unsold_streak` | да |
| `PAUSED_RATE_LIMITED` | 300 с | `rate_limited_pause_s` | да |
| `WEEK_BUDGET` | 10 000 запросов в неделю, останов на 0.8 | `bloom_request_budget` (`limit_week`, `stop_at`) | да |
| `MAX_OPEN_POSITIONS` | 5 | `BLOOM_MAX_OPEN` / `max_open` | нет (считается только по позициям Bloom) |
| `SKIPPED_DUP_MINT` | кулдаун 900 с | `mint_cooldown_s` | да |
| `MAX_BUY_TIMES_PER_TOKEN_REACHED` | 2 | `max_buys_per_mint` | да |
| `SIGNATURE_SEEN` | — | `seen_signature` | да |
| `DAILY_LOSS_LIMIT` | **2.0 SOL** (было 0.2 до 03.10 00:50Z) | `BLOOM_DAILY_LOSS_SOL`; умолчание кода `DEFAULT_DAILY_LOSS_SOL = 1.0` | нет |
| `INSUFFICIENT_BALANCE` | нужно `buy_sol` + `fee_reserve_sol` = 0.2 + 0.02 | кошелёк ИСПОЛНИТЕЛЯ Bloom | нет |

**Четыре кода не глушат полосу** — это написано в коде списком
`bloom_exec_state.КОДЫ_ТОЛЬКО_BLOOM` и применяется в
`bloom_detector` (`if код2 in ST.КОДЫ_ТОЛЬКО_BLOOM: строка["lane_allowed"] = True`):
`KILL_SWITCH_BLOOM`, `MAX_OPEN_POSITIONS`, `DAILY_LOSS_LIMIT`,
`INSUFFICIENT_BALANCE`. Причина: у полосы свой кошелёк, свои позиции и свои
пределы. Общий `KILL`, автопаузы, битые счётчики и недельный бюджет в список НЕ
входят намеренно — это признаки поломки, и на них встают обе стороны.

## Часть 2. Фильтры задачи и разбора сигнала — `bloom_detector.фильтры_dbot` и решение по сигналу

Решает, считается ли сигнал покупкой, которую мы копируем.

| Код | Значение сейчас | Где в коде |
|---|---|---|
| `NOT_A_BUY` | — | продажи и прочее не копируются |
| `TARGET_AMOUNT_OUT_OF_RANGE` | **порог входа группы** `min_target_sol`: cand3 2.0, остальные по файлу групп | `фильтры_dbot`, порог из политики группы |
| `THRESHOLD_EDGE` | 0.9 от порога входа (`BLOOM_THRESHOLD_EDGE_PCT`) | **не запрещает**, только называет случай вплотную к порогу |
| `SKIP_TARGET_INCREASE_POSITION` | одна покупка на пару источник+минт, **без окна времени** | `bloom_exec_state.докупка_в_окне` |
| `STALE` | макс отставание сигнала в слотах (`BLOOM_STALE_SLOTS`) | решение по сигналу |
| `UNKNOWN_RATE` | — | трата в стейблах, курса SOL нет |
| `AMBIGUOUS_TX`, `TX_FAILED`, `TX_NOT_FETCHED` | — | разбор сделки источника |
| `INTERMEDIATE_ROUTE` | — | маршрут через промежуточный токен |
| `TOKEN_RECEIVED_NOT_BOUGHT` | — | токен пришёл, источник ничего не отдал |
| `SKIP_TAXED_ROUTE` | ставка налога маршрута | `vtoroe_mnenie_reestr` / `BLOOM_NALOG_2022*` |
| группа `off` при сбое модуля групп | `SG_ГРУППА_ПРИ_СБОЕ = "off"` | неторгующая, если про адрес спросить не удалось |

## Часть 3. Гейт полосы — `bloom_own_send` (цепочка `if/elif`, порядок важен)

Решает, покупает ли ПОЛОСА со своего кошелька. Первая сошедшаяся ветвь и есть
причина; она пишется в решение полем `lane_why_not`.

| Ветвь | Значение сейчас |
|---|---|
| рубильник включён | снят. Это ЧЕТЫРЕ файла, а не один: общий `/etc/bloom-executor/KILL` (root), `KILL_BY_TELEGRAM` в каталоге состояния (служба пишет сама), `KILL_BLOOM` (только площадка, путь можно задать `BLOOM_KILL_BUY_FILE`) и **`KILL_OWN_SEND` -- рубильник ТОЛЬКО полосы**: служба ставит его сама при денежной странности, а снимает только человек (`bloom_exec_state.lane_kill_active`, `:655`). В признаке жизни 03.10 01:47Z `lane_kill: [false, ""]` |
| **авария группы** | ни у одной группы не стоит (`avarii_grupp.json: {}`). Ставят её два счётчика: `АВАРИЯ_БЕЗ_ПРОДАЖИ_ПОДРЯД = 2` (две покупки подряд без продажи) и `АВАРИЯ_НЕУДАЧ_ПРОДАЖИ_ПОДРЯД = 3` (три неудачи продажи подряд), `bloom_own_send.py:4782-4783` |
| полоса выключена | `BLOOM_OWN_SEND` ≠ 1 — включена |
| по группе полоса не торгует | `lane_trades` группы: у `log_only` false (566 адресов) |
| минт уже открыт | один открытый минт на кошелёк |
| **второй минт на группу** | окно 1800 слотов (`ОКНО_ГРУППЫ_МИНТА_СЛОТОВ`) |
| открытых позиций полосы ≥ предела | `lane_open_max` группы: **3** у всех торгующих (batch5, cand1, cand1_03, cand1_05, cand2, cand3, lane_s0, leader, sniper_src) и **1** у kandidaty, log_only, off. Общий предел полосы при отсутствии поля -- **1** |
| за сутки сделок ≥ предела | **50** -- `ЛИМИТ_В_СУТКИ = BLOOM_LANE_DAY_LIMIT` (`bloom_own_send.py:4392`), и поле `per_day` группы его перебивает. Ни одна торгующая группа поля не задаёт, значит у каждой свои 50. В признаке жизни 03.10 01:47Z `limits.per_day: 50`, и у «деньги» `today: 50` -- то есть предел подошёл вплотную (считается ПО ГРУППЕ, а не на всю полосу) |
| упавших подряд ≥ предела | `СТОП_ПОДРЯД_УПАВШИХ` |
| **суточный стоп полосы по всем группам** | **−1.5 SOL** (`LANE_DAILY_LOSS_SOL`, умолчание кода 0.5), `СТОП_ПОЛОСЫ_СУТКИ_SOL` в `bloom_own_send.py:4421`, ветвь гейта 5193, число по цепи считается в 5024-5043. Запрещает покупки ВСЕМ группам до полуночи по Мадриду |
| защёлка | механизм в коде, для групп не срабатывает (Правило 16) |
| потолок расхода группы | `day_cap_sol` группы |
| тип пула не пускается | `lane_pools` группы -- И ОТДЕЛЬНО флаги типов: `LANE_BONDING_CURVE`, `LANE_DAMM2`, `LANE_DBC`, `LANE_DLMM`, `LANE_CLMM`, `LANE_LAUNCHLAB`, `LANE_WHIRLPOOL`, `LANE_AMMV4` (и `..._GROUPS` у каждого -- включить тип только части групп), `ДОП_ТИПЫ_ПОЛОСЫ` в `bloom_own_send.py:1070`. По признаку жизни сторож умеет 11 типов, котирует 10 |

**Суточных стопов групп (`stop_loss_sol`) больше нет** — Правило 16, слово
владельца 02.10: поле снято у девяти групп, `потолок_группы` отдаёт `None`
независимо от файла, и вернуть прежнее поведение можно только числом
`LANE_GROUP_DAILY_STOP=1`.

## Часть 3б. Запрещает покупку, но не ветвью гейта

Эти отказы живут ВНУТРИ сборки и проверки, а не в цепочке `if/elif`, и в
первой версии списка их не было -- хотя покупку они останавливают так же.

| Что | Значение | Где |
|---|---|---|
| **потолок комиссии пула** | **5 %** (`BLOOM_LANE_MAX_POOL_FEE`) | `ПОТОЛОК_КОМИССИИ_ПУЛА`, `bloom_own_send.py:1078`. У свежих пулов Meteora бывает расписание комиссии: в живой сделке 26.09 она была 50.9 %, и покупка значила отдать пулу половину входа |
| **потолок ноги USDC** | **0.01 SOL** (`BLOOM_USDC_NOGA_POTOLOK_SOL`) | `ПОТОЛОК_USDC_НОГИ_SOL`, `bloom_own_send.py:218` |
| **возраст баланса по цепи** | **300 с** (`LANE_CHAIN_MAX_AGE_S`) | `ПРЕДЕЛ_ВОЗРАСТА_ЦЕПИ_S`, `:3461`. Протухший баланс -- отказ, а не «просадки нет» |
| **счёт по цепи не прочитан** | -- | `bloom_own_send.py:5031` и `5040`, та же ветвь суточного стопа |
| полоса выключена | `BLOOM_OWN_SEND` ≠ 1 | ветвь гейта, названа выше |
| отправка не живая | `BLOOM_OWN_SEND_LIVE` | сборка идёт, отправки нет |
| контроль доставки выключен | `BLOOM_LANE_CONTROL` ≠ 1 | `:5930`, служебный путь доставки |

Проверено отдельно: `LANE_CHAIN_VS_LEDGER_SOL` (0.05) -- число ТОЛЬКО для
самопроверки (`:9545`), покупку оно не запрещает.

### Денежных пределов у полосы ДВА, и они разные

Это нашлось 03.10 в 01:47Z в признаке жизни детектора, когда список уже был
написан, -- и это ровно тот случай, про который сказано «скрытых быть не
должно». В первой версии списка оба предела были названы одним числом −2.0, и
это было неверно:

| Что | Переменная | Значение на хосте | Что делает |
|---|---|---|---|
| Суточный стоп полосы | `LANE_DAILY_LOSS_SOL` | **1.5** | `lane_why_not` ветвь 5193: покупки ВСЕХ групп до полуночи. Рубильник НЕ ставит |
| Рубильник по просадке | `LANE_KILL_DROP_SOL` | **2.0** | `ПОРОГ_KILL_ПО_БАЛАНСУ_SOL`, `bloom_own_send.py:4425`: ставит KILL |

Значит покупки встанут на **1.5**, а не на 2.0: до рубильника дело не дойдёт.
Числа живые, из признака жизни 03.10 01:47Z: `lane_daily_stop.threshold_sol`
1.5 при `pnl_all_groups_sol` −0.183467425, и `balance_day_threshold`
`threshold_sol` 2.0 при просадке 0.13085657 по цепи. Ни один не стоял.

**У этой же ветви есть ещё два отказа -- «закрыто при неясности»**
(`bloom_own_send.py:5031` и `5040`): «суточный стоп полосы по цепи не прочитан»
и «в счёте по цепи нет итога с открытыми по цене». Если счёт по цепи прочитать
не удалось, покупка НЕ идёт -- и это правильно (иначе стоп обходился бы
молчанием узла), но в списке они быть должны: ночью 02→03.10 ни один не
срабатывал.

**В TG стоп 1.5 не печатается вовсе.** У рубильника 2.0 есть тревога
(`⚠️ … просадка от 00:00 X SOL при рубильнике 2.0`), а у стопа 1.5 тревоги нет
ни одной: он ложится только в `lane_why_not` журнала решений и числом в
«пропущено сигналов» у 🧾 и 📋. То есть покупки могли бы встать, а в чате об
этом не было бы ни строки. Это тоже решение владельца -- ставить ли тревогу.

**Трогать я это не стал**: порог -- торговый параметр, а Правило 16 владелец
назвал как «только рубильник −2.0». Нужно слово: либо `LANE_DAILY_LOSS_SOL`
приравнять к 2.0 (тогда стоп и рубильник сойдутся), либо 1.5 оставить
намеренно -- но тогда «только рубильник −2.0» нужно читать как «покупки
встают на 1.5, рубильник на 2.0».

## Как это печатается в TG

* **Рубильник полосы −2.0 по цепи** — тревогой в виде
  `⚠️ HH:MM:SS <что> · <группа> · <число> · <до когда>`, числом
  «просадка от 00:00 X SOL при рубильнике 2.0». Одно сообщение на срабатывание,
  одно на снятие, иначе тишина.
* **Авария группы** — тем же видом тревоги, одно сообщение, снятие только по
  слову владельца.
* **Стопы и пропущенные сигналы по группам** — блоком в часовой 🧾 и суточной
  📋 (`bloom_doklad.стопы_групп` и `пропущено_сигналов`); стоящий стоп
  печатается и в тихом окне, где сделок ноль.
* **Получасовая строка :13/:43** — `рубильник стоит` первым словом, когда он
  стоит; снят — молчит (слово владельца 02.10: без слова «стоп», если ни один
  не стоит).
* **Остальные отказы** в TG НЕ печатаются по одному — они в журнале решений с
  кодом и в сводках числом. Иначе поток отказов заглушил бы денежные строки.

## Что НЕ является защитой от покупки

Чтобы список не путали: пол 70 % от котировки в подписываемых байтах, порог
30 % от входа у продажи и правило 4 (б) — это защиты ПРОДАЖИ, покупку они не
запрещают. Гейт перезапуска («нуль позиций») запрещает не покупку, а деплой. Файл
`KILL_SELL_BY_TELEGRAM` останавливает ПРОДАЖИ, а не покупки: «перестань
продавать» и «перестань торговать» -- разные приказы, и файлы у них разные.
