# P4 — kill-критерии (фандинг/базис на перп-рынках сток-токенов)

**Заморожено ДО просмотра данных и ДО запуска стадии `p4_lighter_markets`,
2026-09-01.** Критерии ниже — дословно от владельца, коммит этого файла
предшествует коду и любому запуску `analysis/p4_lighter_markets.py` /
`.github/workflows/run_p4_lighter.yml`. После коммита не редактируются
без явного решения владельца (тот же режим, что у `docs/R1_DESIGN.md`
§2, `docs/G1_DESIGN.md` §2, `docs/SC1_NOTE.md` §0).

## Критерии решения (дословно)

1. **Нет ≥30 дней истории фандинга ни по одному стоковому перпу → KILL.**
   Проверяется по максимально доступному периоду истории funding rate
   на каждом сток-/RWA-перпе, найденном на Lighter (см.
   `docs/P4_RECON.md`, секция «Lighter — верифицировано API»). Если
   *ни один* сток-перп не набирает 30 дней непрерывной/достаточной
   истории — KILL. Наличие истории ≥30 дней хотя бы на одном
   сток-перпе — гейт пройден для этого условия (остальные критерии
   всё равно проверяются по каждому перпу отдельно).
2. **Медианный годовой фандинг в пользу шорта минус издержки хеджа
   < 8% → KILL.** Фандинг переводится в годовые (часовая ставка ×
   24 × 365, если Lighter отдаёт часовую ставку; иначе — по
   документированному интервалу выплат этого перпа, см.
   `docs/P4_RECON.md`). «В пользу шорта» — берётся с тем знаком,
   при котором шорт по сток-перпу ПОЛУЧАЕТ фандинг (положительный
   funding rate при стандартной конвенции «лонг платит шорту»).
   «Издержки хеджа» — стоимость хеджирующей позиции (лонг базового
   актива/стейблкоин-обеспечение или альтернативный хедж) — конкретное
   численное значение издержек хеджа НЕ зафиксировано в этом документе
   (не предоставлено владельцем на момент заморозки) и должно быть
   явно указано и обосновано источником (не по памяти) в отчёте по
   факту расчёта критерия, до вынесения итогового вердикта по этому
   пункту.

   **Обновление (2026-09-01, по факту диагностики стадии
   `p4_lighter_markets`):** Lighter отдаёт `rate` ВСЕГДА неотрицательным
   и кодирует направление отдельным полем `direction` со значениями
   "long"/"short" (не "long_pays_short"/"short_pays_long", как
   документировано в SDK) — какое из двух означает «в пользу шорта»,
   **не подтверждено официальной документацией** (см. `docs/P4_RECON.md`,
   «Важная оговорка»). Применение этого критерия должно ждать
   подтверждения семантики `direction`, а не молчаливого допущения.
3. **Глубина на ±0.5% меньше планируемого размера ноги → KILL по
   ёмкости.** «Планируемый размер ноги» НЕ зафиксирован числом в этом
   документе (не предоставлен владельцем на момент заморозки) — при
   оценке этого критерия по факту данных нужно явно взять размер ноги
   из протокола микро-лайва/лестницы депозита (`docs/PROJECT_STATE.md`,
   «Протокол микро-лайва ($100)», лестница $100 → $500–1000 → рабочий
   размер) и явно указать, какая ступень лестницы использована для
   сравнения, либо запросить решение владельца, если ни одна ступень
   явно не подразумевается заданием.

## Явная оговорка (два критерия неполны без ввода владельца)

Критерии №2 и №3 содержат количественные пороги (8%, «планируемый
размер ноги»), но **не полностью параметризованы** этим сообщением
владельца — «издержки хеджа» и «размер ноги» не названы числом.
Раздел зафиксирован здесь ДОСЛОВНО, как получен, без домысливания
недостающих чисел (владелец: «никогда не выдумывай данные»). Отчёт по
стадии `p4_lighter_markets` (см. `docs/P4_RECON.md`) считает и
публикует все входящие в критерии агрегаты (медиана/p10/p90 годового
фандинга, глубина на ±0.1%/±0.5%), но **финальное применение
критериев №2 и №3 к вердикту требует либо explicit-числа от владельца
для «издержек хеджа»/«размера ноги», либо консервативной оценки,
явно помеченной как таковая** — не тихой подстановки произвольного
числа.

## Порядок

Этот файл закоммичен ДО стадии `p4_lighter_markets`. Стадия читает
только публичный REST Lighter (без Dune, без регистрации на внешних
сервисах — если API требует ключ, стадия останавливается и докладывает,
не пытается получить доступ). Результат — агрегаты в
`docs/P4_RECON.md`, секция «Lighter — верифицировано API». Применение
критериев №1–3 к агрегатам и итоговый вердикт P4 — отдельный шаг после
того, как агрегаты посчитаны (не автоматически в этом же коммите,
т.к. критерии №2–3 требуют ввода владельца, см. выше).
