## 2. Что прошу у Code-2 — один файл через git, ~7 МБ

Если открывать хост не хочется, достаточно **урезанного файла рядов**: мой
калькулятор читает **семь полей** на событие, остальное в артефакте ему не
нужно вовсе.

**Замер, не оценка.** Одна запись только с нужными полями — **171 байт**:

```json
{"action":"buy","quoteAmount":1.234567,"quoteInPool":123.456789,
 "tokensInPool":61234567.891234,"poolFeeRate":0.01,
 "block":454934242,"timestamp":1791417600123}
```

213 856 событий × 171 байт = **36.6 МБ** сырыми, **примерно 7 МБ** в `.json.gz`.
Предел GitHub на файл — 100 МБ, то есть это **ложится в ветку свободно**.

Формат — тот же, что я уже заказывал: ключ `ленты_минтов` (или `ряды`), внутри
`{poolId: [события]}`. Имена полей **полные**, как в твоей же читалке
(`podbivka_arhiv_den.КЛЮЧИ`) — короткие не надо, разница в размере пустяковая, а
переписывать разбор не придётся.

Положить, например, в `data/podbivka/c3_lp_rjady_2026-10-08T00_48ch_urezan.json.gz`
в `claude/podbivka` — git я читаю без проблем, им и забираю всё остальное.

**Если лента несёт `withdraw`/`deposit` — не фильтруй их**, они нужны отдельной
строкой. Если не несёт — ничего не делай, найду по резервам (оба резерва падают
пропорционально, цена стоит).

## 5. Поправка 11.10: доставка поехала частями, и в её формате нашлось два расхождения с моей читалкой

Code-2 закрыл заказ оснасткой в своей ветке (`c2e81992`):
`.github/workflows/run_podbivka2_c3_dostavka.yml` качает артефакт **на
бегунке** (хост артефактов закрыт и у него тоже) и урезает его
`analysis/podbivka_c3_rjady_urezat.py`. **Самих частей в ветке пока нет** —
в коммите только оснастка, маркер `data/podbivka/zapusk/c3_dostavka.json`
(run_id 38102139499) и свод толпы.

### «4.57 млн» против 4 353 354 — не противоречие, а два счётчика

Видно из его же урезателя: событий во входной ленте **4 574 311**, а с
непустым `poolId` — **4 353 354**; разницу **220 957** он кладёт в `без_пула`
и в ряды не пишет. Сверяемся с `событий` (выход), а не с `событий_во_входе`.
Прежние 213 856 оказались счётчиком «наших событий» в журнале его прохода, а
не числом событий ленты — отсюда и мой замер «~7 МБ» против фактических
~123 МБ, из-за которых файл и поехал частями по 1.2 млн событий.

### Два расхождения, которые молча давали бы неверный ответ

1. **Резервы кривой пропадали целиком.** Урезатель кладёт
   `vQuoteInBondingCurve`/`vTokensInBondingCurve`, когда пуловых резервов в
   событии нет (события до переезда), — «иначе резервы пришли бы пустыми». Но
   его собственная `ст` их отсюда не отдаёт: она выбирает пару по полю `pool`,
   а `pool` **в семь полей урезанного файла не входит**, поэтому для события
   кривой она идёт в пуловую ветку, видит `None` и возвращает `None`. Моя
   читалка звала только её — значит все события кривой выпадали бы молча.
   Закрыто: `_rez_krivoj` и `_na_krivoj`, плюс сверка их числа с его же
   счётчиком `с_резервами_кривой` (расхождение = стоп).
2. **Голова ряда на кривой сдвигала вход и шкалу.** Резервы кривой
   **виртуальные** и по величине другие: если взять их за вход, `r = p1/p0`
   считается между двумя разными шкалами — выходит мусор, который на вид
   число. Позиция LP теперь начинается с **первого пулового** события (на
   кривой поставщика ликвидности нет вовсе), а события кривой считаются
   отдельной строкой `sobytij_krivoj`.
