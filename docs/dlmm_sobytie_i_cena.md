# Meteora DLMM: что найдено по цепи и что ещё нужно строителю N4

Записано 28.09. Разбор: `analysis/c2_dlmm_recon.py`, девять настоящих сделок
источников из `data/c2_pool_samples/LBUZKhRxPF3XUpBCjp4YzTKgLccjZhTSDM9YuVaPwxo.json`
(двенадцать шагов DLMM). Ничего не подписывалось и не отправлялось.

## Найдено и подтверждено фактом

1. **События DLMM нет в `Program data:`.** Первый заход искал там и не нашёл ни
   в одной сделке из девяти; у двух образцов таких строк нет вовсе. Событие
   уходит **по CPI**: внутренней инструкцией к самой программе DLMM, данные
   которой начинаются дискриминатором Anchor `e445a52e51cb9a1d`, дальше идёт
   дискриминатор события и тело.

2. **Тел два на каждый своп:** 145 байт (событие `516ce3becdd00ac4`) и 163
   байта (`2e7452d7941b544d`). Разобрано короткое; раскладка тела (после
   16 байт двух дискриминаторов):

   | смещение | поле | проверка |
   |---|---|---|
   | 0..32 | `lb_pair` | совпал со счётом 0 вызова свопа — **12 из 12** |
   | 32..64 | кто торговал | — |
   | 64 | `start_bin_id` (i32) | значения правдоподобны (отрицательные, конец > начала на покупке) |
   | 68 | `end_bin_id` (i32) | — |
   | 72 | `amount_in` (u64) | совпал с переводами шага — **12 из 12** |
   | 80 | `amount_out` (u64) | совпал с переводами шага — **12 из 12** |
   | 88 | `swap_for_y` (1 байт) | 0 на всех покупках базы за котировку |
   | 89 | `fee` (u64) | 0.2 %–8.75 % от `amount_in` |
   | 97 | `protocol_fee` (u64) | ≈ 10 % от `fee` |
   | 105 | `fee_bps` (u128) | — |
   | 121 | `host_fee` (u64) | 0 везде; тело ровно 129 байт |

   Числа шага брались **по переводам токенов внутри каждого вызова**: все
   образцы — транзакции роутера, DLMM в них вызывается по одному-два раза на
   разных пулах, и разница балансов за всю транзакцию ни к одному событию не
   относится. Первый заход этим и ошибся — совпадений не было ни одного.

3. **Цена корзины.** Для шага, не вышедшего из корзины (`start_bin_id ==
   end_bin_id`), средняя цена сделки и есть цена корзины: вся сделка прошла по
   одной цене. Это готовый денежный путь: наша покупка следом идёт по той же
   корзине, пока та не кончится; кончится — минимум выхода не выполнится и цепь
   откажет, то есть промах, а не потеря.

4. **Шаг корзины сходится.** У пула `CJab6RE2…` две сделки на корзинах −346 и
   −362: отношение цен 1.17307 на 16 корзин даёт `(1 + bin_step/10000) =
   1.01003`, то есть **bin_step = 100**. При нём `1.01^-346 = 0.03196` против
   измеренной цены корзины `0.031975` — сходится. Значит цена корзины **в сырых
   единицах** равна `(1 + bin_step/10000)^bin`, без пересчёта по десятичным.

## Чего не хватает и почему нельзя брать вслепую

* **bin_step пула.** Он лежит в счёте пула (`lbPair`), раскладка счёта нам
  неизвестна. Без него цена **конечной** корзины у шага, сменившего корзину,
  не считается — а таких шагов 11 из 12. Брать шаг корзины «по памяти»
  нельзя: у разных пулов он разный (у `CJab6RE2…` вышло 100, у других
  неизвестно).
* **Ликвидность корзины.** Сколько ещё осталось в активной корзине, событие не
  говорит. Поэтому даже на однокорзинном шаге наша покупка может не набрать
  ожидаемого выхода. Это защищено минимумом выхода: цепь откажет, деньги
  останутся.

## Порядок работ по строителю N4

1. Прогон на хосте: прочитать счёта `lbPair` тех пулов, по которым есть живые
   сделки, и **вывести** смещение `bin_step` (u16) переносом того же приёма, что
   сработал с `amm_config` у CLMM: смещение считается найденным, когда одно и то
   же место даёт цену корзины, воспроизводящую сделку источника, **у всех**
   пулов сразу.
2. `dlmm_min_out` на этой цене: `fee` из события, цена конечной корзины, отказ
   без прочитанного `bin_step` — ровно как у CLMM отказ без ставки комиссии.
3. Самопроверки на этих же живых сделках, включая отказы.
4. Включение словом `dlmm` в `lane_pools` группы и первая живая сделка.

## Шаг 2 выполнен: bin_step выведен по цепи (28.09, 12:47Z)

Прогон `run_dlmm_shag_korziny_nl.yml` (только чтение: 9 getTransaction + 1
getMultipleAccounts, 10 вызовов). Разобрано **12 шагов DLMM в 11 разных пулах**,
счета пулов -- по 904 байта.

Перебор ВСЕХ смещений u16 оставил **два** смещения: **73 и 80**. Они не спорят:
у каждого из 11 пулов оба дают **одно и то же** число. Так и должно быть -- у
lbPair шаг корзины лежит дважды (числом и байтами семени PDA), поэтому критерий
исправлен: выведенным считается смещение, когда все годные смещения согласны у
всех пулов. Порог остаётся жёстким: если бы они расходились, значит нашли не то
поле, и брать нельзя.

Выведенные шаги корзин: 20, 100 (семь пулов), 125, 200 (два пула) -- это
штатные ступени Meteora, а не случайные числа.

**Независимая проверка:** у пула `CJab6RE2…` шаг корзины из счёта = 100, и то же
самое 100.27 получилось раньше из ОТНОШЕНИЯ ЦЕН двух его сделок на корзинах −346
и −362 -- то есть без всякой раскладки счёта. Два независимых способа дали одно
число.

Осталось по строителю N4: `dlmm_min_out` на этой цене (комиссия из события, цена
конечной корзины, отказ без прочитанного шага корзины -- как у CLMM отказ без
ставки), самопроверки на живых сделках, включение словом `dlmm` в `lane_pools` и
первая живая сделка.
