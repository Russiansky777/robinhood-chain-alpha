# Задача 5 — спецификация «чистого» замера времени включения (write-path)

Написано по прямому заданию владельца (сессия 2026-09-13, п.2): предыдущий
замер (`scripts/writepath_test.sh`, результаты
`data/p3_guard_cache/task5_writepath_test_{nl,dallas}_result.json`) даёт
`lag_ms`, загрязнённый временем локального поллинга рецепта через
Cloudflare-хост `rpc.mainnet.chain.robinhood.com` — это верхняя граница
реального времени включения, не оно само. Пересчёт этих двух файлов по
`block_number`/`block_timestamp` — `analysis/task5_writepath_block_recompute.py`
и раздел паспорта "Пересчёт task5_writepath_test — по блокам, не по lag_ms".
Этот документ — спецификация для НОВОГО, более чистого замера, не пересчёт
старого.

## Что не так со старым методом (коротко, честно)

1. **Таймер меряет чтение, не запись.** Рецепт всегда читается через
   `rpc.mainnet...` (Cloudflare) для ОБЕИХ серий (`rpc_mainnet` и
   `sequencer_mainnet_guess`) — цикл поллинга `eth_getTransactionReceipt`
   каждые 50мс. `lag_ms` = время от `t_send` до момента, когда ЭТОТ цикл
   впервые увидел рецепт. Если Cloudflare-чтение имеет собственный джиттер
   (anycast-репликация, см. паспорт, честная оговорка про n=1 замер с
   2203мс лагом), он одинаково добавляется к обеим сериям — но не
   одинаковой ВЕЛИЧИНОЙ на каждой попытке, а значит остаётся шумом,
   который путает сравнение путей ЗАПИСИ.
2. **Серии не изолированы друг от друга по времени.** Чередование
   rpc/sequencer в одном последовательном цикле (нечётные/чётные попытки)
   означает, что состояние сети (загрузка, темп блоков) в момент попытки
   N необязательно совпадает с состоянием в момент попытки N+1 — реальный
   темп блоков в замере (`analysis/task5_writepath_block_recompute.py`)
   показывает разброс 0.077–0.132 с/блок в пределах ОДНОГО 10-попыточного
   прогона, то есть сеть не находится в стационарном состоянии всё время
   замера.

## Метод — три изменения относительно `writepath_test.sh`

### 1. Таймер по фиду секвенсера, не по циклу поллинга RPC

Фоновая задача держит WebSocket-подписку на `wss://feed.mainnet.chain.robinhood.com`
(тот же Nitro broadcaster protocol, что `analysis/task5_bot_feed_client.py`
и `analysis/seq_feed_latency_probe.py` — используем `websockets`, БЕЗ
стороннего пакета `rhfeed`: интеграция `rhfeed` как git-зависимости живого
бота была заблокирована классификатором предыдущей сессии, см. паспорт,
"Real-World Transactions"/"Untrusted Code Integration" — этот скрипт
диагностический, не часть исполнителя, но лучше не создавать тот же
триггер повторно без явной проверки владельцем).

Для каждого сообщения фида с `sequenceNumber` фоновая задача пишет
`t_wall_first_seen[sequenceNumber] = time.time()` (только первое
наблюдение, не перезаписывать). **Найденный ранее в этой сессии факт
(README инструмента `chainstacklabs/robinhood-chain-sequencer-feed`,
процитировано в `seq_feed_latency_probe.py`): "carries a sequence number
matching the block number" — то есть `sequenceNumber` фида и есть номер
L2-блока на этой цепи, 1 сообщение = 1 блок.** Это утверждение стороннего
инструмента, не проверено здесь байт-в-байт независимо (честная
оговорка) — но именно на нём уже построен предыдущий `feed lead time`
замер (`seq_feed_latency_probe.py`, реальный прогон 2026-09-11), и оно же
даёт прямой мост "wall-clock времени появления блока N на фиде" без
декодирования содержимого L2-сообщения (декодер `decode_l2_message`
подтверждённо ненадёжен — 0/2286 реальных сообщений декодировано в
прошлом раунде, см. паспорт).

`t_feed_seen(block_number)` = `t_wall_first_seen.get(block_number)` —
момент, когда локальный подписчик фида впервые увидел ЭТОТ номер блока.
Это НЕ зависит от Cloudflare (фид — отдельный WS-хост,
`feed.mainnet.chain.robinhood.com`, отдельный от `rpc.mainnet...`, хотя
оба резолвятся за Cloudflare anycast, см. паспорт п.1 региона — важно:
это не решает вопрос "сам фид тоже за Cloudflare", просто убирает
конкретно контаминацию 50мс-поллинг-цикла и множественных HTTP-round-trip
на попытку).

### 2. Одна транзакция за раз, строго последовательно

Nonce читается ОДИН раз в начале (`eth_getTransactionCount(addr,
"pending")`), инкрементируется локально **только после подтверждённого
включения текущей попытки** (получен `block_number` из рецепта). Скрипт
**обязан остановиться** (не продолжать со старым/угаданным nonce), если:
- отправка вернула ошибку;
- рецепт не получен за `RECEIPT_TIMEOUT_S` (по умолчанию 30с);
- получен рецепт с `status=0` (revert) — честно записать и остановиться,
  не пытаться "досчитать" оставшиеся попытки тем же nonce.

Это прямой ответ на диагноз владельца "очередь из 10 транзакций одного
nonce" — новый скрипт физически не может отправить попытку N+1, пока
попытка N не подтверждена (нет цикла, который слепо шлёт следующую по
таймауту/расписанию поверх непризнанной).

### 3. Блок на момент отправки — известен напрямую, без интерполяции

Поскольку фоновая задача уже поддерживает актуальный `sequenceNumber`
(= номер последнего виденного блока), у каждой попытки есть
**`block_before_send`** = последний известный номер блока на фиде
непосредственно перед `t_send` — читается напрямую из состояния
подписчика, не оценивается интерполяцией назад (как пришлось делать в
`task5_writepath_block_recompute.py` для СТАРЫХ данных, где такого поля
не было). Итоговая метрика **`blocks_to_inclusion = block_number_included
- block_before_send`** — целое число блоков, посчитанное без каких-либо
оценок/интерполяций.

## Что скрипт пишет по каждой попытке

```json
{
  "attempt": 0,
  "submit_endpoint": "rpc_mainnet | sequencer_mainnet_guess",
  "tx_hash": "0x...",
  "block_before_send": 60538184,
  "block_number_included": 60538186,
  "blocks_to_inclusion": 2,
  "t_send": 1789158398.748945,
  "t_feed_seen_inclusion": 1789158399.01,
  "clean_inclusion_latency_ms": 261.06,
  "feed_lookup_status": "ok | block_not_seen_on_feed | feed_disconnected"
}
```

`clean_inclusion_latency_ms` — главная замена `lag_ms`: от `t_send`
(локальные часы, ДО сетевого вызова отправки, как и раньше) до момента,
когда подписчик фида ВПЕРВЫЕ увидел блок включения — без единого
обращения к циклу поллинга RPC в тайминге. Один-единственный вызов
`eth_getTransactionReceipt` в скрипте всё ещё нужен (сеть не даёт узнать
номер блока включения иначе — секвенсер-эндпоинт read-запросы не
обслуживает, подтверждено ранее), но он используется ТОЛЬКО чтобы
узнать факт (какой блок), не момент — момент берётся из уже
накопленного `t_wall_first_seen`, записанного независимо и заранее
(фоновая задача слушает фид непрерывно весь прогон, не только "после
отправки").

`feed_lookup_status="block_not_seen_on_feed"` — честный случай: если
WS-соединение оборвалось и переподключилось (реально наблюдалось в
прошлом раунде, "первый обрыв через ~85с") и мы пропустили ровно нужный
номер блока — `clean_inclusion_latency_ms` не пишется как число, вместо
него `null` + этот статус. Не подставлять оценку/интерполяцию вместо
реального пропуска.

## Итоговая агрегация (тот же формат, что старый скрипт, для сравнимости)

`overall` и `by_submit_endpoint` — медиана/p90/min/max по
`clean_inclusion_latency_ms` (не `lag_ms`) и отдельно по
`blocks_to_inclusion` (медиана/среднее/stdev) для каждого пути. Плюс
`block_cadence_s_per_block` за прогон (та же формула, что recompute-скрипт,
для честного сравнения темпа сети между прогонами).

## Запуск — одна команда, как `scripts/writepath_test.sh`

`scripts/writepath_test_clean.sh` — тот же паттерн: читает
`/etc/bot/env` (`PRIVATE_KEY_NOX`), сам ставит `eth-account`, `requests`,
`websockets`, сам запускает. Переменные окружения (все опциональны):
`BOT_ENV_FILE`, `N_ATTEMPTS` (по умолчанию 10), `VALUE_WEI`,
`LOCATION_LABEL`, `RECEIPT_TIMEOUT_S` (по умолчанию 30), `FEED_URL`
(по умолчанию `wss://feed.mainnet.chain.robinhood.com`).

```
bash scripts/writepath_test_clean.sh
```

Разовый диагностический запуск, НЕ часть бота — ничего не запускается
автоматически повторно, нет цикла, реальная отправка — только копеечные
(~$0.01) переводы владельца самому себе, тот же протокол, что старый
скрипт. Сама подпись/отправка — тот же явный `eth_sendRawTransaction` с
приватным ключом из `/etc/bot/env`, что и раньше (не новый механизм, не
требует отдельного разрешения сверх уже данного на `writepath_test.sh`).

## Что этот замер НЕ решает (честно, не обещать больше)

- Не устраняет вопрос "сам фид тоже виден за Cloudflare anycast" — не
  переизмеряет локацию/RTT до фида, только берёт его как источник
  таймстемпов, независимый от цикла поллинга рецепта.
- Не проверяет независимо равенство "`sequenceNumber` фида = номер
  L2-блока" — берёт как данность из документации стороннего инструмента,
  уже использованную в прошлом раунде для похожего расчёта
  (`seq_feed_latency_probe.py`). Если это когда-то окажется неточным
  (например, есть проскакиваемые sequence numbers без блока, или
  наоборот), `blocks_to_inclusion` и `clean_inclusion_latency_ms` будут
  сдвинуты — риск зафиксирован, не проверен здесь заново.
- Не решает вопрос происхождения sequencer-хоста за Cloudflare/AWS
  (уже закрыт в паспорте, п.1 региона) — использует тот же
  `sequencer.mainnet.chain.robinhood.com`, что и старый скрипт, тем же
  способом (`eth_sendRawTransaction`, публичный write-only приёмник, без
  обхода какой-либо аутентификации).
