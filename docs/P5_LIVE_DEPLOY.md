# P5 LIVE — план деплоя на VPS (владелец, 2026-09-03, п.3)

GH Actions не годится для Step 3-4 живого бота (60-секундный цикл,
24+ часа, мгновенные предохранители) — платформенный потолок job'а
6 часов, между прогонами неизбежен зазор в мониторинге захеджированной
позиции. Ниже — план для постоянно работающего процесса на VPS
(Ubuntu, US East, по решению владельца).

**Статус: план, не выполнено.** Ничего из этого ещё не задеплоено —
хоста пока нет. Шаги 1-2 из живого задания (открытие LP и шорта) не
начинаются до готовности хоста (владелец, явно).

## 1. Устройство процесса

Один долгоживущий Python-процесс (`p5_live_bot.py`, ещё не написан —
будет отдельным шагом после готовности хоста и закрытия пп.1-2 живого
задания), с явным разделением на:

- **Цикл наблюдения** (каждые 60с): цена пула, дельта позиции, текущий
  шорт, решение о ребалансе, проверка предохранителей (п.4 живого
  задания).
- **Часовой лог**: дописывает строку в `data/p5_live_log.jsonl`.
- **Heartbeat**: на каждой итерации цикла обновляет
  `/opt/p5-bot/heartbeat` (mtime — признак "процесс жив и не завис").

## 2. systemd-юнит

`/etc/systemd/system/p5-live-bot.service`:

```ini
[Unit]
Description=P5 live hedged-LP bot (ETH/USDG)
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=600
StartLimitBurst=5

[Service]
Type=simple
User=p5bot
Group=p5bot
WorkingDirectory=/opt/p5-bot
EnvironmentFile=/opt/p5-bot/env/p5-bot.env
ExecStart=/opt/p5-bot/venv/bin/python /opt/p5-bot/p5_live_bot.py
Restart=always
RestartSec=10
# 5 рестартов за 600с (StartLimitBurst/IntervalSec выше) -- дальше
# systemd сам перестаёт пытаться и юнит уходит в failed, это и есть
# сигнал для OnFailure= ниже (не бесконечный тихий crash-loop).
OnFailure=p5-live-bot-alert.service

# Изоляция -- процесс НЕ должен иметь причин трогать что-то за
# пределами своей рабочей директории и сети.
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/opt/p5-bot/data /opt/p5-bot/state
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

Отдельный пользователь `p5bot` (не root, не текущий SSH-пользователь)
— создаётся один раз при настройке (`useradd -r -s /usr/sbin/nologin p5bot`).

## 3. Автоперезапуск

Уже в юните выше: `Restart=always` + `RestartSec=10` — обычный
краш/исключение перезапускается через 10с. `StartLimitBurst=5` за
`StartLimitIntervalSec=600` — если падает чаще 5 раз за 10 минут
(верный признак системной проблемы — не сети, а логики/данных),
systemd останавливается сам и не долбит в API вслепую; это состояние
ловится алертом (`OnFailure=`, ниже), не тихо.

## 4. Логи с ротацией

Два потока:
- `journalctl -u p5-live-bot` — stdout/stderr процесса, системно (уже
  ротируется journald по умолчанию).
- `/opt/p5-bot/logs/p5-bot.log` — собственный текстовый лог бота
  (более подробный, чем то, что имеет смысл слать в journal).

`/etc/logrotate.d/p5-live-bot`:

```
/opt/p5-bot/logs/p5-bot.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su p5bot p5bot
}
```

`data/p5_live_log.jsonl` (часовые агрегаты из п.3 живого задания) —
это отчётный артефакт, НЕ технический лог: не ротируется, копится за
всё 24ч+ время жизни бота, коммитится в репозиторий периодически (тем
же приёмом commit+push, что во всех остальных скриптах этой сессии) —
единственный способ, которым результаты долетают обратно в этот
репозиторий с VPS.

## 5. Health-check и алерт при падении

Два независимых уровня, оба нужны (первый ловит краш процесса,
второй — зависание без краша):

**а) Краш процесса** — `OnFailure=p5-live-bot-alert.service` в юните
выше срабатывает, когда сам процесс завершается с ошибкой (или после
исчерпания лимита автоперезапусков).

**б) Зависание без краша** (процесс жив, но завис — например,
заблокирован на сетевом вызове без таймаута) — отдельный таймер:

`/etc/systemd/system/p5-heartbeat-check.timer` (каждые 5 минут) +
`.service`, который проверяет `mtime` файла `/opt/p5-bot/heartbeat` —
если старше ~3 минут (при 60-секундном цикле — это уже 3 пропущенные
итерации), считает бота зависшим и тоже дёргает алерт.

**Сам алерт** (`p5-live-bot-alert.service`) — маленький скрипт,
отправляющий уведомление. **Нужен канал от владельца** (один из):
- Webhook (Slack/Discord/Telegram-бот) — самый простой, `curl -X POST`
  с текстом в URL, который даёт владелец.
- Email через локальный `msmtp`/`sendmail`, если на VPS будет настроен
  исходящий SMTP.

Без выбранного канала алерт настроить нельзя — заготовка скрипта будет
готова, реальный URL/адрес подставляется на месте (не через чат, см.
п.7 ниже).

## 6. Состояние позиции — переживает рестарт, НО не как единственная правда

`/opt/p5-bot/state/position.json` — атомарная запись (пишем во
временный файл, `os.replace()` в целевой — исключает половинчатую
запись при падении посреди записи). Содержит: `tokenId` LP-позиции,
границы диапазона, последний известный размер шорта, таймстамп
последнего ребаланса, накопленные метрики (комиссии/IL/funding) с
начала работы.

**Важно, явно спроектировано так**: при старте (в т.ч. после рестарта)
бот **не доверяет файлу слепо** — считывает РЕАЛЬНОЕ состояние
(позиция LP по tokenId напрямую с чейна через `eth_call`, реальная
позиция на Lighter через `GET /api/v1/account`, см. `analysis/
p5_live_lighter_account.py` — публичный, без ключа) и сверяет с
файлом. Расхождение — повод для алерта и остановки цикла ребаланса
(не тихого продолжения на возможно устаревших данных), а не для
автоматического "починить и продолжить". Файл — быстрый локальный
кэш и аудит-след, не источник истины.

## 7. Что нужно от владельца

1. **Доступ**: IP VPS, пользователь для SSH, ключ (публичный ключ этой
   стороны — если нужен вход именно с этой сессии — или заведёте
   пользователя и настраиваете сами и присылаете доступ по факту).
   Токен /по паролю — нежелательно, ключ предпочтителен.
2. **Sudo** (для systemd/logrotate юнитов, `useradd`, установки
   пакетов) — на первичную настройку; сам бот-процесс работает от
   непривилегированного `p5bot`.
3. **Секреты — НЕ через чат.** Кладутся владельцем напрямую на VPS
   (по SSH, `nano /opt/p5-bot/env/p5-bot.env`, права `600`,
   владелец — `p5bot`), формат — простой `KEY=value`:
   ```
   PRIVATE_KEY_NOX=...
   LIGHTER_API_KEY_PUBLIC=...
   LIGHTER_API_KEY_PRIVATE=...
   ```
   (то же ограничение, что и с GitHub Secrets всё это время — ключи не
   должны проходить через переписку.)
4. **Канал алерта** (п.5) — webhook URL или email/SMTP-настройки.
5. **Подтверждение региона/ОС** — уже дано (Ubuntu, US East) — версия
   Ubuntu (22.04/24.04) для точных названий пакетов (`python3.11` и
   т.п.).

## 8. Что делаю я (после получения доступа, до открытия позиции)

1. Первичная настройка хоста (пользователь, зависимости, venv,
   юниты, logrotate) — по SSH.
2. `p5_live_bot.py` — сам процесс (Step 1-4 живого задания), с
   dry-run режимом по умолчанию (тот же принцип, что
   `analysis/sc1_launcher.py --confirm-mainnet` — реальная отправка
   только по явному флагу/переменной, не по умолчанию).
3. Тестовый прогон юнита (systemctl start, проверка heartbeat/логов,
   имитация падения — `systemctl kill` — проверка, что
   `Restart=always` и алерт реально срабатывают) — ДО реальных денег.
4. Доклад владельцу с результатом теста — реальное открытие позиции
   (Step 1) начинается только после явного подтверждения.
