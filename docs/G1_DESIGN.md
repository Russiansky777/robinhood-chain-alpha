## 2. Пре-регистрированный дизайн

### 2.1 Гипотеза и выборка
H1: после градуации токена на pons.family существует систематический положительный ЧИСТЫЙ (после издержек) дрейф цены хотя бы на одном горизонте сетки 30с–24ч.
Выборка: все градуации pons.family на Robinhood Chain (chain id 4663) с 01.07.2026 00:00 UTC (или с первой градуации, если она позже) до даты конца покрытия данных минус 24 часа. Точная дата конца фиксируется на Шаге 1 по метаданным покрытия.

### 2.2 Фильтр торгуемости (использует только пре-entry информацию)
Событие включается, если в окне (t0; t0+30с]: объём покупок ≥ $250 И число сделок ≥ 3. Долю отфильтрованных событий — в отчёт.

### 2.3 Определения входа и выхода
- t0 = таймстемп блока события градуации.
- Entry = VWAP сделок в окне (t0+30с; t0+90с] — моделирует задержку сигнал→исполнение. Нет сделок в окне → событие исключается как неисполнимое (логировать; если доля исключённых >30% — зафиксировать как ограничение выборки).
- Сетка горизонтов h: 30с, 1м, 2м, 5м, 15м, 30м, 1ч, 4ч, 12ч, 24ч.
- Exit(h) = VWAP сделок в окне (t0+h; t0+h+δ], где δ = max(30с; 0.1·h). Нет сделок в окне → последняя цена сделки ≤ t0+h+δ, флаг no_exit_liquidity_h = true.

### 2.4 Издержки и доходность
r_i(h) = ln(Exit_i(h) / Entry_i) − c, где c — раунд-трип издержки (комиссии пула в обе стороны + газ + слиппедж при размере ~$100). Сценарии: c = 1% / **3% (базовый)** / 5%.

### 2.5 Колонки выгрузки (одна строка на событие)
token_address, t0, n_buys_pre и vol_usd_pre (окно (t0; t0+30с]), n_scored_wallets_pre (покупатели из скоринга факт-прибыльности, кэш Sprint 1/1.5), n_hunters100_pre (покупатели из бакета «100+»), entry_vwap; для каждого h: exit_vwap_h, no_exit_liquidity_h. Итого ~35 колонок; строк — по числу событий (тысячи максимум).

### 2.6 Статистический план
- Основной тест: односторонний знаковый (биномиальный) тест H1 «медиана r(h) > 0» по каждому горизонту при базовой стоимости 3%; поправка Бенджамини–Хохберга по 10 горизонтам, α = 0.05.
- Секондари: бутстреп-CI (10 000 ресемплов) для 5%-усечённого среднего r(h).
- Робастность: (а) медианы обеих календарных половин периода; (б) сценарии стоимости 1%/5%; (в) стресс-сценарий S: события с no_exit_liquidity_h считаются r = −100% нетто.

### 2.7 Правила решения (заморожены коммитом Шага 0)
- **KILL**: при N ≥ 200 ни один горизонт не значим по BH (q ≥ 0.05) при базовой стоимости. Линия graduation-momentum в этой формулировке закрывается, ретест запрещён.
- **GO → G2**: существует горизонт h* ≥ 1 мин, для которого одновременно: BH-q < 0.05; медиана нетто ≥ +2% при базовой стоимости; медианы обеих календарных половин > 0.
- **GRAY**: значимость есть, но нарушено любое из остальных условий GO (медиана < +2%, провал половинок, эффект только на h < 1 мин) → решение владельца, дефолт — закрыть.
- **UNDERPOWERED**: N < 200 → вердикт не выносится, решение владельца (продлить период / закрыть).

### 2.8 Эксплораторные фичи (на вердикт НЕ влияют)
(а) n_scored_wallets_pre; (б) n_hunters100_pre; (в) режим рынка (дневной объём сети + 7-дневный тренд, дешёвый агрегат). Только описательная статистика и квартильные разрезы. Хороший результат по фиче не отменяет KILL; любая условная стратегия по фичам = новая пре-регистрация отдельным решением владельца.

### 2.9 Ограничения (обязательны в отчёте)
Налоги токенов и ханипоты не полностью учтены в ретро-издержках (частично покрыты сценарием 5%); MEV/сэндвич; VWAP ≠ гарантированно исполнимая цена на тонкой ликвидности; полнота декодинга Dune. При GO всё это проверяется протоколом микро-лайва.

**Найдено по данным:**
1. Поиск по `information_schema.tables` (`table_schema like
   '%robinhood%'`, агрегация distinct-схема) вернул 113 схем — ни одна
   не содержит подстроку «pons» ни в имени схемы, ни (по смыслу

2. Разбивка `dex.trades` за июль по (`project`, `version`) через
   `query_02_swaps_raw_july` показала: **100% объёма свопов** на чейне
   4663 в июле декодируется как `project='uniswap'` — v3 (58 581 299

   архитектуры v4 с единым PoolManager-контрактом, где адрес пула не
   гранулярен на уровне decoded-таблицы). Отдельного тега проекта или
   схемы для pons.family в декодинге Dune не существует.

**Вывод и выбранная механика:** т.к. Dune не даёт ни отдельной схемы,
ни отдельного тега проекта для pons.family, единственный наблюдаемый
сигнал — **появление нового пула Uniswap v3** (`min(block_time)` по
`pool_address`, только `project='uniswap' and version='3'`) как прокси
события градуации: рабочая гипотеза (миграция ликвидности с
bonding-curve на AMM-пул после градуации создаёт новый v3-пул)
подтверждается тем, что это единственный структурный сигнал, который
вообще существует в данных, а не выбором из нескольких альтернатив.

**Проверка правдоподобия темпа:** посуточные «рождения» v3-пулов за
июль — 907..22 049/день (сумма 277 396, сходится с общим числом пулов
из пункта 2 с точностью до округления), один день в августе
(2026-08-30) дал 24 293 новых пула. И то, и другое кратно больше порога
N≥200 (§2.1/2.7) — гейт Шага 1 пройден с огромным запасом, экстраполяция
до точного числа не требуется для прохождения гейта (точный подсчёт —
задача Шага 3).

**Ограничение метода (в дополнение к §2.9, которое как часть §2
заморожено дословно и не редактируется — детали ограничения relevant
to detection idет здесь и будет отражено в `docs/RESULTS.md`):** прокси
«новый v3-пул» **не различает** «градуация конкретно с pons.family» и
любую другую причину появления нового v3-пула на этом чейне (прямой

1%-сценарию, чем к базовому 3%; slippage/gas добавляются сверху и не
входят в hookFeeBps). Из собранного hook fee: `protocolFeeShareBps =
3000` (30% -> протокол), `buybackBurnBps = 5000` (50% от оставшегося ->
buyback/burn). `maxInternalPriceImpactBps = 300` (3%, потолок
внутреннего прайс-импакта, не издержка на трейдера напрямую).
`MAX_TOTAL_TRADE_FEE_BPS = 2000` (2%, верхний предел совокупной комиссии
за сделку) -- при выставлении на максимум round-trip издержка может
доходить до ~4%, ближе к базовому 3%/5%-сценариям §2.4.

**Квота может быть не WETH:** `PairTokenApprovalUpdated`/
`PairTokenEconomicsUpdated` в PonsV2LaunchFactory.sol подтверждают
поддержку нескольких pair/quote токенов (не только WETH, вплоть до
сток-токенов, как отметил владелец) -- нормировка Entry/Exit VWAP в USD
должна идти через цену КВОТЫ на момент сделки (amount_usd из dex.trades
уже в USD -- полагаемся на курируемый прайсинг Dune, не пересчитываем
вручную), не считать квоту фиксированно WETH при агрегации.
