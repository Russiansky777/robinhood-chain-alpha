# Sprint SC1 — конвейерный запуск токенов (serial creators): юнит-экономика

**Зафиксировано ДО просмотра данных: 2026-09-01.** Критерий решения
ниже вставлен дословно из промпта штаба и после коммита Шага 0 не
редактируется. Выполняется ПАРАЛЛЕЛЬНО Sprint R1, не трогая его каскад;
при конфликте ресурсов (GH Actions runner, порядок пушей в общую ветку)
R1 приоритетнее — см. `docs/PROJECT_STATE.md`.

## Критерий решения (заморожен коммитом Шага 0)

«Критерий решения SC1 (зафиксирован до просмотра данных): конвейерный
запуск токенов признаётся экономически оправданным, если медианный
конвейер (кластер-создатель с 50+ запусков за август 2026) заработал
creator-комиссий больше, чем 2× стоимость газа своих запусков по
пост-вейверным ценам. Оценка газа: фактические gas units деплоя (из
реальных транзакций) × цена газа сети после окончания вейвера (взять
текущую базовую цену газа Robinhood Chain из ончейн-данных или RPC;
источник указать). Независимо от медианы: если >90% всех
creator-комиссий августа сконцентрировано в верхних 5% кластеров —
конвейер признаётся лотереей, идея закрывается. Смешанные исходы
(медиана проходит, но концентрация >90%) трактуются как лотерея.»

## Смета и правила (наследуются от G1/R1)

Бюджет: 20 кредитов, namespace `sprintSC1`, принудительный гард.
Временные границы в каждом запросе к трейдам/логам (регрессионный тест
обязателен); наружу только агрегаты (топ-5 кластеров — с адресами, для
справки, остальное агрегатами); калибровка узким срезом ×2.5;
binding-гард на чтения; кэш `data/sprintSC1_cache/` + коммит после
каждой платной операции; 2x-стоп при факте ≥25 кредитов.

## Порядок исполнения

**Шаг 0.** Заморозка критерия (этот файл) — коммит ДО первого платного
запроса.

**Шаг 1 — данные запусков (дёшево/бесплатно).**
- V1-запуски: уже в кэше (266K событий с деплоерами, если поле
  деплоера есть; если нет — восстановить из закэшированных логов, не
  платя заново).
- V2-запуски за август: логи V2-фабрики (`TokenLaunched` = деплой на
  кривую в терминах V2), с границами по времени. Нужны: token,
  deployer, timestamp, gas_used транзакции деплоя (если доступен в
  логах/трейсах дёшево; иначе — выборка 100 транзакций для оценки
  медианного gas_used).

**Шаг 2 — кластеризация создателей (агрегатно, внутри Dune).**
- Уровень 1: группировка по адресу деплоера.
- Уровень 2: склейка деплоеров по общему источнику финансирования —
  funding parent = отправитель первой входящей ETH-транзакции
  кошелька-деплоера. Кластер = компонента связности «деплоеры с общим
  фандером» (одна итерация склейки достаточна, глубже не строить).
- Наружу — только агрегаты по кластерам, никаких адресов построчно
  (топ-5 кластеров можно с адресами для справки).

**Шаг 3 — экономика по кластерам.** Для каждого кластера: n_запусков;
суммарный объём торгов их токенов в первые 24ч после запуска (границы
времени!); оценка creator-комиссий: для V2 из fee-стека
(hookFeeBps=100, protocolFeeShareBps=3000 → создателю ≈0.7% объёма),
для V1 — фактическая доля из исходников V1 (если отличается —
задокументировать здесь); доля токенов кластера с нулём внешних
покупателей (покупатели ≠ сам кластер).

**Шаг 4 — выгрузка (агрегаты).**
- Децили экономики по кластерам с 50+ запусков (конвейеры):
  комиссии/кластер, комиссии/запуск, объём/запуск, доля нулевых
  токенов.
- Те же децили по кластерам с 1–4 запусками (штучные создатели) —
  контраст.
- Концентрация: доля суммарных creator-комиссий августа у топ-5%
  кластеров.
- Число кластеров в каждой группе.

**Шаг 5 — отчёт в этом файле.** Вердикт строго по замороженному
критерию; таблица децилей обеих групп; оценка «газ после вейвера ×
медианный конвейер» в долларах; явные оговорки, где оценка комиссий
приблизительная (маршрутизация, не-hook пулы). Финальное сообщение
владельцу: вердикт + 5 ключевых чисел.

Возвратная точка: отчёт SC1 готов. До неё — автономно.

## Уточнение владельца (2026-09-01): выборка V1-специфична, fee-стек V1 ≠ V2

Данные запусков августа (39 680 событий, `sc1_launches.py`) фактически
ограничены **01.08–12.08** — после 12.08 поток ушёл на V2 (см.
`docs/G1_DESIGN.md`, "Судьба фабрики после 12.08.2026"). Замер
конвейеров этим замером — **V1-специфичный**, не репрезентативен для
текущей V2-реальности, где сейчас и идут запуски. В §5 отчёта это
будет явно помечено, отдельным абзацем — оценка применимости вывода к
V2.

Требование владельца: НЕ переносить fee-цифру V2 (0.7% объёма) на V1 —
у V1 другая механика. Проверено на источнике (GitHub,
`ponsdotdev/ponsfamily`, `contractsV1/src/PonsLaunchFactory.sol`,
запрошено дословно):

- V1 **не** использует bonding curve — "one-sided Uniswap V3 position,
  full supply from the first block". Creator revenue = "trading fees
  on the locked position" — LP-комиссии на этой позиции (которую
  можно передать на альтернативный кошелёк, `feeWallet`/
  `initialBuyRecipient`).
- Fee-тир — поле `poolFee` (`uint24`) в `DexConfig`, **конфигурируемое
  per-launch** (не единая константа, как V2's 0.7%) — стандартный
  Uniswap V3 тир (0.01/0.05/0.3/1% и т.п.), потенциально РАЗНЫЙ у
  разных launch-конфигураций.
- Плюс `launchFee` — плоский **native**-сбор в пользу
  `protocolFeeRecipient` при каждом запуске (издержка создателя,
  ДОБАВОЧНАЯ к газу, не доход) — точное значение пока не определено
  дёшево, см. ниже.

План: получить ФАКТИЧЕСКИЙ fee-тир пулов V1-запусков августа из
ончейн-метаданных (Uniswap V3 pool.fee(), декодировано Dune) —
`analysis/sc1_v1_fee_discovery.py`. Если тир единый по всем/почти всем
пулам — используется как факт. Если разный — считается распределение,
экономика по нижней и верхней границе диапазона тиров (владелец: "если
дёшево не найдёшь — не гадай, границы"). Аналогично для `launchFee`,
если не определится дёшево.

### Результат: fee-тир V1 определён точно, не гадание

`uniswap_v3_robinhood.uniswapv3factory_evt_poolcreated` за окно
01–13.08.2026 (50 934 PoolCreated по всему чейну) пересечён локально с
пулами всех 39 680 августовских V1-запусков — **совпадение 39680/39680
(100%)**, и **fee = 10000 у ВСЕХ** (Uniswap V3 fee-units — сотые доли
бипса, 10000 = **1.00%**), tickSpacing=200 у всех. Единый тир,
согласуется с тем, что все запуски используют один
`launch_config_id`/`dex_id`/`dex_factory` (проверено локально по
декодированным событиям).

**V1 creator-комиссия = LP-доход с одностороннней "full supply"
позиции при tier=1%** — если создатель держит позицию как
единственный/доминирующий LP (согласуется с "one-sided ... full
supply ... locked position" из README), эффективная ставка **≈1.00%
объёма торгов**, а НЕ 0.7% (V2). Это ВЫШЕ, а не ниже V2-цифры —
существенно меняет экономику в пользу критерия GO, если её механически
перенести без учёта различий. Используется 1.00% как факт для V1,
0.7% остаётся фактом только для V2 (после 12.08) — раздельно, не
смешивается.

Оговорка (не устранена дёшево): доля объёма, реально доставшаяся
именно ЭТОЙ позиции (а не другим LP, если кто-то ещё добавил
ликвидность в тот же пул) не проверялась отдельно — считаем позицию
доминирующей по умолчанию, риск переоценки в меньшую сторону при
наличии сторонней ликвидности. `launchFee` (плоский native-сбор) —
проверяется отдельно через `robinhood.transactions` (gas_used заодно,
нужен для критерия).

## Газ и launchFee (Шаг 2, эмпирически)

Агрегат по 39 382 успешным транзакциям `launch()` (`robinhood.
transactions`, `to = PonsLaunchFactory V1`, окно 01–13.08.2026):

- **gas_used**: медиана 7 107 605.6, среднее 7 090 291.1, диапазон
  [25578; 30 348 571].
- **gas_price фактический** (в период вейвера): медиана 22 951 601.4
  wei/gas (≈0.02295 gwei). Владелец, критерий: "взять ТЕКУЩУЮ базовую
  цену газа Robinhood Chain из ончейн-данных" — это она и есть,
  источник: `robinhood.transactions.gas_price`, декодировано Dune,
  медиана по факту 39382 успешных launch-транзакций. Отдельного
  RPC-запроса не потребовалось; страница docs.robinhood.com/chain/
  gas-and-fees (получена через GH Actions runner) объясняет механику
  (L2 execution fee + L1 data fee, Arbitrum-стиль), но не даёт
  отдельного "пост-вейверного" числа — используем текущую медиану как
  и просил владелец.
- **ИСПРАВЛЕНО (владелец, "критично: разбери природу launchFee").**
  Первый проход (медиана всех ненулевых `value` ≈ 0.0512 ETH) был
  ОШИБОЧНЫМ — он смешивал launchFee с опциональной seed-покупкой.
  Источник (GitHub, `ponsdotdev/ponsfamily`,
  `contractsV1/src/PonsLaunchFactory.sol`, функции `launch()` и
  `_payLaunchFee()`, получено WebFetch): `launchFee` — ФИКСИРОВАННАЯ
  константа (`uint256 public launchFee`, меняется только владельцем
  через `setLaunchFee`), списывается ПЕРВОЙ операцией внутри `launch()`
  и уходит НЕВОЗВРАТНО в `protocolFeeRecipient()` (казна протокола).
  Остаток `initialBuyAmount = msg.value - launchFee` — ОПЦИОНАЛЬНАЯ
  seed-покупка, инвестиция создателя в собственный токен (позиция
  остаётся у создателя, это не издержка).
  Точное значение найдено запросом `sc1_v1_launchfee_exact.sql`
  (`approx_most_frequent` по `cast(value as bigint)` + `min(value)
  filter (where value > 0)` по тем же 39 382 транзакциям):
  **launchFee = 500 000 000 000 000 wei = 0.0005 ETH** ровно —
  совпадает и минимум ненулевых `value`, и самое частое значение
  (10 826 из ~39 381 ненулевых, ≈27.5% — создатели, не делавшие seed buy).
  Кросс-валидация: у остальных топ-5 значений `value` разница с 0.0005
  ETH даёт круглые суммы seed-buy (3.5, 3.88, 0.05, 0.005 ETH) — что и
  ожидается от "launchFee + опциональный круглый seed buy".
  **launchFee — доминирующая невозвратная статья издержки конвейера**,
  используется в критерии как есть (0.0005 ETH), без верхней/нижней
  границы — значение точное, не оценочное.
- **Газовая стоимость запуска** = gas_used × gas_price ≈ 7 107 606 ×
  22 951 601 wei ≈ 1.631×10^14 wei ≈ **0.000163 ETH** на запуск.
- **Полная невозвратная стоимость одного V1-запуска** = launchFee +
  газ ≈ 0.0005 + 0.000163 = **0.000663 ETH** — это то, к чему по
  уточнению владельца (2026-09-01) теперь применяется порог 2x в
  критерии SC1 (было: только газ; изначальная гипотеза владельца о
  ~$150+/запуск при launchFee-как-издержке была основана на неверной
  величине launchFee ≈0.05 ETH — при подтверждённой точной величине
  0.0005 ETH издержка на порядок ниже, чем предполагалось до проверки).

## Шаг 3: объём торгов по кластерам в первые 24ч (self-contained JOIN)

`sql/sc1/sc1_volume_24h_{calib,full}.sql` — self-contained: адреса
токена/пула выводятся ВНУТРИ запроса из `robinhood.logs`
(`TokenLaunched`, `contract_address` = PonsLaunchFactory V1), JOIN на
`dex.trades` по `project_contract_address` в окне `(t0; t0+24ч]`.
Калибровка 1 днём (01.08) → проекция на весь 12-дневный диапазон
20.3 кредита (факт калибровки 0.68×12×2.5) — прошла санитарную
проверку без партиционирования, выполнена одним запросом.

Итог: **30 394 из 39 680 токенов (76.6%)** имеют хотя бы одну сделку в
первые 24ч; у оставшихся 23.4% объём за 24ч точно 0 (INNER JOIN не
находит совпадений) — это те самые "запуски без внешних покупателей".
Суммарный объём за 24ч по всем найденным токенам — **$336 165 491**.

## Итоговая экономика по кластерам (Шаг 4, 0 кредитов, локально)

`analysis/sc1_report.py` — merge `sc1_august_launches_decoded.csv`
(token→deployer) × `sc1_deployer_to_cluster.csv` (deployer→cluster_id,
уровень 2) × `sc1_volume_24h_all.csv` (token→объём 24ч, LEFT JOIN,
отсутствующие = 0). Creator-fee revenue = 1.00% объёма 24ч
(эмпирический V1 fee-тир). Полная невозвратная стоимость запуска =
launchFee (0.0005 ETH) + газ (0.00016313 ETH, из медиан gas_used/
gas_price) = **0.00066313 ETH ≈ $1.26** по курсу выше — на порядок
меньше первоначальной гипотезы владельца (~$150+/запуск), потому что
launchFee оказался на два порядка меньше первого (ошибочного) прочтения.

Результат записан в `data/sprintSC1_cache/sc1_cluster_economics.csv`
(8695 строк: cluster_id, n_launches, fee_revenue_usd, vol_usd_24h,
cost_usd, fee_to_cost_ratio, zero_volume_share и т.д.).

### Конвейеры (48 кластеров, ≥50 запусков)

- Медианный конвейер (298 запусков): заработал комиссий (24ч-объём
  ×1.00%) **$4 812.20**, заплатил launchFee+газ **$373.96** —
  отношение **14.5x** (порог владельца: ≥2x на полных издержках,
  не только на газе).
- Децили fee_revenue_usd по кластеру: от $126 (p10) до $163 699 (p90) —
  широкий разброс, но даже p10 (наименее удачливый конвейер) заработал
  в разы больше средних издержек одного конвейера ($374).

относительно реальной структуры costs/revenue в V1.

### Применимость к V2 (текущая реальность после 12.08.2026)

**Этот вердикт относится строго к V1-конвейерам августа 2026** (окно
выборки 01–12.08, после чего поток запусков перешёл на V2-контракты).
V1 и V2 отличаются структурно, и прямой перенос числового вердикта на
V2 некорректен:

- **Fee-механика иная**: V1 — фиксированный fee-тир Uniswap V3 LP-
  позиции (1.00%, эмпирически подтверждено); V2 использует другую
  модель (в конфиге проекта заложено 0.7% от объёма как отдельная
  константа `sc1_v2_hook_fee_bps`/`sc1_v2_creator_fee_share_of_volume`)
  — на 30% ниже V1 при равном объёме, что снижает revenue-часть
  критерия, но не меняет его знак при таком запасе (14.5x), если
  издержки не выросли пропорционально сильнее.
- **launchFee для V2 НЕ проверялся** в этом замере (владелец просил
  разобрать именно V1-природу launchFee) — если V2 сохраняет
  аналогичный некрупный флэт-сбор, вывод, скорее всего, переносится
  качественно (издержка запуска остаётся много меньше revenue при
  ненулевом объёме); если V2 ввёл принципиально другую (например,
  процентную от объёма или растущую) схему издержек — расчёт нужно
  повторить с нуля на V2-данных.
- **Механика запуска иная** (V1 — мгновенная полная позиция, V2,
  предположительно, иная кривая/аукцион по прежним заметкам этого же
  документа) — это может менять и распределение объёма по времени
  (24ч-окно из V1 может не быть репрезентативным для V2), и, как
  следствие, саму применимость метрики "объём в первые 24ч" как
  прокси для creator revenue.

**Итог по применимости**: направление вывода (конвейерная экономика
работает, комиссии не деградируют в чистую лотерею) правдоподобно
переносится на V2 качественно ввиду большого запаса (14.5x), но
количественный вердикт (конкретные $X/$Y/14.5x/78.65%) **привязан к
V1 и не должен цитироваться как актуальный для текущих V2-запусков**
без отдельного повторного замера на V2-данных.

### Что конкретно изменилось V1 → V2: доля создателя и стоимость запуска (дозапрос, по просьбе штаба)

**Доля создателя — источник найден.** `contractsV2/src/v2/hooks/PonsV2MemeHook.sol`
(репозиторий `ponsdotdev/ponsfamily`, дословно из констант исходников,
цитировано в `docs/G1_DESIGN.md` при работе Sprint G1): `hookFeeBps =
100` (1% с каждого свопа) → из него `protocolFeeShareBps = 3000` (30%
уходит протоколу) → создателю остаётся оставшиеся 70% от 1% = **0.7%
объёма** (константа `sc1_v2_creator_fee_share_of_volume` в
`analysis/config.py`, задокументирована при закрытии Sprint G1).
Плюс `buybackBurnBps = 5000` — по исходникам это 50% «от оставшегося»
после протокольного вычета, но **не установлено дословно**, идёт ли
эта доля из ПРОТОКОЛЬНОЙ доли (тогда создатель по-прежнему получает
полные 0.7%) или из доли СОЗДАТЕЛЯ (тогда фактическая доля создателя
могла бы быть ниже, ~0.35%) — это НЕ проверялось отдельно ни в G1, ни
в SC1, отмечается здесь честно, не додумывается. **Направление
изменения V1→V2 однозначно: доля создателя V2 (0.7%, возможно ниже)
МЕНЬШЕ, чем эмпирическая доля V1 (1.00%, подтверждено 100%-совпадением
`pool.fee()` по всем 39680 V1-запускам августа)** — на ~30% ниже при
том же объёме, в консервативном случае (если buybackBurnBps не режет
долю создателя) или больше, если режет.

**Стоимость запуска (launchFee-аналог + газ) — НЕ ПРОВЕРЕНО, честно
неизвестно.** В отличие от V1 (где точное значение launchFee = 0.0005
ETH установлено эмпирически по `sc1_v1_launchfee_exact.sql`), для V2
**ни launchFee-аналог, ни характерный gas_used запуска не измерялись**
ни в этом спринте, ни в Sprint G1 — владелец прямо просил в SC1
разобрать именно V1-природу launchFee (см. «Уточнение владельца»
выше), запросов по V2-стоимости запуска не было. Если у кого-то есть
гипотеза о величине V2-издержки — она НЕ зафиксирована в этом
документе и не должна использоваться без отдельной проверки на
V2-данных (тот же принцип, что и для launchFee V1 до его точного
измерения — см. инцидент с ошибочной первой оценкой ~$150+/запуск
выше).
