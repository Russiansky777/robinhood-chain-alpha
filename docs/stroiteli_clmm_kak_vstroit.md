# Строитель покупки Raydium CLMM для Code-1: как встроить

**Файл:** `analysis/c2_clmm_stroitel.py`. **Флаг:** `BLOOM_CLMM_STROITEL` /
`BLOOM_CLMM_STROITEL_GROUPS`, по умолчанию ВЫКЛЮЧЕН (правило то же, что у типов пулов полосы:
список групп сильнее общего флага, группа неизвестна -- выключено).
**Проверка без денег и без сети:** `deploy/checks/stroiteli_vosstanovlenie.py --tip clmm`.
**Цена:** перенос кода программы Code-2 `analysis/podbivka_clmm_quote.py` (ветка `claude/podbivka`).

## Зачем он, если CLMM у полосы уже есть

У полосы на CLMM стоят два ограничения, и оба денежные:

1. **Цена по событию, а не по состоянию.** `c2_swap_build.clmm_min_out` берёт ликвидность L из
   события сделки источника и продолжает кривую от неё. Пока своп не переходит инициализированный
   тик -- верно; перешёл -- L уже другая, и минимум выхода посчитан не по той ликвидности.
2. **Массивы тиков от источника.** Сборка берёт список счетов из сделки источника, а какие массивы
   нужны -- зависит от ТЕКУЩЕГО тика пула. Замер на снимках Code-2: весь набор нужных сейчас
   массивов был у источника лишь в **5 случаях из 13**, мест под массивы хватало в **8 из 13**.
   Отсюда и нынешний отказ полосы «наша покупка уходит за край массива тиков источника».

Ещё одно, по охвату: `extract_template` принимает у CLMM только `swap_v2` и только «точный вход без
предела цены». По сбору Code-2 (598 живых инструкций CLMM у 34 источников за 28--29.09) это
отсекает **все 197 инструкций `swap` (v1)** и **47 `swap_v2` с точным выходом** -- 244 из 598.
Новый строитель читает оба вида и не требует у источника точного входа: свой хвост он собирает сам.

## Как работает подстановка массивов -- и почему именно так

Правило взято не из головы, а из исходника программы того же коммита, что развёрнут в сети
(`raydium-io/raydium-clmm`, `ed1eb41`, `programs/amm/src/instructions/swap_v2.rs` и `swap.rs`):

```rust
for account_info in remaining_accounts.into_iter() {
    if account_info.data_len() == TickArrayState::LEN { tick_array_states.push_back(...) }
    else if account_info.data_len() == TickArrayBitmapExtension::LEN { ... }
    else { break; }
}
```

Отсюда три следствия, на которых и стоит модуль:

* **Очередь массивов складывается по порядку счетов**, а `swap_internal` достаёт их
  `pop_front()` и выбрасывает те, чей `start_tick_index` не нужен; очередь кончилась --
  `NotEnoughTickArrayAccount`. Значит массивы подставляются в места **по возрастанию места**, а их
  порядок берётся у котировки (`нужные_массивы` -- по ходу свопа, первым массив текущего тика).
* **Дописывать в конец можно**, и это не догадка: остаток разбирается по ДЛИНЕ счёта, поэтому
  расширение между массивами разбор не прерывает. У `swap` (v1) первый массив стоит на месте 9, а в
  остатке бывает только расширение -- мест под массивы одно, а нужно три; без дописывания такой
  сигнал терялся бы зря.
* **Чужой счёт в остатке -- отказ.** На первом счёте другой длины программа прекращает разбор, и
  дописанное за ним не прочитает. Такой счёт в живых данных встретился (адрес
  `He7p7JqTGkxFjwdkrkipZBUGjLyA7cQBJGPJx6NRJ6aY` у пула `MhJNpUtFnZuHMoBu9yZnUAKHsQ1e2SC85yx2QAuSiPW`,
  8 инструкций): ни массив этого пула, ни расширение -- чем он является, в данных нет.

Расширение битовой карты, если оно нужно (шаг тика меньше 15 -- только тогда программа за ним
пойдёт), а в шаблоне его нет, **дописывается**; дописать некуда -- отказ.

## Шаги в торговом пути

1. **Шаблон** -- `шаблон(tx_источника, пул)`: инструкция CLMM по этому пулу, вид по дискриминатору.
2. **Разворот под покупку** -- `под_покупку(...)`: если сделка источника была продажей,
   переставляются места 3/4, 5/6 и (у `swap_v2`) 11/12. Минты и программы сторон прикрепляются к
   шаблону: у `swap` (v1) минтов в инструкции нет вовсе, и без них наши ATA не вывести.
3. **Чтение 1:** `getMultipleAccounts([пул, адрес_расширения(пул)])`.
4. **Какие массивы:** `нужные_массивы(pool, ext, zero_for_one, 3)`; `zero_for_one` -- по минту
   котировки против `token_mint_0` пула.
5. **Чтение 2 -- одним запросом:** `getMultipleAccounts([пул, amm_config] + адреса_массивов)`, чтобы
   пул, конфиг и массивы были из одного слота. Шаг тика у пула и у конфига обязан сойтись -- иначе
   прочитан не тот конфиг, и ставка комиссии тоже не та.
6. **Котировка:** `котировка_точный_вход(...)`. Не хватило массива -- `ОшибкаCLMM("нет tick array N")`,
   отказ. Остался непотреблённый вход -- тоже отказ: ликвидности по направлению не хватило на всю
   сумму, и цепь вернула бы нам часть входа.
7. **Шаблон с нынешними массивами** -- `шаблон_с_нынешними_массивами(...)`.
8. **Сборка** -- `собрать_покупку(...)`: бюджет вычислений, ATA (идемпотентно), обёртка SOL, своп,
   чаевые. Хвост данных собирается заново: предел цены 0 (программа сама подставит границу
   направления) и `is_base_input = true`.

Вся дорога -- один вызов: `подготовить(tx_источника, пул=…, лампорты=…, проскальзывание=…,
rpc_call=…, минт_котировки=…, минт_базы=…, группа=…)` → `{ok, why_not, шаблон, min_out,
expected_out, fee, fee_share, чтений, мс_чтений, …}`. Форма ответа -- та же, что у
`bloom_own_send.массивы_dlmm_сейчас`.

## Правка полосы (делает Code-1, я общие модули не трогал)

Гейт у CLMM уже есть целиком: константа `CLMM`, запись в `SPECS`, имя типа в `ИМЕНА_ТИПОВ`, функция
`clmm_включён`, `ДОП_ТИПЫ_ПОЛОСЫ` и имя строителя для предела CU. Нужна одна развилка в `собрать()` --
та же, что и для Whirlpool и DBC, по словарю «адрес программы → модуль строителя»:

```python
М = МОДУЛИ_СТРОИТЕЛЕЙ.get(прог)          # {B.CLMM: c2_clmm_stroitel, ...}
if М is not None and М.включён(группа_сигнала):
    д = М.подготовить(tx_источника, лампорты=лампорты, проскальзывание=проскальзывание,
                       rpc_call=rpc_call, минт_котировки=C.WSOL, группа=группа_сигнала)
    if not д.get("ok"):
        из_["why_not"] = д.get("why_not"); return из_
    tpl, мо, СБОРЩИК = д["шаблон"], д, М
    mv = {"quote_mint": д["минт_котировки"], "base_mint": д["минт_базы"]}
else:
    ...прежний путь...; СБОРЩИК = B
```
и в конце -- `СБОРЩИК.build_buy(tpl, tx_источника, …)` вместо `B.build_buy(...)`: у модуля эта дверь
с той же подписью и тем же смыслом, что у `c2_swap_build.build_buy`. Остальное в `собрать()` не
меняется -- потолок комиссии пула читает `мо["fee_share"]`, предел CU берёт `tpl["ix"]`.

Флаг выключен -- развилка не срабатывает, и CLMM идёт прежним путём (`extract_template` →
`clmm_min_out`). То есть включение обратимо одним флагом, без правки кода.

Замер CU по логам живых сделок (38 инструкций в снимках Code-2): p50 **50 226**, p99 **62 509** -- в
нынешний `ПРЕДЕЛ_CU_НОВОГО` (200 000) укладывается с запасом.

## Что проверено офлайн, без сети и без симуляции

Прогон: `deploy/checks/stroiteli_vosstanovlenie.py --tip clmm --sbor <clmm_sbor.json ветки Code-2>`.
Узел подставлен: `getMultipleAccounts` отвечает из записанных байтов снимка. Отчёт --
`data/stroiteli/vosstanovlenie_clmm.json`.

| что | число |
|---|---|
| снимков, разобрано / всего | 33 / 40 (у 7 в транзакции нет инструкции свопа по этому пулу) |
| **данные инструкции байт в байт** | **33 из 33** |
| **список счетов байт в байт** | **27 из 33** |
| из расхождений -- только наши токеновые счета | 6 из 6 (все на месте 4, `output_token_account`) |
| вне правила полосы «котировка пула только SOL» | 20 из 33 |
| точная котировка на записанном состоянии | **12 из 13** пулов против SOL |
| наша покупка собралась | 12 из 12 |
| собранная транзакция сверена обратным разбором | **12 из 12** |
| размер нашей транзакции | 899 байт (p50 и max) |

**Почему 27, а не 33.** Все шесть расхождений -- одно место, `output_token_account`: у этих
источников он не ATA подписанта инструкции (сделка шла через агрегатор, подписант -- PDA роутера).
Раскладка и роли восстановлены у всех 33; тот же счёт по сбору Code-2 не является ATA payer у 25
инструкций из 401.

**Единственный отказ котировки** -- `ни один массив тиков не прочитан: [27000]`: нужного массива нет
среди записанных в снимке. Это предел сбора, а не порта.

## Чего не входит

* Точный выход (`is_base_input = false`) -- мы всегда покупаем точным входом.
* Налог Token-2022 на выходе. Программа сравнивает `other_amount_threshold` с суммой ПОСЛЕ налога
  минта выхода (`swap_v2.rs`: `amount_1_without_fee = amount_1 - transfer_fee_1`), а котировка
  отдаёт сырые единицы пула. Если база -- Token-2022 с налогом, вызывающий обязан уменьшить
  `min_out` на налог (как у DLMM -- снаружи модуля).
* Лимитные ордера на тике границы порт считает, но в сбор Code-2 их не попало ни одного: этот кусок
  математики на цепи не проверен.
* Сделки между нашим чтением и нашей покупкой меняют состояние -- то же место в блоке, что и в
  остальной модели.
