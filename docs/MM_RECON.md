# MM — экономика маркетмейкинга сток-токенов в закрытые часы (владелец, 2026-09-02)

Задача: измерить экономику маркетмейкинга сток-токенов в закрытые часы
с хеджем перпом. Публичный RPC + API Lighter, 0 Dune, 0 капитала.
Только измерение, ничего не торгуем. П.6 (дисциплина): «Оценить число
RPC-вызовов до старта и доложить ожидаемое время».

## Статус: discover не завершён — найдена архитектурная сложность, требующая решения владельца, а не просто «подождать ещё»

## 1. Рабочая вселенная кандидатов — определена из данных

Пересечение двух уже добытых в прошлых спринтах реестров:
`data/sprintR1_cache/r1_token_feed_map.csv` (32 сток-токена с
подтверждёнными price-feed адресами) и
`data/p4_lighter_cache/p4_lighter_markets_result.json` (45 рынков
Lighter) — токены, у которых есть И onchain-price-feed, И активный
перп-рынок на Lighter (без рынка хедж невозможен). **24 токена**: AAPL,
AMD, AMZN, COIN, CRCL, CRWV, DELL, EWY, GME, GOOGL, INTC, META, MSFT,
MSTR, MU, NBIS, NVDA, ORCL, PLTR, QQQ, RKLB, SNDK, SPY, TSLA.

## 2. Версия протокола — определена из данных: v4, не v3

Полная история (address-scoped, 5157 вызовов `eth_getLogs`) показала:
**0 из 24 токенов имеют v3-пул, 24 из 24 имеют v4-пул** (PoolManager
`0x8366a39cc670b4001a1121b8f6a443a643e40951`). Это подтверждает
предположение владельца (v4), но по факту данных, не по умолчанию —
как и требовалось.

## 3. Находка: массовое размножение технически различных `pool_id` — не «один спот-пул на токен»

Первая попытка калибровки (полный необработанный список) показала **у
NVDA 8270 уникальных v4 `pool_id`** (у GME — 3095, TSLA — 2446, SPY —
1986) — физически невозможно для одного «спот-пула акции». Расследование
подтвердило: PoolManager на Robinhood Chain активно переиспользуется
Pons V2 (бондинг-кривая градуации мем-токенов, см. `docs/G1_DESIGN.md`)
— вероятно, каждый запуск получает свой hook-контракт, из-за чего даже
пары с ОДИНАКОВЫМИ двумя валютами получают РАЗНЫЕ `pool_id` (Uniswap v4
`pool_id` — хэш от `(currency0, currency1, fee, tickSpacing, hooks)`, и
`hooks`-компонента, похоже, меняется от launch к launch).

**Первая эвристика фильтрации (порог: контрагент общий минимум для 3
разных сток-токенов) — недостаточна.** После неё осталось **2481
«genuine»-пула** (148 v3 + 2333 v4) на 24 токена — всё ещё абсурдно
много (у NVDA — 489 v4-пулов), и «общих контрагентов» набралось **128**
— тоже слишком много для «канонических котируемых активов».

**Вторая проверка (жёстче, сделана локально из уже собранных данных, БЕЗ
новых RPC-вызовов):** ограничил контрагента ТОЛЬКО тремя АДРЕСАМИ,
независимо подтверждёнными как реальные значимые активы через
СОВЕРШЕННО ДРУГОЙ источник данных (реальные кросс-чейн депозиты Across,
`docs/RELAYER_RECON.md`) — WETH (`0x0bd7d308f8e1639fab988df18a8011f41eacad73`),
USDG (`0x5fc5360d0400a0fd4f2af552add042d716f1d168`), нативный ETH
(`0x0…0`). Результат: **всё ещё 1573 пула** (72 v3 + 1501 v4) — у NVDA
391 пул ПРЯМО против WETH/USDG/native, у GME — 233, у SPY — 101, у MSTR
— 102.

**Вывод: даже пары сток-токен↔(WETH|USDG|native) переиспользуются Pons V2
десятками-сотнями раз технически различными `pool_id`.** Это означает,
что «отфильтровать шум по паре валют» в принципе не работает для этого
чейна — нужен другой критерий: **реальная ликвидность/объём по
КОНКРЕТНОМУ `pool_id`**, а не факт существования пары. Это, по сути,
правильная переформулировка самого п.1 задания («топ-5 по объёму,
определить из данных») — калибровка ДОЛЖНА была с самого начала мерить
объём по каждому кандидату и ранжировать, а не пытаться заранее
угадать «какие пулы настоящие» через эвристику по паре валют.

## 4. Почему это не «просто подождать ещё»

Калибровка Swap-плотности через `eth_getLogs` стоит ~10 вызовов на
`pool_id` (окно 20 000 блоков / chunk 2000). При 1573 кандидатах это
**~15 730 вызовов** — при наблюдаемой на этом RPC пропускной
способности (~45 вызовов/мин с учётом rate-limit и ретраев) это **~5.8
часов** ещё ОДНОГО прогона, просто чтобы отсеять шум для 24 токенов —
и это раздельно от собственно полной выгрузки сделок (п.1-5 задания).
Пять прогонов подряд (2026-09-02 19:14 — 2026-09-03 06:27, суммарно
**>11 часов**) уже потрачены на попытки найти дешёвую эвристику
по паре валют — она не работает на этом чейне из-за архитектуры Pons V2.

**Дешёвая альтернатива, не опробованная:** вместо `eth_getLogs`-скана
плотности свопов (дорого, по логам) — прямой `eth_call` к
`getReserves()`/аналогичной view-функции пула (по образцу
`PonsV2BondingCurveMath.getReserves()`, уже использованного в
`analysis/sc1_nvx_chronology.py` для SC1) — **1 вызов на pool_id вместо
10**, сразу показывает, есть ли в пуле реальная ликвидность (мёртвые/
технические пулы Pons V2, скорее всего, покажут нулевые или
незначительные резервы). Это на порядок дешевле (1573 вызова вместо
15 730) и является более прямым критерием «реальности» пула, чем
плотность Swap-логов. **Не запущено** — требует решения владельца,
продолжать ли (см. ниже).

## Решение нужно от владельца

Варианты (не выбираю сам — существенно меняет объём работы и уже
далеко за пределами исходной оценки):

1. **Продолжить**: запустить дешёвый `getReserves()`-предфильтр

3. **Отложить MM** совсем — уже потрачено более 11 часов при изначально
