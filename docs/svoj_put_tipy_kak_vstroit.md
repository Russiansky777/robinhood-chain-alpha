Модуль: `analysis/c3_svoj_put_tipy.py` (самопроверка **16/16**).
Инвентарь числами: `data/c3_inventar_tipov.json`.

## 1. Инвентарь: чем полоса торгует и где второго пути нет

Замер по `data/nashi_pump_amm.json` (562 позиции, снимок наших сделок). Имя и
адрес одной программы схлопнуты — иначе один тип считался бы дважды.

| тип | позиций | доля | свой путь продажи |
|---|---|---|---|
| Pump AMM | 197 | 35.1 % | **есть** (`bloom_lane_sell`) |
| Pump.fun (кривая) | 150 | 26.7 % | **есть** (`c3_prodavec_sborka`) |
| Jupiter v6 | 135 | 24.0 % | маршрутизатор, не тип пула |
| **Meteora DLMM** | **35** | **6.2 %** | нет |
| **Raydium CPMM** | **16** | **2.8 %** | нет |
| Raydium CLMM | 10 | 1.8 % | нет |
| Orca Whirlpool | 5 | 0.9 % | нет |
| Raydium AMM v4 | 1 | 0.2 % | нет |

Своим путём полоса закрывает **61.8 %** позиций. Остальные 11.9 % (не считая
Jupiter) идут только через Jupiter — то есть правило «лучший из двух» на них
вырождается в «один путь».

**Котировка по резервам** у всех этих типов уже есть
(`c2_swap_build.min_out_from_reserves`: отдельные ветки DAMM2/DBC/CLMM/DLMM/
LAUNCHLAB/BONDING плюс общая по двум хранилищам). Не хватает именно **сборки
своей продажи**.

## 2. Продажа Raydium CPMM своим путём

`swap_base_input` у CPMM — **13 счетов**, и это проверено на всех 25 живых
образцах. Направление задаёт не дискриминатор, а то, какие счета стоят входом
и выходом, поэтому

> **продажа = наша покупка, у которой переставлены четыре пары:**
> (4,5) счета пользователя, (6,7) хранилища, (8,9) программы токена,
> (10,11) минты. Места 0,1,2,3,12 (payer, authority, amm_config, pool_state,
> observation) **не трогаются**.

```python
import c3_svoj_put_tipy as SP
ш = SP.shablon_prodazhi_cpmm(tx_нашей_покупки, nash_koshelek=кошелёк)
if ш["ok"]:
    счета = ш["accounts"]      # 13 штук, готовы к сборке инструкции
```

Перестановка **проверяется остатками самой транзакции**: какое хранилище какой
минт держит, говорит цепь (`pre/postTokenBalances`), а не раскладка по памяти.
Не сошлось — отказ по имени (доказанный красный в самопроверке: подменили
минты в остатках — шаблон отказал).

Котировка: `SP.kotirovka_cpmm(rezerv_vhoda=…, rezerv_vyhoda=…, vhod=…,
komissija_bps=…)` — постоянное произведение с комиссией. **Ставка комиссии не
предполагается**: она живёт в `amm_config` (счёт 2), и без неё котировки нет.
Два резерва читаются **одним** `getMultipleAccounts` на два хранилища.

## 3. Размер пакета с закрытием счёта

`SP.razmer_tx(...)` считает размер версии 0 аналитически; формула **сверена с
настоящей сериализацией** (solders, 05.10) — расхождение **ноль байт** на
четырёх разных формах. Векторы записаны в самопроверке, поэтому она идёт без
solders.

| пакет | байт | влезает в 1232 |
|---|---|---|
| CPMM своп + nonce + 2×ComputeBudget + чаевые + **closeAccount**, 20 ключей | **1017** | да, запас 215 |
| то же при 36 ключах | **1529** | **нет**, перебор 297 |

То есть рента не копится: закрытие счёта в ту же транзакцию **влезает**, пока
ключей не больше примерно тридцати. Где не влезает — модуль говорит это
числом **до** отправки, а не отказом сети после.

## 4. Что нужно от Code-1 для боя

**Главного не хватает: живой ПРОДАЖИ.** В репозитории 25 образцов CPMM — три
покупки за SOL и **ноль продаж**, поэтому сверить перестановку байт в байт не
с чем, и она держится на инвариантах. Снять по одной живой продаже каждого
типа (только чтение, любой известный нам пул):

```
python3 -c "import json,urllib.request,os;u=os.environ['BLOOM_RPC'];b=json.dumps({'jsonrpc':'2.0','id':1,'method':'getTransaction','params':['<ПОДПИСЬ_ПРОДАЖИ>',{'encoding':'jsonParsed','maxSupportedTransactionVersion':1,'commitment':'finalized'}]}).encode();print(urllib.request.urlopen(urllib.request.Request(u,data=b,headers={'Content-Type':'application/json'}),timeout=15).read().decode())" > data/c3_prodazha_cpmm.json
```

Нужны: CPMM, DLMM, CLMM (по одной продаже). С ними перестановка и размер
проверяются байт в байт, и свой путь можно включать за флагом.

Второе: **ставка комиссии пула** — одно чтение `amm_config` на пул, значение
меняется редко и кэшируется.
