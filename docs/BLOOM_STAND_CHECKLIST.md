# Стенд Bloom: контролируемая проверка детектора и исполнителя

Смысл стенда — не ждать органических сигналов, а получить все нужные
случаи по заказу, с кошелька владельца, и сверить ожидаемое с фактическим
по подписям.

**Тестовые источники — два, у обоих порог 0.05 SOL-эквивалента и все
остальные фильтры как у BATCH-5:**

| адрес | что это | какие пункты |
|---|---|---|
| `8aTMUKspLnkm7jaHf21qfB1b5dzPzXgsmcjPPnJPaPtA` | кошелёк владельца **в Fomo**: комиссию платит Fomo, владелец — второй подписант. Это путь наших боевых источников, и разбор такой сделки надо проверить отдельно | **1–3** |
| `DNJeTYni5QQVCwNNt1SrHu1GjYR4ak5Zw7LeuFsKYmXX` | обычный кошелёк владельца | **4–10** |

В env хоста они лежат одной строкой `BLOOM_TEST_SOURCES` через запятую.

**Изоляция.** Каждое решение по этому источнику несёт `test_source: true`.
Такие сигналы **не входят** в живую сверку с DBot, в счётчик 30 сигналов
и в пары А/Б — они идут отдельным разделом журнала (`by_code_test_source`)
и отдельным разделом отчёта.

**Порядок покупок владельца:** по одной, с паузой **не меньше 60 секунд**,
с сообщением времени каждой. Сверка идёт по подписям в цепи.

## Второй путь выхода: Jupiter Ultra, правило 4

Bloom по токену п. 1 трижды подряд повёл продажу через один и тот же пул
Meteora DAMM v2 без ликвидности в диапазоне (авто-ордер + две попытки

Bloom, поэтому нужен путь, где маршрут выбирает Jupiter.

Как сделан пол по выходу -- проверено на живом API Ultra 23.09 23:36Z по
тому же токену (`92.278326` штук, вход `0.001 SOL`):

| что | значение | вывод |
|---|---|---|
| `slippageBps` в запросе | 3000 (принят, возвращён в ответе) | проскальзывание задаётся явно, значит пол 70 % просится |
| `outAmount` | 895 562 лампорта (0.000896 SOL) | котировка |

| `router` | `metis` | не RFQ |
| байты транзакции (529 байт) | порога прямым числом НЕТ; котировка и 3000 bps -- ЕСТЬ | minimum считается на цепи из них, то есть пол обеспечен подписываемыми байтами |
| котировка к входу | 86–90 % | выше границы 30 %, продавать можно |

Порядок в коде: ордер → проверка пола → подпись → отправка. Ниже пола
транзакция не подписывается вообще; котировка ниже 30 % от входа -- `UNSOLD`
и строка владельцу, а не продажа за бесценок.

Чего не хватает для живой продажи: секрета `BLOOM_WALLET_KEY` (приватный
ключ кошелька исполнителя). Без него подписать нечем; деплой с
`via_jupiter: 1` и пустым секретом останавливается с объяснением, а не
поднимает сторожа, который каждый круг отказывается продавать.

## Проход B — live-test на 0.01 SOL: пункты 1, 3, 4, 5, 9

`BLOOM_LIVE_TEST=1`. Покупки только по тестовому источнику; сигналы
реальных источников в этом режиме идут **исключительно в журнал** (код
`LIVE_TEST_SKIP_REAL_SOURCE`). Лимиты, оба рубильника и сторож действуют
полностью.

Размер — **0.01 SOL**. Если Bloom отвергнет тело по минимуму
(`INVALID_REQUEST` со ссылкой на минимум), делается **один** повтор на
**0.02 SOL**, и первый код ошибки идёт в доклад. На любом другом коде
повтора нет: 200 у Bloom означает «принято», и слепой повтор способен
купить второй раз.

## Гейт live на реальных источниках

Все четыре условия одновременно:

1. все пункты A и B совпали с ожиданием;
2. ноль ложных покупок;
3. все тестовые позиции закрыты;
4. сверка при старте (`bloom_reconcile`) чистая.

Первый live — размер **0.05 SOL**. Переход на 0.2 — при **30 органических
сигналах** с «DBot купил, мы нет» = 0.

**Оговорка, которую нельзя терять:** пары А/Б при 0.05 SOL идут в зачёт
**слотов**, но не в разницу результата — размер входа другой, и сравнивать
выручку с DBot на 0.5 SOL было бы подменой. В отчёте это помечается.
