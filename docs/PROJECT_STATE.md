## 4. РЕЕСТР НАЙДЕННЫХ БАГОВ (самое ценное — чтобы не наступить снова)

1. **`canceled-margin-not-allowed`** — реальная причина 0%/27%/0%/0% филла на 4 первых попытках хеджа (подтверждено аутентифицированным чтением `GET /api/v1/accountOrders`, не гипотеза). Корень: `p5_live_precheck.py` считал требуемую маржу по ЗАШИТОМУ допущению `MAX_LEVERAGE = 3.0`, а РЕАЛЬНОЕ плечо аккаунта было 2× (`initial_margin_fraction="50.00"`) — формула молча считала маржи достаточно, когда её не было. Опровергнуты по пути (реальными данными, не рассуждением) три другие гипотезы: Volume Quota Program (Premium-only, не относится к Standard-аккаунту), post_only/лимитный ордер (SDK не поддерживает такой параметр в этом пути), тонкая глубина книги (реально 412 ETH на 0.10% против запроса 0.0365 ETH). **Фикс:** `real_eth_leverage()` — плечо ВСЕГДА читается с аккаунта (`GET /api/v1/account`, публичный эндпоинт), допущение убрано из формулы совсем.
2. **`err=None` НЕ доказывает исполнение ордера.** `create_market_order`/`create_market_order_limited_slippage` может вернуть `200 OK, err=None` с реальным `tx_hash`, но без фактического филла (тело ответа содержит `"ratelimit": "didn't use volume quota"` — не ошибка, но и не подтверждение). **Фикс:** `_verify_hedge_filled()` — до 4 попыток свежего чтения РЕАЛЬНЫХ `positions()` после отправки, порог ≥85% запрошенного размера (не 50% — частичный 50-85% филл всё ещё существенная голая экспозиция).
3. **`actions/checkout@v4` shallow-clone ломал confirm-гейт.** С дефолтным `fetch-depth=1` `git log -1 --name-only` на корневом коммите (нет родителя) печатает ВСЕ файлы в дереве, не только реально изменённые в пуше — если CONFIRM-маркер хоть раз существовал где-то в истории, ЛЮБОЙ последующий push (в т.ч. чистый dry-run) детектился как РЕАЛЬНЫЙ. Воспроизведено локально (`git clone --depth 1`), эмпирически проверен фикс отдельным dry-run прогоном перед тем, как снова доверять гейту. **Фикс:** во всех confirm-гейтед воркфлоу — режим определяется ТОЛЬКО существованием файла-маркера (`[ -e MARKER ]`, без диффа по git log), маркер удаляется (`git rm -f --ignore-unmatch`) сразу после использования в шаге "Commit results" — не может "протухнуть" и сработать повторно.
4. **Gas-race.** Один `eth_gasPrice()` на весь пакет последовательных tx — base fee успевает подрасти, пока ждём квитанцию предыдущей tx, следующая падает `max fee per gas less than block base fee`. **Фикс:** `send_with_gas_retry()` — свежий `eth_gasPrice()` на КАЖДОЙ попытке + эскалирующийся буфер `[1.15, 1.4, 1.75]`, несколько попыток прежде чем жёсткий стоп.
5. **Across доставляет WETH (в одном реальном случае — через `MulticallHandler`-контракт, который сжигает WETH через `Transfer→address(0)` без сопутствующего `Withdrawal`-события, т.е. не канонический `WETH9.withdraw()`, механизм до конца не расшифрован, но handler в итоге не удерживает ни WETH, ни native ETH — не зависло), не гарантированно native ETH.** Сайзер читал только native-баланс кошелька, недооценивая реальный доступный капитал, сидящий в WETH. **Фикс:** `wallet_balances()` теперь читает WETH; `usable_eth_total = (native ETH − газ-резерв) + WETH`; шаг обёртывания (`wrap`) в mint-последовательности отправляет только НЕДОСТАЧУ сверх уже имеющегося WETH (`wrap_amount_wei`), пропускается целиком, если существующего WETH уже хватает.
6. **`typical_gap_pct_avg` выброс `1.8e+28%`** (P3-гард, QQQ, реальный прогон 33762766617) — один тонкий/давно не торговавшийся v4 `pool_id` дал аномальную цену на одной closing-транзакции, испортив СРЕДНЕЕ (медиана устойчива к выбросам, среднее — нет). **Фикс:** явный порог правдоподобия `>1000% → исключить из среднего`, честно считается и репортится, сколько исключено (`gap_pct_outliers_excluded_from_avg`), не скрывается сам факт выброса.
7. **`positions(tokenId).tokensOwed0/1` обновляются только после "poke" и без него возвращают нули** — прямое чтение `NonfungiblePositionManager.positions()` НЕ отражает реально накопленные, но ещё не собранные торговые комиссии позиции (поле обновляется лениво, только на действие с позицией — mint/increase/decrease/collect — а не непрерывно по мере накопления). ## 5. Формулы (проверены дважды против факта биржи, не только выведены теоретически)

**Дельта хеджа (ETH-нога LP-позиции при текущей цене P, в диапазоне [P_lower, P_upper]):**

```
amount_ETH(P) = L × (1/√P − 1/√P_upper)
```

Дословно `Uniswap/v3-periphery/contracts/libraries/LiquidityAmounts.sol`, реализовано в `p5_live_precheck.py::v3_amounts()`. Это и есть требуемый размер шорта на Lighter.

**Расстояние до ликвидации (оценка, cross-margin, короткая позиция, единственная открытая позиция в пуле обеспечения):**

```
P_liq = (collateral + size×P0) / (size×(1+mmf))
% роста до ликвидации = P_liq/P0 − 1
```

`collateral` — весь доступный collateral аккаунта (cross-режим пулит обеспечение по всем позициям — корректно ТОЛЬКО когда позиция единственная, гарантируется flat-precondition перед хеджем), `size` — размер шорта (ETH), `P0` — цена входа, `mmf` — `maintenance_margin_fraction` рынка (реальное сырое поле `orderBookDetails`, единицы — `raw/10000`, подтверждено формулой самого SDK `imf=int(10000/leverage)` из `update_leverage()`). Реализация — `p5_live_step1.py::liquidation_distance_pct()`.

**Проверено против факта дважды, на двух РАЗНЫХ реальных открытиях** — обе проверки дали разницу 0.0 между формулой и реальным полем `liquidation_price` позиции:
- Первое живое открытие (tokenId 999556, плечо 3.0003×): вход $2499.94, реальный `liquidation_price=$10046.265582243843` ⇒ implied move 301.8602679361842%; формула независимо дала 301.8602679361843% (разница на уровне последнего знака float, не содержательная).
- Текущее открытие (tokenId 1000756, плечо 3.0003×): вход $2506.43, реальный `liquidation_price=$4044.0837011564145` ⇒ implied move 61.348360064171544%; формула дала ровно то же число.

Точные цифры — `data/p3_guard_cache/p5_live_step1_result.json` (текущее открытие) и история коммитов (предыдущий `p5_live_step1_result.json` перед закрытием 999556).

**Единицы плеча/margin fraction (реальная формула SDK, не догадка):** `imf_raw = int(10_000 / leverage)` ⇒ `leverage = 10_000 / imf_raw`. Строковое поле `positions[].initial_margin_fraction` в ответе `/api/v1/account` — уже ПРОЦЕНТ (`raw/100`), напр. `"33.33"` ⇒ `leverage = 100/33.33 ≈ 3.0003`.

**Эластичность требуемого хеджа по цене (владелец, задача расширения отчёта, 2026-09-04) — производная формулы `amount_ETH(P)` выше:**

```
x(P) = amount_ETH(P) = L × (1/√P − 1/√P_upper)
dx/dP = −L / (2×P^1.5)

(dx/x) / (dP/P) = −(1/(2√P)) / (1/√P − 1/√P_upper)
```

При текущей цене на момент снятия ($2501.15, диапазон [$2258.86, $2760.88], `data/p3_guard_cache/p5_live_snapshot_1000756_result.json`, 2026-09-03T22:54:10Z): **эластичность = −10.37** (независимо посчитана владельцем на близком по времени снимке цены $2495.62: −10.14 — то же порядка величины, различие — реальный дрейф цены между двумя снятиями, не расхождение формул). Смысл: **1% движения цены ETH ⇒ ~10% изменения требуемого размера хеджа** вблизи текущей точки диапазона — и это НЕ константа, эластичность зависит от того, где цена находится внутри диапазона (растёт по модулю ближе к границам, минимальна в середине).

**Отсюда прямое следствие для порога ребаланса (владелец, дословно): "скорость дрейфа «X%/час» — не константа, это одна реализация цены; правильная запись порога — в процентах хода цены, а не хеджа."** Наблюдавшаяся на первой живой точке скорость дрейфа хеджа ≈9.7%/час размера хеджа (см. `data/p5_live_snapshot_1000756_result.json` первого прогона) — артефакт конкретного пройденного пути цены и текущей эластичности (~−10 в этой точке), не универсальная константа самого пула/позиции. **Порог ребаланса, когда будет выбираться, должен фиксироваться в % хода ЦЕНЫ (dP/P), а не в % дрейфа ХЕДЖА** — дрейф хеджа тогда получается автоматически через актуальную эластичность в момент проверки, а не наоборот. Демон (`p5_live_bot.py`) ещё не написан — это регистрация формулы и вывода ДО реализации, не изменение уже принятого решения по диапазону/порогам (§8).

## 6.1. GeckoTerminal API — реальные ограничения и особенности (для будущей работы над σ пула, §8)

Найдено эмпирически при работе над P5 (реальные вызовы, не документация "как должно быть" — GT публичной OpenAPI-спецификации не даёт):

- **Слаг сети — `robinhood`, НЕ `robinhood-chain`.** Неверный слаг возвращает 404, не подсказывает правильный.
- **Rate limit: 30 запросов/мин без ключа**, ключ не требуется для базовых эндпоинтов (`/pools/{addr}`, OHLCV) — но именно по этой причине бюджетировать вызовы заранее, не бить лимит вслепую сериями.
- **OHLCV-агрегаты** (`GET /networks/{network}/pools/{addr}/ohlcv/{timeframe}`): доступные `timeframe` — `minute` (агрегация `1`/`5`/`15`), `hour` (`1`/`4`/`12`), `day` (`1`). `limit` — максимум **1000** точек за запрос.
- **`include_empty_intervals=true` ОБЯЗАТЕЛЕН** — без этого параметра эндпоинт молча пропускает интервалы без сделок, и таймстемпы соседних точек "едут" (перестают быть равномерным шагом) — для расчёта волатильности по равномерной сетке это критично, не косметика.
- **Пагинация — через `before_timestamp`** (unix-время в СЕКУНДАХ, не миллисекундах) — не через номер страницы/курсор.
- **Ориентация пула `0x52e65B17...` (подтверждено реальным ответом `/pools/{addr}`, `relationships.base_token`/`quote_token`): `base` = USDG, `quote` = WETH.** Для получения цены ETH в USDG использовать `currency=token&token=quote` (цена quote-токена в единицах base, т.е. напрямую ETH/USDG) — **не** конвертировать через `currency=usd`: USD-цена самой USDG на этой сети шумная (владелец, 04.09.2026: наблюдённый суточный диапазон **$0.9374–$1.0095** — конкретная пара цифр получена владельцем, не перепроверена этой сессией отдельным API-вызовом, но направление проблемы понятно и без перепроверки: USDG не идеальный $1-стейбл на этом чейне) — считать по ней σ ETH/USDG значит примешивать шум курса стейблкоина к волатильности самой торгуемой пары, искажая результат.

## Правила работы с Dune (оплачены ~1400 кредитами ошибок)

1. Сырые данные не покидают Dune: наружу через API — только агрегаты. Чтения биллятся по объёму.
2. Санитарная проверка ДО исполнения: оценка >40 кредитов ИЛИ множественное сканирование тяжёлых CTE = жёсткий стоп.
3. Отклонение факта от оценки >2x = немедленный стоп сессии.
4. Смоук-тест на одном дне данных до любого полнопериодного прогона.
5. Постоянный кэш `data/sprint*_cache/` с коммитом сразу после каждой оплаченной операции.
6. Бюджетный гард: `data/credits_spent.json`, проверка до КАЖДОЙ платной операции, лимит на спринт в конфиге. Лимит поднимается только явным решением владельца, максимум дважды.
7. Состояние цикла (2026-09-01): потрачено 2138.84 из 2500, сброс 14.09.2026. Резерв 20 неснижаемый. Мультиаккаунты запрещены.
8. Пороги в деньгах, не в голых кредитах: операции дешевле ~$1 не требуют доклада штабу.
9. **Новый Dune-аккаунт "Mozila" (2026-09-04, `secrets.DUNE_API_KEY_MOZILA`) — правила те же + два дополнительных (владелец):** (а) каждый НОВЫЙ запрос сначала на `LIMIT 100` для проверки синтаксиса/структуры, полный прогон — только вторым шагом; (б) фактическая стоимость каждого запуска — в `data/credits_spent_mozila.json` (отдельный от старого леджер, коммитится сразу после каждой платной операции, тот же механизм `credit_guard.py`, см. `CREDIT_GUARD_FILE`/`CREDIT_GUARD_NAMESPACE=funding_mozila`) — остаток виден в файле в любой момент, не должен обнаружиться нулём внезапно.
