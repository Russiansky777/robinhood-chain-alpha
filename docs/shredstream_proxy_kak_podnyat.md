# shredstream-proxy: как поднять и как проверить, что записи идут

Всё, что можно было сделать без сети и без хоста, сделано. Code-1 остаётся запустить.

| что | где |

## Три вещи из кода, которые надо знать до запуска

**1. Дата отключения ShredStream (5 сентября 2026) нас не касается — и это проверено
по коду, а не по надежде.** В `main.rs` есть `SHREDSTREAM_SHUTDOWN_DATE` и отказ
`ShredstreamProxyError::Shutdown`, но он стоит внутри
`if matches!(&shredstream_args, ProxySubcommands::Shredstream(_))` — то есть **только**
в режиме, который просит шреды у Jito. `ForwardOnly` запускается и после этой даты.
Прогон сборки проверяет именно это условие и падает, если оно уедет.

**2. `--dest-ip-ports` обязателен, даже когда нужны только записи.** Иначе прокси
выходит с `No destinations found. You must provide values for --dest-ip-ports or
--endpoint-discovery-url.` Поэтому в юните стоит тупик на себя `127.0.0.1:20099`, где
никто не слушает: наружу не уходит ничего.

**3. «gRPC только на localhost» флагом НЕ делается — флага такого нет.** Сервер
записей биндится на все адреса, и адрес зашит:

```rust
server::start_server_thread(SocketAddr::new(IpAddr::V4(Ipv4Addr::UNSPECIFIED), port), ...)
```

Значит закрывать порт надо **снаружи процесса**, и это не «он слушает localhost», а
«мы не даём до него дойти». Разницу надо держать в голове. Два независимых способа,
и нужны оба:

* на хосте политика ufw уже `Default: deny (incoming)` — порт записей снаружи и так
  закрыт; плюс явное правило-ремень (ниже);
* фильтр адресов самого юнита (`IPAddressDeny=any` + `IPAddressAllow=…`) —
  в юните он **закомментирован нарочно**: `IPAddressDeny=any` закрывает юниту и вход
  тоже, и без строки с адресом источника шреды перестанут приходить ВОВСЕ, а выглядеть
  это будет как «прокси не работает».

## Как поднять

**0. Кто нам на самом деле шлёт.** До всего остального: на 20001/udp в ufw уже
открыты два адреса замера (`64.130.43.48`, `67.209.53.15`). Посмотреть, кто шлёт
сейчас, не поднимая прокси:

```bash
sudo timeout 20 tcpdump -n -i any udp port 20001 | head -40
```

Адрес из вывода — это и есть тот, который пойдёт в `IPAddressAllow`, если фильтр юнита
включать. Пусто — дальше идти незачем: прокси нечего принимать.

**1. Собрать.** Прогон `Шреды: сборка shredstream-proxy`, вход `runner`:

* `cloud` (по умолчанию) — бегунок `ubuntu-22.04`, бинарник артефактом. 22.04, а не
  `latest`, нарочно: собранное на старой glibc работает на новой, обратное — нет.
* `host` — собрать на NL-хосте (`nice 19`, `ionice 3`), бинарник сразу в
  `/home/bot/shredstream_build`. Ставить пакеты на торговом хосте прогон **не будет**:
  нет инструментов — падает и говорит, каких.

**2. Положить и проверить сумму.**

```bash
sudo -u bot mkdir -p /home/bot/shredstream
sudo -u bot cp jito-shredstream-proxy /home/bot/shredstream/
sudo -u bot chmod 755 /home/bot/shredstream/jito-shredstream-proxy
sha256sum /home/bot/shredstream/jito-shredstream-proxy   # сверить с MANIFEST.txt
/home/bot/shredstream/jito-shredstream-proxy forward-only --help | head -30
```

**3. Порт записей закрыть снаружи — ДО первого запуска.**

```bash
sudo ufw deny in 9999/tcp comment 'gRPC zapisey shredov -- tolko localhost'
sudo ufw status numbered | grep -n 9999
```

**4. Руками, в переднем плане, две минуты.** Юнит — потом; сначала надо увидеть
журнал своими глазами. Строка — `deploy/shredstream/komandnaya_stroka.txt`.
Ожидание в журнале: `Shredstream started, listening on 0.0.0.0:20001/udp.`,
`starting server on 0.0.0.0:9999`, и раз в минуту сводка принятого. Если в сводке
нули — шреды не приходят, и виноват не прокси (см. шаг 0).

**5. Юнит.**

```bash
sudo cp deploy/shredstream/shredstream-proxy.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start shredstream-proxy      # enable -- только после проверки ниже
systemctl status shredstream-proxy --no-pager
journalctl -u shredstream-proxy -n 50 --no-pager
```

## Как проверить, что записи идут — и это ТЕ ЖЕ транзакции

Что прокси что-то принял, видно в его сводке. Но «принял шреды» и «из них собираются
наши транзакции» — разные утверждения, и второе надо мерить. Этим меряется:

```bash
cd /home/bot/robinhood-chain-alpha
HELIUS_API_KEY2=... python3 deploy/checks/shredy_zapisi_protiv_ws.py \
    --grpc 127.0.0.1:9999 --seconds 120 --out /tmp/zapisi_protiv_ws.json
```

Нужен `grpcio` (`pip install grpcio` в venv бота) и `websockets` — он уже есть у
слушателя шредов. Заглушки `protoc` **не нужны**: запрос `SubscribeEntriesRequest`
пустой (ноль байт), а ответ `Entry` — два поля, они разбираются вручную.

**ГЛАВНОЕ ЧИСЛО, которое печатает проверка:**

```
  ГЛАВНОЕ ЧИСЛО -- подписей WS нашлись в записях: N из M (…%)
  опережение записей над WS: медиана … мс, p90 … мс; записи раньше WS у … из N
```

`M` — сколько транзакций наших источников пришло по WS за окно; `N` — сколько из них
нашлось в записях, собранных из шредов. **Пока N = 0, «записи идут» не доказано**, и
проверка возвращает код 2 и печатает «НЕ СОСТОЯЛОСЬ» — чтобы ноль нельзя было принять
за успех. Опережение считается **только по пересечению** и **одними монотонными
часами** одного процесса: сравнивать настенное время двух источников на миллисекундах
нельзя, NTP правит его на десятки миллисекунд.

Обратное направление считать бессмысленно: в записях транзакций на порядки больше, чем
у наших источников (WS подписан только на них). Поэтому числитель — WS, а не записи.

## Что уже измерено (без сети) и что измерит Code-1

Своё измерение у меня одно, зато от него зависит всё остальное: **разбор записей
верен**. `python3 deploy/checks/shredy_zapisi_protiv_ws.py --self-test` — **23/23**,
и главные четыре проверки идут на НАСТОЯЩИХ транзакциях, собранных solders
(legacy, v0 без таблиц, v0 с таблицей адресов, v0 с двумя инструкциями): разбор обязан
съесть **ровно** столько байт, сколько их в транзакции, и вернуть **ту же подпись**,
что у solders. Сойтись случайно это не может. Плюс: `Vec<Entry>` из трёх записей (одна
пустая) — подписи и порядок те же и блоб съеден без остатка; лишний байт в конце —
отказ, а не «почти сошлось».

**Числа, которых у меня нет и быть не может:** сколько записей доходит, какая доля
транзакций WS в них находится и на сколько раньше. Это живой замер на нашем канале, и
его делает Code-1 шагом 6. Сети у меня нет, прокси я не собирал и не запускал,
прогонов GitHub Actions не делал.

## Чего этот путь не решает

* **На приёмном порту аутентификации нет никакой.** Шреды примет кто угодно, кто
  дотянется до 20001, — и подложные тоже. Порт обязан быть открыт ТОЛЬКО на адрес
  источника; это уже так, и так должно остаться.
* **Неполные наборы теряются.** Записи собираются из FEC-наборов; прокси восстанавливает
  недостающие data-шреды из кодовых (`ReedSolomonCache` в потоке `shred_reconstructor`),
  но набор, пришедший слишком дырявым, просто не даст записи. Какая это доля на нашем
  канале — часть замера шага 6, из кода её не видно.
* **Решения на этом пути ещё нет.** Штаб решает после числа Triton; здесь только
  подготовлено так, чтобы вечером оставалось запустить.
