# Пост-мортем по расходу кредитов Dune (перед запуском Sprint 1.5)

Написано по запросу пользователя ДО запуска `run_sprint_1_5.yml` — три
условия из этого запроса: (1) пост-мортем, (2) персистентный бюджетный
гард, (3) инвентаризация шагов перед запуском. Ничего не запускалось,
пока не написан этот документ.

### Проверка гипотезы пользователя

Заявленный факт: потрачено в цикле 1394 кредита. 1394 − 217.978
(единственный чистый успешный прогон Sprint 1) ≈ **1176** — арифметика
сходится с числом, которое назвал пользователь.

Но реконструкция ПО ЛОГАМ всех 13 прогонов вместе даёт только
~560–580 кредитов, а не 1176. **Разрыв ≈ 800 кредитов не объясняется
логами GitHub Actions.**

**Вердикт: гипотеза подтверждена частично, не полностью.**

Подтверждено конкретными примерами:
- #3→#4: идентичные 5 запросов schema probe выполнены заново с нуля
  (кэш не пережил смену контейнера).
- #11: ~100-кредитный полномесячный запрос запущен и потерян нашим
  поллингом при таймауте — с высокой вероятностью продолжил
  исполняться (и списывать кредиты) на стороне Dune.
- #13: sensitivity-прогон MIN_TRADES=15 пересчитал 03/04/05 заново
  (~42 кредита) из-за бага с churn query_id, хотя SQL был идентичен.
- #8: запрос реально исполнился и был оплачен, но стоимость никогда не
  попала в лог (крах на скачивании результатов ДО строки печати).

Но эти конкретные находки в сумме дают дополнительно ~115–120
кредитов — далеко не 800. **Я не буду утверждать, что механизм
query_id-churn + смерть кэша контейнера полностью объясняет 1176
кредитов — это была бы подгонка под ответ, а не факт.** Честный
следующий шаг — дашборд биллинга на dune.com/settings/billing (реальный
источник правды с разбивкой по каждому запросу), к которому у меня нет
API-доступа отсюда. Я не могу подтвердить полный разрыв без него.

## 2. Персистентный бюджетный гард — реализовано

- `data/credits_spent.json` (закоммичен, инициализирован фактом
  пользователя): `billing_cycle.initialized_spent = 1394.0`,
  `billing_cycle.external_limit = 2450.0`,
  `sprint15.budget_remaining_at_init = 150.0`, `sprint15.spent = 0.0`.
- `analysis/credit_guard.py`: `check_before_execute(name, estimate)` —
  вызывается из `DuneClient.execute()` (то есть перед КАЖДЫМ реальным
  вызовом Dune `/query/{id}/execute` в проекте, а не только из
  `run_sql_cached`). При `sprint15.spent + estimate > 150` ИЛИ
  `(1394 + sprint15.spent) + estimate > 2450` — печатает полный отчёт и
  делает жёсткий `raise BudgetGuardStop` (`SystemExit`), ничего не
  исполняется.
- `record_execution(name, actual_credits, execution_id)` — вызывается
  сразу после того, как становится известна (или окончательно
  неизвестна — таймаут) реальная стоимость: обновляет
  `sprint15.spent`, пишет запись в `entries`, **коммитит и пушит файл
  немедленно** (не ждёт финального шага workflow) — так гард переживёт
  ровно те сценарии, что вызвали пробелы в пост-мортеме выше (#8, #11).
- Проверено локально: оценка 5 кредитов проходит, оценка 200 кредитов
  корректно останавливает выполнение до вызова Dune.

## Ревизия 2: вторая дыра — API Result Read биллится по объёму данных

Пользователь проверил биллинг-страницу Dune напрямую и нашёл то, что
пост-мортем выше не мог увидеть по логам: **чтение результата через
`/execution/{id}/results` биллится ОТДЕЛЬНО от execute(), по объёму
данных.** Пары execution_id на биллинг-странице подтвердили: чтение
полного результата `03_wallet_agg_july` (1,210,160 строк × 5 колонок =
6,050,800 датапоинтов) стоило **163.98 кредита ЗА ОДНО чтение** —
столько же (тир ×3) объясняет три отдельных факта чтения этого же
запроса в разных прогонах Sprint 1. Тиры 52.37×3 и 22.38×4 — судя по
всему, чтения `04_sniper_insider_exclusions` и `05_final_cohort_pool`
соответственно. Суммарно ~740 кредитов только на чтениях + три
исполнения полномесячного 02 (~102 каждое, включая один зафиксированный
в разделе 1 как "потерянный на таймауте поллинга") — **разрыв ~1176
кредитов объяснён.**

Наш гард (ревизия 1) стоял только на `execute()` — это была вторая
дыра. Каждый вызов `get_results_df()` в проекте до сих пор шёл в обход
любой проверки.

### Изменения

1. **Гард распространён на чтения.** `analysis/credit_guard.py`:
   `check_before_read(name, row_count, column_count)` — оценка по
   `estimate_read_credits()`, калиброванной на подтверждённом
   пользователем факте (163.98 / 6,050,800 датапоинтов, ×1.5 запаса) —
   та же персистентная проверка против лимита 150, с записью в
   `credits_spent.json` после операции (`record_read`). Вызывается из
   `DuneClient.get_results_df()` — то есть перед КАЖДЫМ реальным
   скачиванием результата в проекте, не только из специально
   помеченных мест.

2. **Принцип «сырые данные не покидают Dune».** `get_results_df()`
   теперь требует от вызывающей стороны заранее объявить
   `expected_max_rows`/`expected_columns` (дефолт 20k строк — выше
   этого явный сигнал "это построчная выгрузка, а не сводка", с
   предупреждением в логе, если факт превысил объявленное). Гейт 1
   (снайперы, обе версии окна), гейт 2, капы копируемости и отбор
   когорт теперь считаются ОДНИМ SQL-запросом на стороне Dune
   (`sql/03b_cohort_selection.sql`) — наружу через API едут только
   строки кошельков, попавших хоть в одну из 8 групп (когорта А/Б × 4
   комбинации), не полный гейтованный пул. Сводка по капам
   (`sql/03c_cap_summary.sql`, 4 строки) и гистограмма снайперов
   (`sql/03d_sniper_histogram.sql`, ≤4 строки) — тоже агрегаты на
   стороне Dune, не построчные выгрузки.

3. **План исполнения без пересчёта 02.** Pre-flight-проверка
   (`DuneClient.create_query(..., require_cached=True)`) подтверждает,
   что query_id'ы 02/01/03 уже в `query_id_map.json` (материализованы
   в Sprint 1, кэш actions/cache того же дня) — если нет, жёсткий отказ
   ДО единого платного вызова, а не тихий пересчёт 02 (~103-125
   кредитов). 03b/03c/03d ссылаются на эти query_id через `query_<id>`
   без повторного execute. Псевдослучайный контроль в 03b —
   детерминированный `sha256(seed || wallet_address)` вместо
   numpy-seed(42) (не идентично Sprint 1 побитово, но так же
   воспроизводимо).

4. **Пост-хок потолок на 03b.** Реальная стоимость execute() 03b (самый
   тяжёлый шаг — 8 проходов `row_number()` по ~1.2M строк) неизвестна
   заранее (Dune не даёт pre-execution оценку). Если факт > 60 —
   `sprint_1_5.py` немедленно останавливается (03c/03d/06×2 не
   запускаются), пишет частичный отчёт с чёткой пометкой.
