### Проверка гипотезы пользователя

Заявленный факт: потрачено в цикле 1394 кредита. 1394 − 217.978
(единственный чистый успешный прогон Sprint 1) ≈ **1176** — арифметика
сходится с числом, которое назвал пользователь.

Но реконструкция ПО ЛОГАМ всех 13 прогонов вместе даёт только
~560–580 кредитов, а не 1176. **Разрыв ≈ 800 кредитов не объясняется
логами GitHub Actions.**

**Вердикт: гипотеза подтверждена частично, не полностью.**

Подтверждено конкретными примерами:
- #3→#4: идентичные 5 запросов schema probe выполнены заново с нуля
  (кэш не пережил смену контейнера).
- #11: ~100-кредитный полномесячный запрос запущен и потерян нашим
  поллингом при таймауте — с высокой вероятностью продолжил
  исполняться (и списывать кредиты) на стороне Dune.
- #13: sensitivity-прогон MIN_TRADES=15 пересчитал 03/04/05 заново
  (~42 кредита) из-за бага с churn query_id, хотя SQL был идентичен.
- #8: запрос реально исполнился и был оплачен, но стоимость никогда не
  попала в лог (крах на скачивании результатов ДО строки печати).

Но эти конкретные находки в сумме дают дополнительно ~115–120
кредитов — далеко не 800. **Я не буду утверждать, что механизм
query_id-churn + смерть кэша контейнера полностью объясняет 1176
кредитов — это была бы подгонка под ответ, а не факт.** Честный
следующий шаг — дашборд биллинга на dune.com/settings/billing (реальный
источник правды с разбивкой по каждому запросу), к которому у меня нет
API-доступа отсюда. Я не могу подтвердить полный разрыв без него.

## 2. Персистентный бюджетный гард — реализовано

- `data/credits_spent.json` (закоммичен, инициализирован фактом
  пользователя): `billing_cycle.initialized_spent = 1394.0`,
  `billing_cycle.external_limit = 2450.0`,
  `sprint15.budget_remaining_at_init = 150.0`, `sprint15.spent = 0.0`.
- `analysis/credit_guard.py`: `check_before_execute(name, estimate)` —
  вызывается из `DuneClient.execute()` (то есть перед КАЖДЫМ реальным
  вызовом Dune `/query/{id}/execute` в проекте, а не только из
  `run_sql_cached`). При `sprint15.spent + estimate > 150` ИЛИ
  `(1394 + sprint15.spent) + estimate > 2450` — печатает полный отчёт и
  делает жёсткий `raise BudgetGuardStop` (`SystemExit`), ничего не
  исполняется.
- `record_execution(name, actual_credits, execution_id)` — вызывается
  сразу после того, как становится известна (или окончательно
  неизвестна — таймаут) реальная стоимость: обновляет
  `sprint15.spent`, пишет запись в `entries`, **коммитит и пушит файл
  немедленно** (не ждёт финального шага workflow) — так гард переживёт
  ровно те сценарии, что вызвали пробелы в пост-мортеме выше (#8, #11).
- Проверено локально: оценка 5 кредитов проходит, оценка 200 кредитов
  корректно останавливает выполнение до вызова Dune.
