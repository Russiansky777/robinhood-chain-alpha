Заявленный факт: потрачено в цикле 1394 кредита. 1394 − 217.978

## 2. Персистентный бюджетный гард — реализовано

- `data/credits_spent.json` (закоммичен, инициализирован фактом
  пользователя): `billing_cycle.initialized_spent = 1394.0`,
  `billing_cycle.external_limit = 2450.0`,
  `sprint15.budget_remaining_at_init = 150.0`, `sprint15.spent = 0.0`.
- `analysis/credit_guard.py`: `check_before_execute(name, estimate)` —
  вызывается из `DuneClient.execute()` (то есть перед КАЖДЫМ реальным
  вызовом Dune `/query/{id}/execute` в проекте, а не только из
  `run_sql_cached`). При `sprint15.spent + estimate > 150` ИЛИ
  `(1394 + sprint15.spent) + estimate > 2450` — печатает полный отчёт и
  делает жёсткий `raise BudgetGuardStop` (`SystemExit`), ничего не
  исполняется.
- `record_execution(name, actual_credits, execution_id)` — вызывается
  сразу после того, как становится известна (или окончательно
  неизвестна — таймаут) реальная стоимость: обновляет
  `sprint15.spent`, пишет запись в `entries`, **коммитит и пушит файл
  немедленно** (не ждёт финального шага workflow) — так гард переживёт
  ровно те сценарии, что вызвали пробелы в пост-мортеме выше (#8, #11).
- Проверено локально: оценка 5 кредитов проходит, оценка 200 кредитов
  корректно останавливает выполнение до вызова Dune.

## Ревизия 2: вторая дыра — API Result Read биллится по объёму данных

Пользователь проверил биллинг-страницу Dune напрямую и нашёл то, что
пост-мортем выше не мог увидеть по логам: **чтение результата через
`/execution/{id}/results` биллится ОТДЕЛЬНО от execute(), по объёму
данных.** Пары execution_id на биллинг-странице подтвердили: чтение
полного результата `03_wallet_agg_july` (1,210,160 строк × 5 колонок =
6,050,800 датапоинтов) стоило **163.98 кредита ЗА ОДНО чтение** —
столько же (тир ×3) объясняет три отдельных факта чтения этого же
запроса в разных прогонах Sprint 1. Тиры 52.37×3 и 22.38×4 — судя по
всему, чтения `04_sniper_insider_exclusions` и `05_final_cohort_pool`
соответственно. Суммарно ~740 кредитов только на чтениях + три
исполнения полномесячного 02 (~102 каждое, включая один зафиксированный
в разделе 1 как "потерянный на таймауте поллинга") — **разрыв ~1176
кредитов объяснён.**

Наш гард (ревизия 1) стоял только на `execute()` — это была вторая
дыра. Каждый вызов `get_results_df()` в проекте до сих пор шёл в обход
любой проверки.

### Изменения

1. **Гард распространён на чтения.** `analysis/credit_guard.py`:
   `check_before_read(name, row_count, column_count)` — оценка по
   `estimate_read_credits()`, калиброванной на подтверждённом
   пользователем факте (163.98 / 6,050,800 датапоинтов, ×1.5 запаса) —
   та же персистентная проверка против лимита 150, с записью в
   `credits_spent.json` после операции (`record_read`). Вызывается из
   `DuneClient.get_results_df()` — то есть перед КАЖДЫМ реальным
   скачиванием результата в проекте, не только из специально
   помеченных мест.

2. **Принцип «сырые данные не покидают Dune».** `get_results_df()`
   теперь требует от вызывающей стороны заранее объявить
   `expected_max_rows`/`expected_columns` (дефолт 20k строк — выше
   этого явный сигнал "это построчная выгрузка, а не сводка", с
   предупреждением в логе, если факт превысил объявленное). Гейт 1
   (снайперы, обе версии окна), гейт 2, капы копируемости и отбор
   когорт теперь считаются ОДНИМ SQL-запросом на стороне Dune
   (`sql/03b_cohort_selection.sql`) — наружу через API едут только
   строки кошельков, попавших хоть в одну из 8 групп (когорта А/Б × 4
   комбинации), не полный гейтованный пул. Сводка по капам
   (`sql/03c_cap_summary.sql`, 4 строки) и гистограмма снайперов
   (`sql/03d_sniper_histogram.sql`, ≤4 строки) — тоже агрегаты на
   стороне Dune, не построчные выгрузки.

3. **План исполнения без пересчёта 02.** Pre-flight-проверка
   (`DuneClient.create_query(..., require_cached=True)`) подтверждает,
   что query_id'ы 02/01/03 уже в `query_id_map.json` (материализованы
   в Sprint 1, кэш actions/cache того же дня) — если нет, жёсткий отказ
   ДО единого платного вызова, а не тихий пересчёт 02 (~103-125
   кредитов). 03b/03c/03d ссылаются на эти query_id через `query_<id>`
   без повторного execute. Псевдослучайный контроль в 03b —
   детерминированный `sha256(seed || wallet_address)` вместо
   numpy-seed(42) (не идентично Sprint 1 побитово, но так же
   воспроизводимо).

4. **Пост-хок потолок на 03b.** Реальная стоимость execute() 03b (самый
   тяжёлый шаг — 8 проходов `row_number()` по ~1.2M строк) неизвестна
   заранее (Dune не даёт pre-execution оценку). Если факт > 60 —
   `sprint_1_5.py` немедленно останавливается (03c/03d/06×2 не
   запускаются), пишет частичный отчёт с чёткой пометкой.

## Ревизия 3: 03c стоил 144 кредита вместо 8 (UNION ALL пересчитывал CTE 4 раза)

Первый реальный прогон ревизии 2 (`run_sprint_1_5.yml` run #2) частично
удался: **query_id-восстановление отработало на 0 кредитов** (см. ниже),
pre-flight переиспользовал 02/01/03 без нового execute, **03b_cohort_selection
стоил 22.79 кредита** (дешевле оценки 45 и потолка 60). Но
**03c_cap_summary стоил 144.00 кредита** вместо оценённых 8 --
`sql/03c_cap_summary.sql` был написан как `UNION ALL` четырёх
независимых `SELECT`, каждый из которых заново ссылается на цепочку CTE
(`gated` → `sniper_flags` → `first_swap_per_wallet_pool` → полное
сканирование `query_02_swaps_raw_july`, миллионы строк). Судя по всему,
движок Dune/Trino не делит вычисление общих CTE между ветками
`UNION ALL`, а пересчитывает всю цепочку в каждой ветке -- 4 полных
пересканирования вместо одного. Итог прогона: 167.05 потрачено из 150
лимита, гард корректно остановил всё ПЕРЕД 03d (не дал уйти в больший
минус), но результата (вердикта) не было.

### Проблема с признанным query_id-восстановлением (для полноты)

Тот же прогон вскрыл ещё один (уже решённый, 0 кредитов) баг: pre-flight
`require_cached=True` упал на run #1 ("Cache not found for input keys:
dune-cache-\*") -- run #13 (единственный успешный прогон Sprint 1,
источник execution_id для 03/04@5мин) выполнился ДО того, как в
`run_pipeline.yml` появился шаг `actions/cache`, поэтому его
`query_ids.json` умер вместе с контейнером. Решение:
`analysis/recover_query_ids.py` -- `GET /execution/{id}/status`
(бесплатно) даёт `query_id` по известному `execution_id`, `GET
/query/{id}` (тоже бесплатно, метаданные) даёт `query_sql` текст, из
которого регуляркой достаются `query_<id>` ссылки на 01/02, внедрённые
туда при создании 04. Записано в **постоянный, закоммиченный**
`data/query_ids_recovered.json` (не `analysis/output/cache/*.json`,
который в `.gitignore`) -- переживёт что угодно теперь.

### Исправления ревизии 3

1. **`sql/03c_cap_summary.sql` переписан в один проход.** Вместо
   `UNION ALL` четырёх `SELECT` -- один `SELECT` с `count(*) filter
   (...)`/`sum(...) filter (...)` по всем 4 комбинациям как отдельные
   колонки ОДНОЙ строки. `gated` вычисляется ровно один раз.
2. **Санитарная проверка ДО любого execute, независимо от остатка
   лимита** (`credit_guard.check_sql_sanity`, вызывается из
   `DuneClient.execute()`): если оценка > 40 кредитов ИЛИ SQL содержит
   `UNION ALL` вместе со ссылкой на сырой источник
   (`query_02_swaps_raw_july`/`dex.trades`) -- жёсткий стоп с докладом
   ДО оплаты. Оценка печатается в лог всегда, для каждого execute.
3. **Пост-хок "факт > вдвое оценки"** (`credit_guard.check_overrun_after_execute`),
   для ЛЮБОГО шага, не только 03b -- останавливает дальнейшие шаги
   немедленно, не дожидаясь исчерпания лимита.
4. **Лимит Sprint 1.5 поднят с 150 до 210** (`data/credits_spent.json`,
   `sprint15.budget_remaining_at_init`) -- покрывает факт 167.05 +
   смету на дозавершение (~25-35) + минимальный резерв. Внешняя граница
   цикла (2450) не менялась.

Обновлённые оценки (все ≤ 40, иначе санитарная проверка не пропустит):
03b=30 (факт 22.79), 03c=30 (переписан, ожидание сопоставимо с 03b),
03d=10, 06×2=8 каждый.

### 1. Аудит на утечку (scheduled-обновления)

`analysis/audit_dune_account.py` (0 кредитов, только `GET /query/{id}`
метаданные + defensive-пробы account/usage эндпоинтов) прогнан на

запросов (список -- в логе run #17), либо на биллинг-дашборде найти

## Ревизия 7 (2026-09-01, владелец, закрытие G1): проверка самодостаточности репозитория

Повторная проверка (та же формулировка, что в прошлом задании
владельца) на момент закрытия линии graduation-momentum -- всё сделано
локально, 0 кредитов, по факту в репозитории:

1. **SQL-тексты.** Все запросы собираются из Python-шаблонов
   (`build_*_query` в `g1_pipeline.py`, `g1_v2_recon.py` и т.д.), а не
   хранятся только как ID сохранённых query на Dune -- SQL воспроизводим
   из кода репозитория без обращения к Dune UI/API за текстом.
2. **Кэши.** `data/sprint15_cache/` (5 файлов) и `data/sprintG1_cache/`
   (34 файла) закоммичены в git (`.gitignore` исключает только
   эфемерный `analysis/output/*.csv|json`, не `data/`) -- полный
   доступ к уже оплаченным результатам есть у любого, кто клонирует
   репозиторий, без повторной оплаты.
3. **Зависимость от материализаций.** Прямых `CREATE VIEW` / обращений
   к нестабильным `dune.dataset`-материализациям в коде нет; единственное
   использование слова "materialize" -- маркер-файл
   `{name}.materialized` в `dune_client.run_sql_cached`, который лишь
   отмечает, что запрос был исполнен ради побочного эффекта (создание
   таблицы) без последующего платного чтения результата -- это кэш
   ПОВЕДЕНИЯ пайплайна, а не зависимость от чужой материализации.
4. **query_id_map / переживание потери эфемерного кэша.** `query_id_map`
   (ключ -- sha256 текста SQL, не имя) собирается слиянием эфемерного
   `analysis/output/cache/query_ids.json` (GH Actions cache, может
   протухнуть) и постоянного `data/query_ids_recovered.json`
   (закоммичен, 3 записи). Обычный путь пайплайна (`create_query` без
   `require_cached=True`) при отсутствии id в обеих картах просто
   создаёт новый query на Dune -- бесплатная операция, деградация
   плавная, не отказ. `require_cached=True` используется только в
   разовых recovery-скриптах (`recover_03b_result.py`,
   `recover_g1_v2_*`), где нужен конкретный уже оплаченный execution_id,
   а не любой query с тем же текстом -- там жёсткий стоп при
   несовпадении осознанный, не дефект.
5. **Смена ключа Dune API.** Единая точка входа --
   `config.py: dune_api_key = os.environ.get("DUNE_API_KEY", "")`,
   всё остальное (`dune_client.py`, все скрипты пайплайна) читает через
   `CONFIG`/окружение, ключ нигде не захардкожен. Ротация = смена одной
   переменной (`.env` локально или секрет `DUNE_API_KEY` в GitHub
   Actions) -- перезапуск кода не требуется.

Итог: репозиторий самодостаточен -- воспроизведение уже оплаченных
результатов (кэш) и де-новых запусков (SQL-шаблоны + один env-ключ) не
требует ничего, что живёт только вне git.
