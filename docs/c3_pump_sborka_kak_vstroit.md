## 2. Почему раскладку больше нельзя «переносить из сделки источника»

`c2_swap_build.py` работает так: берёт счета источника и подставляет наши
**по номеру места** (`user: [13]`, `user_ata: [(14,1,3),(15,2,4)]`,
`assoc_uva: (21,2,4)`). Это и есть причина отказа: у новой разновидности
другое число счетов и другие места, а гейт `n_accounts: 27` такую сделку
просто не пускает.

Новый сборщик выводит счета **по именам IDL**, а не по номерам. Для
`buy_exact_quote_in_v3` это значит, что **источник не нужен вовсе**: все
17 счетов собираются из шести значений.

```
base_mint, quote_mint, base_token_program, quote_token_program,
user, buyback_fee_recipient
```

Остальные 11 — константы IDL, PDA по семенам IDL и ATA. У каждого счёта в
ответе стоит **провенанс**: `константа IDL` / `выведен PDA по семенам IDL`
/ `выведен ATA` / `передан в контексте`. Дырок без имени не бывает: нет
значения — отказ с именем счёта.

### Что НЕ выводится и обязано прийти снаружи

| счёт | откуда брать | если его нет |
|---|---|---|
| `buyback_fee_recipient` | **из живой сделки** той же разновидности (в IDL его нет ни константой, ни PDA) | отказ по имени счёта — адрес наугад отправит комиссию чужому |
| `bonding_curve.creator` (семя для `creator_vault` у `*_v2`) | из **события сделки** той же транзакции — `creator_iz_sobytija` | отказ по имени; в самом списке счетов транзакции его нет |

Пустая строка здесь — это **отсутствие значения**, а не значение: пока
проверки на пустоту не было, `creator=""` давал пустое семя, PDA
считался **без ошибки**, и комиссия создателя ушла бы на чужой адрес.
Теперь это доказанный красный.

## 3. Диф: что менять в денежном пути

Менять **не** раскладки по номерам, а точку входа. Три врезки.

### 3.1 Кривая `6EF8…`, покупка (п.1)

Врезка идёт **выше** отказа 355 — то есть до того, как
`extract_template` заглянет в `BONDING_DISCS`. Сам отказ остаётся на
месте: он по-прежнему ловит всё, чего нет ни в таблице, ни в IDL.

```python
# analysis/c2_swap_build.py -- в extract_template, ПЕРЕД BONDING_DISCS.get()
import c3_pump_sborka as PS

# Разновидности кривой, которые собираются БЕЗ ИСТОЧНИКА -- по именам IDL.
# Их 17 счетов выводятся из шести значений, и перенос мест источника здесь
# не нужен вовсе (ровно он и упирался в гейт n_accounts: 27).
СБОРКА_ПО_IDL_КРИВАЯ = ("buy_v3", "buy_exact_quote_in_v3")

# tpl["ix"] у кривой -- это ГОЛЫЙ ДИСКРИМИНАТОР hex-строкой
# (c2_swap_build.py:352), а не имя: у других программ там имя.
вар = PS.variant_po_disku("pump", bytes.fromhex(tpl["ix"]))
if tpl["program"] == BONDING and вар in СБОРКА_ПО_IDL_КРИВАЯ:
    собрано = PS.pokupka_krivoj_v3(
        base_mint=минт,
        user=user,
        buyback_fee_recipient=получатель_buyback,   # ТОЛЬКО из живой сделки
        spendable_quote_in=amount_in,
        min_tokens_out=min_out,
        base_token_program=программа_токена_минта,  # у пампового минта бывает Token-2022
    )
    ix = Instruction(
        Pubkey.from_string(собрано["programma"]),
        bytes.fromhex(собрано["data_hex"]),
        [AccountMeta(Pubkey.from_string(а["pubkey"]),
                     is_signer=а["isSigner"], is_writable=а["isWritable"])
         for а in собрано["accounts"]],
    )
```

`buy_v3` отличается от `buy_exact_quote_in_v3` только аргументами —
раскладка та же; собирается тем же `PS.sobrat("pump", "buy_v3", …)`.

### 3.4 Покупка в свежий пул по переезду (п.3)

```python
собрано = PS.pokupka_v_svezhij_pul(tx_переезда, nash_koshelek=кошелёк,
                                   buyback_fee_recipient=получатель_buyback,
```

Все счета берутся **из транзакции переезда**, источник не нужен. Два

имени; переезд есть, а `create_pool` в **той же** транзакции нет —
покупать не во что, тоже отказ.

**Честно и числом: образцов переезда в репозитории НОЛЬ.** Путь п.3
собран по IDL и проверен доказанными красными, но ни на одной живой
транзакции переезда не сверен. Снять образец — одной командой:

```
BLOOM_TREKKER_RPC=... python3 -c 'import sys; sys.path.insert(0,"analysis");
import c3_pump_sborka as P; print(P.zagruzit_idl()["pump"]["ix"]["migrate_v2"]["disc"].hex())'
```

дальше искать этот дискриминатор в подписях программы `6EF8…` и положить
2–3 транзакции в `data/` — после этого сверка п.3 станет такой же
измеренной, как остальное.

### Три красных — три причины, и все три названы

Все три упали одинаково, и программа сказала это сама:

```
Program log: Instruction: BuyExactQuoteInV3
Program log: AnchorError caused by account: associated_base_bonding_curve.
  Error Code: AccountNotInitialized. Error Number: 3012.
```

**Причина первая — программа токена базового минта.**
`associated_base_bonding_curve` — ATA счёта кривой, и программа токена входит в
его семена **третьим семенем**. У `pokupka_krivoj_v3` стояло **умолчание
классического Token**, а у пампового минта токен — **Token-2022**. Умолчание
давало чужой адрес, сборка проходила **без ошибки**, и отказ приходил уже с
цепи.

Измерено тремя независимыми способами, а не припомнено:

| замер | что показал |
|---|---|
| 11 живых инструкций кривой в репозитории (6 `buy_exact_quote_in_v2`, 5 `sell_v2`) | `base_token_program` = `TokenzQdB…` у **всех 11**, классический Token не встретился ни разу |
| 24 настоящих переезда `migrate_v2` (`data/pereezdy_po_cepi.json`) | место 19 `base_token_program` = `TokenzQdB…` во **всех 24** |
| сам прогон | `AnchorError 3012` ровно на том счёте, который считается через эту программу |

**Причина вторая — её нашёл Code-1, и это была оснастка, не сборка.** После
первой правки 3012 переехал на `associated_base_user`: наша покупка в бою уходит
**не одной инструкцией** — `c2_swap_build.py:803` всегда ставит перед свопом
`ata_idempotent` на базовый минт, а симуляция посылала одну. На кошельке,
который этого минта никогда не держал, программа честно отвечала «счёт не
инициализирован». Теперь симуляция посылает **то, что мы и отправляем**: две
инструкции.

**Причина третья — тоже его, и она про цепь, а не про нас.** После второй
правки оба близнеца стали получать `AccountNotFound` **на уровне транзакции**:
программа не запускалась вовсе, а раскладка сходилась **без единого
расхождения**. Чужой близнец собран из счетов **самой** транзакции — если и он
не доходит до программы, значит этих счетов на цепи больше нет: кривая закрыта,
счета закрыты, рента возвращена. Образец говорит только о том, что цепь ушла
вперёд. Правило на это **узкое**: нужны оба исхода «до программы», **одно и то
же** имя ошибки и **ни одного** расхождения в раскладке; любая асимметрия —
красный, потому что «наш не дошёл, а чужой дошёл» — это наша ошибка.

Итог после всех трёх правок: **65 из 65, ноль красных**, минты отказа 08.10
зелёные.

### Правка — его, и у меня теперь ровно она

Умолчания у `base_token_program` больше нет **ни в одной** из трёх обёрток
(`pokupka_krivoj_v3`, `prodazha_krivoj_v3`, `prodazha_krivoj_v2`). Я взял
**форму Code-1**, а не свою: она строже — `_проверить_программу_токена` не
только требует значение, но и **проверяет**, что это одна из двух программ
токена, а `programma_tokena_minta` берёт её из сигнала детектора или с цепи
(владелец счёта минта). Своё я добавил рядом третьим источником:
`programma_tokena_iz_tranzakcii(tx, mint)` — когда транзакция уже на руках,
сети не нужно вовсе.

`quote_token_program` остаётся классическим: котировка у нас WSOL. **Но на цепи
это не всегда так** — из 24 переездов у **трёх** котировка не WSOL
(`SPCXxcqXj6e5…`, `XsCPL9dNWBMv…`, `XsDoVfqeBukx…`) и программа котировки
Token-2022. Для нашей полосы умолчание законно, при покупке в свежий пул
котировку надо брать **из транзакции переезда** — так `pokupka_v_svezhij_pul` и
делает.

**Важно про ветки.** Прогон больше **не выкачивает** сборщик и оснастку из
`claude/stroiteli` — иначе вернулось бы молчаливое умолчание. Работают **копии
Code-1**. Поэтому я свёл свои файлы **на его**: взял его версию целиком и
положил сверху только то, чего у него нет (§7). Диф для него — ровно эти
добавления.

### Почему у Pump AMM было ноль образцов — это была оснастка, не цепь

Предел чтений стоял **общий**, и внешний цикл шёл сначала по кривой. Кривая
съела все 900 чтений, и до `pAMMBay…` чтение **не дошло ни разу**: счётчик
упирался в предел до второй программы, и первая же её подпись ломала цикл. В
отчёте это выглядело как «на цепи их нет».

Теперь у **каждой программы своя доля** предела, и доля считается от остатка на
число ещё не обслуженных программ — значит недобравшая получает и остаток чужой
доли. Проверка на поддельном узле: при пределе 100 кривая читает 50, `pAMMBay…`
читает 50; доля и прочитанное стоят в отчёте **по каждой программе**.

### Одна раскладка из 20 у `sell_v2` — чужой выбор счёта, не наша арифметика

На подписи `3oy7t1iEGw8tgQnZCaVN…` наш `associated_base_user` разошёлся с
цепью. Это **не** Token-2022: оба ATA считаются через **одну и ту же**
`base_token_program`, и второй сошёлся — значит программа токена верна, а
источник держит токен **не на каноническом ATA**. Code-1 завёл на это **узкое**
правило: образец «не сравним», только если расхождение ровно одно, ровно в
пользовательском счёте токена и код ровно 3012; любое другое расхождение
остаётся **красным**, чтобы щели для настоящей ошибки раскладки не было.

### Имя ошибки теперь берётся из логов цепи

До этой правки в отчёт уходило «код 3012 в таблице ошибок не описан», и причину
трёх красных приходилось искать глазами. Anchor пишет в логи ровно то, чего нет
в таблице IDL — имя ошибки и **имя счёта**, — и теперь разбор читает их оттуда.
Логов нет — код остаётся **числом**: имени я ему не выдумываю.

Заодно видно, **чья** ошибка. Те 20 близнецов `buy_exact_quote_in_v3`, что
«прошли», оба падали с `Custom 1` — а это не ошибка pump (её коды начинаются с
6000), это программа токена, которую pump позвала: средств на чужом кошельке уже
нет. Наши счета программа к тому моменту **приняла**. Теперь такой исход так и
называется, а не числится «раскладка отвергнута».

### Как судит симуляция — близнецами

На каждый образец строятся **две** инструкции и прогоняются через узел
одинаково (один и тот же плательщик — чужой, `sigVerify=false`,
`replaceRecentBlockhash=true`, флаги signer/writable из IDL у обеих):

* **чужой оригинал** — счета и байты ровно те, что стоят в транзакции;
* **наша копия** — собрана сборщиком из минимальных входов.

Исход совпал — наша сборка неотличима от настоящей, это «прошло».
Разошёлся — красный, и в отчёте стоят **оба** исхода. Так уехавшие
резервы не могут выдать нашу ошибку за чужую.

Исход классифицируется **по имени ошибки из таблицы того же IDL** (109
ошибок у кривой, 88 у AMM), а не по виду:

| исход | что значит |
|---|---|
| `ПРОШЛО` | узел принял инструкцию |
| `ЭКОНОМИКА/СОСТОЯНИЕ` | программа **разобрала** счета и аргументы и отказала на числах (`TooMuchSolRequired`, `ExceededSlippage`, `BondingCurveComplete`…) — раскладка принята |
| `РАСКЛАДКА ОТВЕРГНУТА` | всё остальное, включая рамочные коды Anchor 2000–5999, которых в таблице IDL нет. Имени такому коду я **не выдумываю** — в отчёт уходит число |
| `ДО ПРОГРАММЫ` | `AccountNotFound`, `InsufficientFundsForRent`… — программа не запускалась, и прошедшим это **не считается** |

Один код — разные программы, разный смысл: `Custom 6004` у кривой это
`MintDoesNotMatchBondingCurve` (раскладка, красный), у AMM —
`ExceededSlippage` (экономика). На это есть отдельная проверка.

## 5. Что запустить — одной строкой

Ключей здесь нет, подписей нет, `sendTransaction` в файле нет ни одного.

окружения, в argv параметра для него нет вовсе.


Живой прогон на торговом хосте:

```
BLOOM_TREKKER_RPC=<узел> python3 deploy/checks/pump_sborka_simulyaciya.py --live
```

С публичным узлом (без ключа) он упрётся в предел запросов — тогда

прогон всегда, живой — только по слову `live=yes`. Денежные задачи едут
тем же набором файлов, что и до этого: груз симуляции добавляется
**только** для неё.

### Чего ждать от прогона

* **сетевых вызовов**: подписи (до 6 страниц) + до `--predel-tx` чтений
  транзакций + по 2 симуляции на образец + по 1 на минт отказа. При
  полном наборе — 363 симуляции;
* **выход 0** — все девять вариантов набрали 20 образцов и все близнецы

* **выход 1 с `why_not`** — либо недобор образцов (с числом, по каждому

* **`propushcheno`** — образцы, собранные прежней раскладкой: причина и

## 6. Что я проверить не мог — списком, без «примерно»

1. **Симуляцию узлом.** Цепь с этой машины закрыта (`connect_rejected`,
   HTTP 000). Вся оснастка п.4 написана и проверена на поддельном узле
   настоящими транзакциями; настоящие ответы цепи даст только прогон §5.
2. **Образцы семи вариантов из девяти.** В репозитории их ноль — ни одной
   живой `*_v3` у кривой, ни одной 17-счётной `*_v2` у AMM.
3. **Переезд.** Образцов `migrate`/`migrate_v2` ноль; путь п.3 собран по
   IDL и закрыт доказанными красными, но на живой транзакции не сверен.
4. **Образцы, собранные ПРЕЖНЕЙ раскладкой.** Это не хвост и не наша
   ошибка: у двух живых `pump.buy_exact_quote_in_v2` данные занимают **24
   байта**, тогда как нынешний IDL требует **25** — байта `partial_fill` в
   них нет вовсе, сделки старше закреплённого IDL. Наша кодировка по
   нынешнему IDL **обязана** от них отличаться, поэтому близнецов на них
   не строим: ни красным (чужая старая сделка — не дефект сборщика), ни
   молча (это соврало бы о числе образцов). Такие уходят в отчёт
   **причиной и числом** (`propushcheno`), и в цель 20 не засчитываются —
   значит 20 сравнимых набираются по-настоящему. Измерено: таких в
   репозитории ровно **2**, и на это есть проверка.

## 7. IDL отстаёт от развёрнутой программы — перепись раскладок (п.3)

Это подтвердилось числами, и перепись теперь считается **кодом**, а не глазами:
`pump_sborka_simulyaciya.py --perepis` (без сети, по образцам репозитория) и
автоматически внутри `--live` (по тому, что прочитано с цепи).

По каждой торговой разновидности перепись ставит рядом **число счетов и длину
данных с цепи** против чисел IDL и выносит приговор: `po_idl`, `hvost_cepi`
(счетов больше, лишние в конце), `dlina_dannyh_ne_ta`, `rashoditsja_po_oboim`,
`raznocenie` (на цепи живут сразу несколько длин), `obrazcov_net`.

### Что показали живые образцы репозитория

| вариант | IDL сч/байт | образцов | с цепи (сч/байт × сколько) | приговор |
|---|---|---|---|---|
| `pump.sell_v2` | 26/24 | 5 | 26/24 ×5 | **по IDL** |
| `pump.buy_exact_quote_in_v2` | 27/25 | 6 | 27/25 ×4, 27/24 ×2 | **разноцение** |
| `pump.sell` | 14/24 | 2 | 16/24 ×2 | **хвост 2** |
| `pump_amm.sell` | 21/24 | 3 | 24/24 ×3 | **хвост 3** |
| `pump.buy` | 16/26 | 7 | 18/24 ×7 | расходится по обоим |
| `pump.buy_exact_sol_in` | 16/26 | 3 | 18/24 ×3 | расходится по обоим |
| `pump_amm.buy` | 23/25 | 11 | 26/24 ×11 | расходится по обоим |
| `pump_amm.buy_exact_quote_in` | 23/25 | 28 | 26/24 ×25, 25/24, 25/25, 26/25 | **разноцение** |

И то же по прогону на цепи: `pump.buy_v3` — **2 образца с длиной не по IDL и ни
одного по IDL**; `pump.buy_exact_quote_in_v2` — 11 по IDL, **55 с другой длиной**
и 11 с более старой раскладкой; `pump.buy_v2` — 3 по IDL, **17 с другой длиной**.

### Раскладка по цепи, а не по IDL — и префикс при этом цел

Главное, что надо было установить: лишние счета стоят **в конце**, а не
вставлены в середину. Если бы вставлялись — наш кошелёк уехал бы на чужое место.
Это **измерено**, а не предположено:

| замер | выведено | сошлось адрес в адрес |
|---|---|---|
| живые образцы репозитория (все разновидности, с хвостами) | 383 | **383** |
| 24 настоящих переезда `migrate_v2` (места 0..26) | 456 | **456** |

Первая строка — **проверка в самопроверке сборщика**, а не разовый замер: она
пересчитывается на каждом прогоне и краснеет, если хоть один счёт уедет.

Поэтому «счетов больше IDL» = **хвост**, а «счетов или байт меньше» = раскладка
**старше** нашего IDL, где имена мест уже не те. Два случая не склеиваются.

### `migrate_v2`: 29 на цепи против 27 в IDL — оба лишних ВЫВОДЯТСЯ

| место | что это | сошлось |
|---|---|---|
| 27 | `boost_vault_authority` = `PDA(["boost_vault", pool])` под `pAMMBay…` | **24 из 24** |
| 28 | `ATA(место 27, quote_token_program, quote_mint)` | **24 из 24** |

Имя `boost_vault_authority` и семя `boost_vault` взяты **из того же
закреплённого IDL** (`pump_amm`, инструкции `boost_buy_and_burn` и `init_boost`)
— ни одного имени наугад. Функция `hvost_pereezda(pool, quote_mint,
quote_token_program)` выводит их обоих, так что полная 29-счётная раскладка
переезда собирается без неизвестных.

### Побочно, но важно для врезки: котировка не всегда WSOL

Из 24 переездов **21** с `quote_mint = WSOL` и SPL Token, а **3** — с другим
минтом котировки (`SPCXxcqXj6e5…`, `XsCPL9dNWBMv…`, `XsDoVfqeBukx…`) и
**Token-2022** в `quote_token_program`. Для нашей полосы умолчание
`quote_mint = WSOL` законно (мы входим за SOL), но на цепи такие пулы есть, и
при покупке в свежий пул по переезду котировку надо брать **из транзакции
переезда**, а не из умолчания. Это уже так и сделано в `pokupka_v_svezhij_pul`.

### Поля, которых нет в транзакции

Смещения полей в телах счетов теперь считаются **по раскладке IDL**, а не
вбиваются руками (`smeshchenije_polja`). Проверка самой проверки: смещение
`creator` в событии сделки, сверенное ранее на 23 живых инструкциях (169 + 8
байт дискриминатора), **воспроизводится раскладкой IDL ровно в 177** — два
независимых пути дали одно число.

За полем переменной длины смещение **не определено**, и это отказ по имени поля,
а не чтение наугад (доказанный красный: `TradeEvent.quote_mint` стоит за
`ix_name string`).

`Pool.coin_creator` (смещение 211) — семя `coin_creator_vault_authority` и
`coin_creator_vault_ata` у Pump AMM. **В транзакции его нет**, и обхода, как у
кривой (создатель в событии сделки), тоже нет: без чтения счёта пула ни один
образец **старых** `pump_amm.buy / sell / buy_exact_quote_in` собрать нельзя —
на 42 живых инструкциях AMM сборка падала ровно этими двумя именами. **Наших
девяти это не касается:** у 17-счётных `buy_v2 / buy_exact_quote_in_v2 /
sell_v2` счетов создателя нет вовсе (проверено по IDL), им нужны только
переданные значения плюс четыре выводимых.

### Что это значит для врезки

1. Для **наших** разновидностей IDL сошёлся с цепью: `buy_exact_quote_in_v3` и
   `sell_v3` — 20 из 20 адрес в адрес и байт в байт; `sell_v2` — 20 из 20
   (одна раскладка разошлась из-за неканонического счёта источника, не из-за
   IDL). По ним врезка идёт как написана в §3.
2. Для `buy_exact_quote_in_v2` и `buy_v2` на цепи живут **несколько длин
   данных**. Отправлять надо ту, которую программа принимает **сейчас**, и
   узнать её может только прогон: перепись теперь печатает все встреченные
   длины с их числами.
3. Гейты по числу счетов (`n_accounts`, `min_accounts`) менять **не надо** —
   у наших девяти числа совпали с IDL. Хвост встречается только у **старых**
   имён (`buy`, `sell`, `buy_exact_sol_in`, `pump_amm.buy/sell/
   buy_exact_quote_in`), которыми мы не торгуем.
4. `migrate_v2` собирать **по 29 счетам**, не по 27 — оба лишних выводятся
   `hvost_pereezda`.
