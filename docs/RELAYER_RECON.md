# Across relayer — наблюдение без капитала (задача A, владелец, 2026-09-02)

Владелец: «Релеер Across — прогон в режиме наблюдения, без капитала».
5 пунктов: (1) слушать депозиты на маршрутах Robinhood Chain 24ч, ничего не
отправлять; (2) по каждому депозиту — маршрут/размер/спред/эксклюзивность/
кто и за сколько заполнил/на каком чейне взято возмещение; (3) агрегаты
(объём USDC↔USDG по дням, распределение спреда p10/p50/p90, медианное
время до филла, доля эксклюзивных, концентрация топ-3, сколько бы
«выиграли мы» при инвентаре $1k/$5k/$20k); (4) время fill→repayment,
доступность выбора чейна репеймента; (5) `docs/RELAYER_RECON.md` + сводка
в чат. **Ни одной транзакции, 0 капитала — соблюдено на всех стадиях.**

## Статус: разведка выполнена, полный 24ч-наблюдатель — следующий шаг

## 2. Разведка (полная история + сэмпл 500k блоков) — ключевой факт

Первый реальный прогон (`analysis/relayer_recon.py`, публичный RPC без
ключа, ~58 минут) дал результат, который меняет всю картину задачи:

**`EnabledDepositRoute` — 0 событий за ВСЮ историю чейна** (блоки
156309..52 647 755, полное покрытие, 2625 вызовов `eth_getLogs` с
`chunk_size=20000` — не срез, не сэмпл). Это означает: **администратор
SpokePool ни разу явно не включал ни один маршрут депозита через этот
механизм** — либо (а) маршруты в этом форке включены иначе (не через
`setEnableRoute`/`EnabledDepositRoute`, а через какой-то другой
механизм/дефолт), либо (б) исходящих депозитов (Robinhood Chain →
другой чейн) в штатном режиме вообще не бывает и вся активность —
только входящая (депозит на другом чейне, филл здесь).

При этом сэмпл последних 500k блоков (`FundsDeposited`/`FilledRelay`,
address-scoped на сам SpokePool) **содержит реальные логи** с этими
топиками — то есть контракт живой и что-то через него проходит, вопреки
нулю `EnabledDepositRoute`. Расшифровка одного из найденных
`FundsDeposited`-логов **упала** (`eth_abi.exceptions.NonEmptyPaddingBytes`)
— схема данных не легла ровно на дословную ABI из
`V3SpokePoolInterface.sol`, взятую как рабочая гипотеза. **Не
досочиняем расшифровку** — сырой лог (`sample_deposit_decode_errors` в
`data/p3_guard_cache/relayer_recon_result.json`) сохраняется для разбора
байт напрямую, скрипт исправлен (`try/except` на каждый лог + resume,
коммит `79e36dd`) и перезапущен 02.09.2026 — результат появится здесь
при следующем обновлении.

## 3. Что это значит для пунктов 1–4 задания (честно, до полного результата)

- **П.1 (24ч-наблюдатель):** имеет смысл строить ТОЛЬКО после того, как
  подтвердится (а) реальная ли активность вообще есть на достаточном
  для суточной статистики уровне (сэмпл 500k блоков — это единственный
  ориентир пока), и (б) исправлен декодер, иначе наблюдатель будет либо
  падать на каждом непонятном логе, либо (хуже) молча пропускать данные.
- **П.2/3 (спред/эксклюзивность/агрегаты/концентрация):** не считаются
  на выдуманных числах — ждут исправленного прогона.
- **П.4 (repayment chain, fill→repayment turnaround):** `FilledRelay`
  содержит `repaymentChainId` НАПРЯМУЮ в самом событии (не нужен второй
  RPC-запрос) — это уже подтверждено по схеме контракта (`across_common.py`,
  дословный докстринг с указанием источника). Реальные ЗНАЧЕНИЯ
  `repaymentChainId`, увиденные в сэмпле, — тоже ждут исправленного
  прогона (декодер `FilledRelay` тоже был обёрнут в `try/except`
  защитно, хотя крашился именно декодер депозитов, не филлов).
- **Контрагент-чейн:** какой конкретно chainId выступает партнёром
  Robinhood Chain на маршруте USDC↔USDG (нужно для полной
  двусторонней картины, см. честную оговорку в `across_common.py`)
  — тоже не определён пока сэмпл не декодирован до конца.

## 4. Методологическая оговорка (зафиксирована ДО прогона, не задним числом)

С ОДНОГО SpokePool (только Robinhood Chain) видна ПОЛНАЯ картина только
для одного направления каждого маршрута: `FilledRelay` (филл, здесь)
содержит ВСЕ параметры исходного депозита, сделанного на чужом чейне —
то есть входящее направление видно полностью с одного узла. Исходящее
направление (депозит сделан здесь, филл — на чужом чейне) видно только
наполовину (маршрут/размер/эксклюзивность из `FundsDeposited`, но НЕ
кто/когда заполнил и на каком чейне взял репеймент — это требует RPC
чейна-контрагента). Решение о добавлении RPC контрагента принимается
ПОСЛЕ того, как разведка покажет, какой чейн это на практике, не
заранее.
