## п.2 Дыра в `run_vps_pravka_grupp_nl.yml` — закрыта

Дыра оказалась **шире**, чем названо. Кроме трёх значений в одинарных кавычках на удалённой стороне
(`--znachenie '$ZNACHENIE' --politika '$POLITIKA' --pometka '$POMETKA'`) строка `ARGS` собиралась из
**шести** входов вообще без кавычек. Пробел в любом из шести или апостроф в любом из трёх — и это
уже чужая команда от root на **торговом** хосте. Пометка по смыслу поля свободный текст, то есть
апостроф там был вопросом времени.

Чем закрыто: правка собирается **планом** — тем же файлом, которым прогон уже умеет применять
список правок, — и уезжает по stdin. В команде root остались только неизменяемые литералы
(`--file`, `--plan`, при показе `--pokazat`). Новой ветки в модуле не завелось: одиночная правка и
план сходятся в один и тот же список операций (`deploy/checks/pravka_grupp.py:415-425`). План
собирает python **из окружения** (`deploy/checks/pravka_grupp_plan_iz_okruzhenija.py`, самопроверка
11/11, среди проверок проход апострофа и точки с запятой как данных): `os.environ` не разбирается
как код ни при каком значении.

**Проверено подменным ssh на враждебном значении.** При `pometka = "a'; rm -rf / ; echo '"` в
команде root ноль вхождений `ADRES1`, `cand2`, `rm -rf`, `echo '`. Заодно ушёл скрытый дефект: в
прежней ветке `set -e` стоял до `rc=$?`, поэтому при отказе не выполнялись ни уборка временных
файлов на хосте, ни `exit $rc`.

Попутно: я сперва написал сборщик плана heredoc'ом, решил, что он не работает из-за отступа тела, и
**проверил — работает**. YAML снимает общий отступ блочного скаляра, и бегунок получает тело и
терминатор в нулевой колонке; мой первый тест был построен неверно. Ложное утверждение из файлов
убрал, бессмысленное правило в линтер не завёл.

## п.3 Часы на lab-miami — **НЕ ПОСТАВЛЕНЫ. Упираюсь в допуск.**

Установщик работает до конца: доказательство «это лаборатория, а не торговый хост» проходит, скрипт
часов разбирается, имена ветки сторожатся от лишних знаков, токен уехал бы по stdin в файл 0600 root
и нигде не печатается. Прогон останавливается на одном: **секрета `LAB_DISPATCH_TOKEN` заданию не
видно.**

Четыре прогона (37198875680, 37198994037, 37200179744, 37200574243) говорят одно и то же:

```
  LAB_DISPATCH_TOKEN net
  LAB_DISPATCH net

  DISPATCH_TOKEN net
  GH_DISPATCH_TOKEN net
  vars.LAB_DISPATCH_TOKEN net

```

То есть широкий `GH_RUNNER_PAT` заданию виден, а под именем `LAB_DISPATCH_TOKEN` не доходит ничего.
Прочитать список секретов мне нельзя: прокси отвечает 403 и на `actions/secrets`, и на
`environments`.

**Одну частую причину я проверил и почти закрыл.** Если секрет заведён как секрет *окружения*, то
`secrets.X` в задании пуст **всегда**, пока у задания нет `environment:`, — и со стороны это
выглядит ровно как «секрета нет». Прогон теперь сам читает список окружений обычным GITHUB_TOKEN:
окружение в репозитории **одно, `github-pages`** (его создаёт сам GitHub под Pages). То есть
положить туда секрет можно было только намеренно.

Остаются три причины, и выбрать между ними может только владелец:
1. **Секрет лежит в другом репозитории.** «Fine-grained, один репозиторий» — это область действия
   *токена*; сам секрет при этом хранится там, где его завели. Если он создан не в
   `Russiansky777/robinhood-chain-alpha`, прогон его не увидит никогда.
2. **Имя отличается** от пяти проверенных.
3. **Это секрет Dependabot**, а не Actions — такие прогонам не видны вовсе.

Путь проверки: Settings → Secrets and variables → **Actions** → вкладка **Secrets** этого
репозитория; имя должно быть ровно `LAB_DISPATCH_TOKEN`, права токена — Actions: Read and write,
больше ничего.

**Широкий `GH_RUNNER_PAT` я подставлять не стал.** Он умеет регистрировать бегунки, то есть кладёт
на лабораторию куда больше прав, чем требует расписание, а владелец сказал «установщик с
LAB_DISPATCH_TOKEN». Для осознанного выбора во входе прогона есть отдельное слово
`razreshit_runner_pat=yes` — скажите, и часы встанут на нём за один прогон.

**Расписания GitHub у трёх прогонов я, как велено, НЕ снимал** и не сниму до зелёных первых
запусков. Таймеры `lab-uchjot-chas`, `lab-zdorovje-chas`, `lab-konveyer-sutki` на лаборатории
`not-found`, то есть учёт, здоровье и конвейер по-прежнему держатся на cron GitHub — с тем самым
пропуском слотов, из-за которого это и переносилось.

Попутная правка, о которой надо сказать прямо: я сперва сделал печать списка имён допусков через
`toJSON(secrets)` (значений не печатал, только ключи). **GitHub поставил такой прогон на одобрение
владельца** — прогон 37200403600 вернулся `action_required` через 2 секунды, ни один шаг не пошёл.
Деплой, пущенный с того же коммита в ту же минуту, прошёл нормально, то есть дело именно в этом
выражении. Одобрения ради справки я просить не стал, путь убрал и мёртвый вспомогательный файл
удалил, чтобы он не выглядел работающим.
