# P5 — хеджированное LP на ETH/USDG (владелец, приоритет №1, 2026-09-03)

Идея: держать концентрированную ликвидность Uniswap v3 в пуле ETH/USDG,
хеджировать дельту позиции коротким ETH-перпом на Lighter, зарабатывать
торговые комиссии без направленного риска по ETH.

**Пул:** `0x52e65B17fB6E5BA00Ed806f37Afcd2DaA50271Ca`, Uniswap v3, комиссия
0.01%. По интерфейсу (владелец, GeckoTerminal): TVL $21.1M, объём 24ч
$823M, APR 106.59%, балансы 4.9k ETH / 9.4M USDG. Проверка арифметикой
владельца: $823M × 0.01% = $82.3k/сутки на $21.1M TVL = 142% годовых до
вычета издержек. **Эти цифры — со слов владельца/интерфейса
GeckoTerminal, ещё НЕ подтверждены напрямую ончейн в этом документе** —
подтверждение (token0/token1/fee/decimals/реальная ликвидность) — первый
шаг ниже, до любых расчётов backtest.

## Kill-порог — ЗАРЕГИСТРИРОВАН ДО РАСЧЁТА (владелец, п.5)

**Если лучший из проверяемых вариантов (сочетание диапазона ±5%/±10%/
±20%/полный × политика ребаланса раз в час/5%-дрейф/10%-дрейф) даёт
< 25% годовых ПОСЛЕ вычета IL, фандинга, спредов ребаланса и газа —
линия P5 закрывается.** Порог зафиксирован здесь, в этом виде, ДО того,
как получен хотя бы один результат backtest — правки задним числом не
вносятся.

## Метод (по пунктам задания)

1. **Бэктест 30 дней, без капитала**, диапазоны ±5%/±10%/±20%/полный,
   условная позиция $10k, почасовая гранулярность:
   - Заработанные комиссии: `earned_fee_h = pool_volume_h × fee_tier ×
     position_liquidity_share_h` (доля позиции от активной ликвидности
     пула **в моменты, когда цена внутри диапазона позиции** — вне
     диапазона позиция не зарабатывает комиссии, только держит
     единственный актив на границе).
   - Дельта позиции — стандартная формула Uniswap v3 для диапазона
     `[Pa, Pb]` и текущей цены `P`: если `P <= Pa` — позиция полностью в
     ETH (дельта = 1); если `P >= Pb` — полностью в USDG (дельта = 0);
     внутри диапазона — дельта плавно меняется по формуле
     `L, sqrtP, sqrtPa, sqrtPb`.
   - IL (impermanent loss) — разница между стоимостью позиции в пуле и
     стоимостью «просто держать» исходные 4.9k ETH/9.4M USDG (в тех же
     пропорциях, что при входе), по формуле v3 (не по формуле v2 —
     диапазон конечный, не [0, ∞)).
   - Стоимость хеджа — фандинг ETH-перпа Lighter (реальный, за 30 дней,
     API) + спред при каждом ребалансе (реальная глубина книги Lighter
     на нужный размер) + газ (реальная цена газа Robinhood Chain на
     момент операции).
2. **3 политики ребаланса** (раз в час / дрейф дельты 5% / дрейф 10%) —
   итог в %/год: `комиссии − IL − фандинг − спреды_ребаланса − газ`.
3. **Время вне диапазона** — доля времени за 30 дней, когда цена ETH/USDG
   была за границами каждого из 4 диапазонов (± от цены входа).
4. **Ёмкость**: (а) как падает доля комиссий позиции при добавлении
   $10k/$50k/$200k к текущему TVL пула (при неизменном объёме — доля
   позиции размывается пропорционально росту TVL, если позиция —
   единственная новая ликвидность в диапазоне); (б) реальная глубина
   ETH-перпа на Lighter — проходит ли шорт нужного размера (эквивалент
   позиции) без сдвига цены на каждом из указанных размеров.
5. **Источники данных (владелец, п.6, НОВОЕ ПРАВИЛО СЕССИИ):** сначала
   GeckoTerminal/DexScreener/DefiLlama/Uniswap subgraph API (бесплатны,
   доступны с GH Actions runner'а) — ончейн-логи Swap ТОЛЬКО как фолбэк,
   если готовых данных там нет. Что из этого реально доступно для
   Robinhood Chain (chain id 4663) и конкретно этого пула — **проверяется
   эмпирически ниже, не предполагается заранее**.

## Дисциплина (владелец)

- Жёсткий лимит **90 минут** на любой прогон — при превышении скрипт
  сам останавливается, сохраняет частичный результат, докладывается,
  не продолжается вслепую.
- Оценка числа вызовов/времени — **до старта** каждого тяжёлого прогона,
  доложена владельцу, без автозапуска.
- Не пушить во время активного run.
- При конфликте за RPC с задачей MM (приоритет №2) — MM уступает.

### 1. Верификация пула — ПОДТВЕРЖДЕНО, это реально ETH/USDG v3, fee 0.01%

Прямое чтение контракта `0x52e65b17fb6e5ba00ed806f37afcd2daa50271ca`:
`token0 = 0x0bd7...ad73` (WETH), `token1 = 0x5fc5...d168` (USDG),
`fee = 100` (в сотых бипа → 100/1e6 = **0.01%**, совпадает с заявленным),
`liquidity_raw = 6819822132423788378` (реальная, ненулевая),
`sqrtPriceX96 = 3875385805687706545413629`, `tick = -198519`.

Пересчёт цены из `sqrtPriceX96` (decimals WETH=18, USDG=6):
`price = (sqrtP/2^96)^2 × 10^12 = $2392.60` за ETH — сходится (расхождение
<0.01%) с (а) живой ценой ETH/USD с CoinGecko в этом же прогоне ($2392.80)
и (б) `priceUsd` из независимого DexScreener-снепшота того же пула
($2392.57). Тройное совпадение из трёх независимых источников —
пул реален, это не подставной/неликвидный адрес.

DexScreener-снепшот этого же пула (см. п.2 ниже) даёт TVL $21 106 795.3
(база WETH 5014.17 / квота USDG 9 110 013) и объём 24ч $828 339 768.62 —
близко к цифрам владельца (4.9k ETH/9.4M USDG, $823M/сутки), различие в
пределах естественного дрейфа между снятием владельца и снятием скрипта.
**Цифры из интерфейса подтверждены независимо, не выдуманы.**

### 2. Внешние API — что реально доступно с раннера (проверено эмпирически)

- **GeckoTerminal** (`/api/v2/networks`): 200 OK, список сетей получен,
  но **Robinhood Chain в списке НЕТ** (проверено по подстроке "robin" —
  ноль совпадений). GeckoTerminal этот пул/сеть не поддерживает →
  недоступен как источник для P5.
- **DexScreener** (`/latest/dex/search?q=<pool>`): 200 OK, пул найден
  (`chainId: "robinhood"`, `dexId: "uniswap"`, `labels: ["v3"]`) — даёт
  **текущий снепшот**: цена, объём по окнам (m5/h1/h6/h24), ликвидность,
  число сделок по окнам. **Исторических почасовых свечей за 30 дней в
  этом эндпоинте нет** — только моментальный срез на момент запроса.
- **DefiLlama** (`/overview/dexs`): 200 OK, **"Robinhood Chain" есть в
  списке из 291 сети** — это протокольный/чейн-левел агрегатор объёма
  DEX, потенциально даёт исторический ряд объёма по дням для всей сети
  (не обязательно только для этого пула) — **детальный эндпоинт (дневной
  ряд, разбивка по пулу/протоколу) ещё НЕ проверен**, это открытый вопрос
  для следующего дешёвого шага, не факт.
- **Uniswap subgraph** (проверка списка chainId→subgraph URL в исходнике
  интерфейса Uniswap на GitHub): 404 — chain id 4663 / "robinhood" в
  этом списке отсутствует → официального subgraph для этой сети нет.

**Вывод: ни один из четырёх источников не даёт готовый почасовой ряд
цена+объём за 30 дней для конкретно этого пула.** DexScreener и
DefiLlama полезны для точечной сверки (сделано, см. п.1), но не
закрывают потребность в исторических данных бэктеста. Ончейн-фолбэк
(п.5 методологии, GeckoTerminal/subgraph → фолбэк) технически обязателен
для этой линии — не в нарушение нового правила, а как раз то исключение,
которое правило прямо предусматривает («ончейн — только для того, чего
там нет»).

### 3. Калибровка ончейн-фолбэка — прогноз стоимости ПРЕВЫШАЕТ 90-минутный лимит

Калибровочное окно 5000 блоков (~513 сек реального времени на сети) дало
**4910 своп-событий** — это **~34 456 свопов/час**, то есть пул торгуется
почти на каждую секунду. Экстраполяция на 30 дней:
- ~24.8 млн свопов за 30 дней (реальное число, не оценка на глаз — прямая
  линейная экстраполяция калибровочной плотности);
- ~15 158 вызовов `eth_getLogs` (при текущем практическом лимите
  логов/ответ на своп-плотность такого уровня);
- **~337 минут** при уже наблюдённой практической скорости ~45
  вызовов/мин — **это ×3.7 больше 90-минутного жёсткого лимита**.

Прямой полный лог-скан всех свопов за 30 дней в рамках одного прогона
**не проходит по бюджету времени как есть** — честно доложено ДО старта,
без автозапуска, по прямому требованию владельца (п.3 дисциплины).

### Что дальше — варианты, нужно решение владельца (НЕ запущено)

1. **Сузить окно бэктеста** (например 7–10 дней вместо 30) — тот же метод,
   пропорционально дешевле (~80–115 мин при текущей плотности — тоже

2. **Разделить на несколько прогонов** по 90 минут (например 4×~7.5 дней
   с сохранением частичного результата и резюме между прогонами, как уже
   делалось для `mm_discover.py`) — покрывает полные 30 дней ценой
   нескольких итераций вместо одной.
3. **Проверить эмпирически (дёшево, 1-2 вызова)**, даёт ли DefiLlama
   детальный дневной ряд объёма для Robinhood Chain / этого DEX —
   если да, объём брать оттуда (реальные данные, не лог-скан), а
   ончейн-сканирование логов сократить только до цены (по одному

   это поддерживает для прошлых блоков — тоже требует 1 проверочного
   вызова, ещё не сделанного) — на порядок дешевле полного скана свопов.
4. Принять как есть текущий инвентарь (проверка пула + внешние API)
   как окончательный охват P5 на этом шаге и явно отложить полный
   30-дневный бэктест.

Рекомендация (не решение, решение за владельцем): начать с варианта 3
(1-2 дешёвых проверочных вызова: DefiLlama детальный объём + архивный
`eth_call`) — если оба сработают, вариант 2 (несколько прогонов по
90 минут) станет заметно дешевле и точнее одновременно.
