# P3 — гард на концентрацию адресов в кросс-версионных (v3↔v4) закрытиях дислокаций

**Зафиксировано ДО просмотра результата, 2026-09-01.** Критерий ниже —
дословно от владельца, зафиксирован до запуска гарда: «Один дешёвый
гард для P3 (тоже без Dune, через RPC/Blockscout, узкий срез ×2.5):
доля кросс-версионных (v3↔v4) закрытий дислокаций топ-5 сток-токенов,
приходящаяся на топ-3 адреса за последние 7 дней. Если > 80% — P3
закрывается окончательно.»

## Статус: код готов, реальный запуск заблокирован на кредах (не на коде)

Код готов и протестирован (синтетические логи, см. `analysis/
p3_dislocation_guard.py` docstring). Реальный запуск — на GH Actions
runner'е (`.github/workflows/run_p3_guard.yml`), НЕ в интерактивной
сессии агента: egress-прокси интерактивной песочницы блокирует ВСЕ
внешние домены кроме `github.com`/`raw.githubusercontent.com`
(проверено эмпирически на `*.alchemy.com`, `robinhoodchain.blockscout.com`,
`rpc.mainnet.chain.robinhood.com` — все `EGRESS_BLOCKED`). Этот же
паттерн уже задокументирован в проекте для Sprint R1 (`analysis/
r1_feed_match.py`, "eth_call через Alchemy RPC ... недоступный из
интерактивной песочницы инструмента").

**Три реальных прогона на GH Actions сделаны 2026-09-01 (не 0, не
теория) — все три уткнулись в отсутствие рабочего RPC-ключа, не в
баг кода.** Подробности и точная причина — секция "Блокер выполнения"
ниже. Результат (число, вердикт >80%) появится здесь и в
`data/p3_guard_cache/p3_guard_result.json` **после того, как владелец
предоставит один из двух ключей** (см. "Что нужно от владельца"). До
тех пор P3 остаётся в статусе **watchlist** (решение владельца от
2026-09-01, зафиксировано в `docs/PROJECT_STATE.md`) по прежним трём
причинам (латентностная гонка, режим-брейк 29.09, бюджет) — гард ещё
не подтвердил и не опроверг окончательное закрытие.

## Источник данных и без-Dune ограничение

Только `eth_getLogs`/`eth_getTransactionByHash` через Alchemy RPC
(`analysis/alchemy_fallback.py`, уже существовавшая заготовка проекта —
при подготовке этого гарда в ней найден и исправлен блокирующий баг:
модуль импортировал `web3.Web3.keccak`, а `web3` не установлен и не
был в `analysis/requirements.txt` — заготовка НИ РАЗУ не запускалась
с момента создания, поэтому баг не проявлялся; заменено на
`Crypto.Hash.keccak` — тот же метод, что уже используют `analysis/
g1_common.py` и `analysis/r1_common.py`, без новой зависимости).

## Методология

### Шаг 0 — discover (узкий срез, 1 день, chain-wide)

Проверяет факт, а не берёт на веру:

1. Эмпирическая оценка блоктайма (2 точечных `eth_getBlockByNumber`,
   не документированные "~100мс" на слово — измеряется).
2. `eth_getLogs` за последний день, БЕЗ фильтра по адресу, по topic0
   `PoolCreated` (Uniswap V3 Factory) и `Initialize` (Uniswap V4
   PoolManager) — узнаёт адрес(а) фабрики/PoolManager'а ПО ФАКТУ логов,
   не по угадыванию. (Кандидат-адрес V3 Factory — детерминированный
   CREATE2-адрес `0x1F98431c8aD98523631AE4a59f267346ea31F984`,
   одинаковый на десятках EVM-чейнов с официальным деплоем Uniswap —
   не подтверждён напрямую документацией для Robinhood Chain, т.к.
   `developers.uniswap.org` и блокскан заблокированы egress-прокси —
   discover проверяет его сам по факту логов, не полагаясь на цитату.)
3. Пересекает найденные пулы/инициализации с 194-токенным реестром
   сток-токенов (`data/sprintR1_cache/r1_rwa_full_universe.csv`, уже
   оплачено и закэшировано Sprint R1 — 0 новых Dune-запросов) — прямо
   отвечает на вопрос "существуют ли ВООБЩЕ v4-пулы сток-токенов",
   до того как гард тратит хоть один запрос на их поиск за 7 дней.
4. Печатает калибровку: `запросы_за_1_день × 7 × 2.5` — проекция
   стоимости (в RPC-запросах, не в кредитах — но та же дисциплина
   "узкий срез × запас", что везде в проекте, см. `docs/PROJECT_STATE.md`,
   правило 4) для стадии `guard` перед тем, как её запускать.

### Шаг 1 — guard (полный прогон, 7 дней)

1. Address-scoped скан `PoolCreated`/`Initialize` с начала чейна
   (01.07.2026) для полной карты пулов сток-токенов (дёшево — оба
   события редки относительно `Swap`).
2. Если пересечение "токены с V3-пулом" ∩ "токены с V4-пулом" пусто —
   **гард завершается с вердиктом N/A** ("явление не существует"), а
   не подставляет 0% в формулу деления на ноль. Это отдельный, более
   сильный вывод, чем ">80%" — если ни один сток-токен не торгуется
   одновременно на v3 и v4, кросс-версионной дислокации по конструкции
   быть не может.
3. Иначе: топ-5 токенов ИЗ ПЕРЕСЕЧЕНИЯ ранжируются по числу свопов
   (v3+v4) за последние 7 дней (не по $-объёму — конвертация в USD
   потребовала бы либо Dune, либо отдельного оракульного джойна, что
   не входит в scope "дешёвого гарда"; явно зафиксировано здесь, а не
   молча).
4. **Операциональное определение "закрытия дислокации"** (решение
   этого гарда, не внешний стандарт): транзакция, чьи логи содержат
   ОБА — `Swap` на v3-пуле токена И `Swap` на v4-poolId того же токена,
   в ОДНОЙ и той же транзакции (совпадение `tx_hash`). Упрощение,
   зафиксированное явно: направления двух ног (знаки `amount0`/`amount1`)
   не проверяются — совпадение `tx_hash` уже достаточно редкое и
   специфичное событие (одновременная активность на обеих версиях в
   одной атомарной транзакции), чтобы служить консервативным прокси
   для "арбитраж, закрывающий ценовой разрыв между пулами", без
   дополнительного декодирования знака.
5. Адрес = `from` транзакции (`eth_getTransactionByHash`, по одному
   вызову на уникальный `tx_hash` — их ожидается немного, это редкое
   событие, не полный объём свопов).
6. Доля топ-3 адресов = (сумма закрытий трёх самых частых `from`) /
   (общее число закрытий), **пул по всем топ-5 токенам вместе** (не
   топ-3 на каждый токен по отдельности) — так читается формулировка
   владельца ("доля... закрытий... топ-5 токенов, приходящаяся на
   топ-3 адреса", единое число, не таблица из пяти чисел).

## Ограничения (зафиксированы до результата)

- Топ-5 по числу свопов, не по $-объёму (см. выше).
- "Закрытие" = совпадение `tx_hash` в v3- и v4-множествах свопов,
  без проверки встречности направления — консервативно занижает
  число ложных срабатываний ценой возможного пропуска дислокаций,
  закрытых НЕ одной атомарной транзакцией (две отдельные транзакции
  в одном/соседних блоках) — такие случаи этот гард не увидит.
- Адрес = `tx.from` (инициатор), не адрес контракта-исполнителя, если
  арбитраж идёт через смарт-контрактного бандлера/агрегатора — в этом
  случае "топ-3 адреса" могут на самом деле быть 1-2 ботами,
  вызывающими транзакции с разных EOA (маскировка концентрации) —
  не проверяется этим гардом, честная оговорка, не скрытая.
- Блоктайм измеряется эмпирически по 2 точкам (latest и
  latest−200000) — усреднённая оценка, не поблочная точность; при
  сильной вариации блоктайма во времени граница "последние 7 дней"
  может съехать на несколько часов.
- Если фабрика/PoolManager подтверждаются discover-стадией на очень
  малом числе логов (узкий 1-дневный срез) — возможен false negative
  (адрес не засветился именно в этот день), стадия `guard` компенсирует
  это повторным address-scoped сканом с начала чейна, но САМ адрес
  берётся из discover — если discover в принципе не нашёл ни одного
  PoolCreated/Initialize за узкий срез (маловероятно на активном
  чейне, но не исключено), `guard` откажется работать без него.

## Блокер выполнения: оба бесплатных RPC-пути требуют ключ, которого нет в этой сессии

Три реальных прогона на GH Actions (не в интерактивной сессии, см. ниже), в порядке:

1. **`ALCHEMY_API_KEY`** ([run #33553407884](https://github.com/Russiansky777/robinhood-chain-alpha/actions/runs/33553407884)) — упал сразу: `ALCHEMY_API_KEY / ALCHEMY_ROBINHOOD_RPC_URL не заданы`. В этом репозитории секрет `ALCHEMY_API_KEY` НЕ настроен в GH Actions (проверено фактом падения, не документацией). Согласуется с тем, что `analysis/r1_feed_match.py` (тот же Alchemy-путь, Sprint R1) ни разу не оставил закэшированного результата в `data/sprintR1_cache/` — Sprint R1 в итоге пошёл через `feed_match_dune` (декодированные call-traces на Dune), а не через прямой RPC.
2. **Публичный Blockscout eth-rpc без ключа** ([run #33553766600](https://github.com/Russiansky777/robinhood-chain-alpha/actions/runs/33553766600)) — `POST https://robinhoodchain.blockscout.com/api/eth-rpc` вернул `403 Forbidden`. Стандартная документация Blockscout (`docs.blockscout.com/devs/apis/rpc/eth-rpc`) говорит «API key не обязателен, но повышает RPS» — это верно для большинства чейнов на Blockscout, но не для этого.
3. **То же самое + `User-Agent`** ([run #33553900159](https://github.com/Russiansky777/robinhood-chain-alpha/actions/runs/33553900159)) — тот же `403`, заголовок не помог (значит это не UA-фильтр WAF).

**Причина найдена** (официальная документация Robinhood Chain в репозитории `blockscout/docs`, файл `robinhood-api.mdx`, получено WebFetch дословно): Robinhood Chain на Blockscout обслуживается через отдельный **«PRO API» гейтвей** (`api.blockscout.com`, `chain_id=4663`), а не через обычный бесплатный `<explorer>/api/eth-rpc`, который есть у большинства чейнов. Цитата: «Get a free API key at dev.blockscout.com — required for all PRO API tiers, including free.» — то есть бесплатный тир СУЩЕСТВУЕТ, но требует регистрации на внешнем сервисе (`dev.blockscout.com`) и получения ключа. ETH RPC-запросы идут `POST https://api.blockscout.com/4663/json-rpc` с `Authorization: Bearer <ключ>`.

**Эта сессия не регистрируется на внешних сервисах и не создаёт учётные данные самостоятельно** — получение ключа `dev.blockscout.com` требует действия владельца (или добавления уже имеющегося `ALCHEMY_API_KEY` секретом в GH Actions — любой из двух путей разблокирует гард).

### Что сделано, чтобы гард завёлся сразу после появления ключа

`analysis/config.py`/`analysis/alchemy_fallback.py::_rpc_url()` теперь: Alchemy (если настроен) → Blockscout PRO API с `Bearer`-токеном (если задан `BLOCKSCOUT_API_KEY`) → явная понятная ошибка (не тихий сбой), объясняющая обе причины. `.github/workflows/run_p3_guard.yml` пробрасывает оба секрета (`ALCHEMY_API_KEY`, `BLOCKSCOUT_API_KEY`) в обе стадии. `.env.example` документирует оба варианта. Ограничение источника Blockscout: 1000 логов на один запрос `eth_getLogs` — `_chunked_get_logs` рекурсивно бисектит диапазон блоков, если ответ вернул ровно 1000 строк (подозрение на молчаливую обрезку), а не молча теряет логи сверх лимита.

### Что нужно от владельца, чтобы получить реальный результат

Один из двух (любой достаточен):
- Добавить секрет `ALCHEMY_API_KEY` (или `ALCHEMY_ROBINHOOD_RPC_URL`) в GH Actions этого репозитория, **или**
- Зарегистрировать бесплатный ключ на `dev.blockscout.com` (тир PRO API "включая бесплатный") и добавить его секретом `BLOCKSCOUT_API_KEY`.

После этого: поменять `data/p3_guard_cache/STAGE_REQUEST` на `discover` (push-триггер перезапустит) — либо, если репозиторий к тому моменту смержен в дефолтную ветку, использовать `workflow_dispatch` напрямую (см. ниже).

## Как запускалось на практике

`workflow_dispatch` через GitHub API требует, чтобы файл воркфлоу уже
существовал на ДЕФОЛТНОЙ ветке репозитория (ограничение самого GitHub
API, не выбор этого проекта) — а дефолтная ветка этого репозитория
(`git ls-remote --symref origin HEAD`) оказалась
`claude/robinhood-copytrading-hypothesis-awjj0g`, не веткой этой сессии
(`claude/sc1-verdict-3jaxoy`), и системные инструкции сессии прямо
запрещают пушить в другую ветку без явного разрешения владельца.
Решение: у воркфлоу есть второй триггер — `push`, отфильтрованный по
изменению ровно одного маркер-файла
(`data/p3_guard_cache/STAGE_REQUEST`, содержит `discover` или `guard`).
Push-триггеры GitHub Actions читают файл воркфлоу из ветки самого
пуша (не с дефолтной ветки) — это не подпадает под ограничение
`workflow_dispatch`-API. Каждый реальный прогон в этом файле ниже —
результат коммита, поменявшего `STAGE_REQUEST` и запушенного в
`claude/sc1-verdict-3jaxoy`, без единого пуша куда-либо ещё.
