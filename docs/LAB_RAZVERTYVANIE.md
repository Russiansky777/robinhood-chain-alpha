## 2. Бегунок и прогоны

### Три места счёта

| место | что на нём | как запускать |
|---|---|---|
| облачный бегунок GitHub (`ubuntu-latest`, 4 ядра) | всё обычное: матрица пакетов по кошелькам, архивные проходы без кэша | маркер в `data/podbivka/zapusk/zadacha_*.json` |

источникам трендинга: сетевая политика окружения отвечает `403` на CONNECT. Поэтому любой
архивный проход и любое чтение артефакта — только заданием.

## 3. Архив PumpApi: формат, часы, кэш, выходы

**Адрес часа:** `https://replay.pumpapi.io/<ГГГГ>/<ММ>/<ДД>/<ЧЧ>.jsonl.zst` — имя файла есть
час НАЧАЛА (сверено по `timestamp` событий). Одна строка = одно событие пула; сжатие zstd,
~0.467 ГБ на час, ~11.2 ГБ на сутки.

**Что в событии:** `action` (buy / sell / create / migrate / transfer / distributeFees),
`pool` (pump, pump-amm, raydium-cpmm, raydium-launchpad, meteora-dlmm / damm-v1 / damm-v2 /
launchpad), `poolId`, `mint`, `quoteMint`, `txSigner`, `signature`, `block`, `timestamp` (мс),
суммы (`quoteAmount`, `tokenAmount`), состояние пула ПОСЛЕ сделки (`quoteInPool`,
`tokensInPool`, для кривой ещё `vQuoteInBondingCurve`, `vTokensInBondingCurve`), `poolFeeRate`,
`priorityFee`. Полный перечень полей — в `docs/podbivka_2026-09-28_pumpapi.md`.

**Чего в архиве нет:** индекса транзакции в блоке (порядок внутри слота — только оценка по
`timestamp` мс), чаевых Jito отдельным полем, и событий пулов Raydium CLMM, AMM v4, Orca
Whirlpool (эти три — только по цепи).

**Читалка:** `analysis/podbivka_arhiv_den.py`. Ключевые флаги:

```bash
python3 analysis/podbivka_arhiv_den.py \
  --s 2026-10-08T17 --chasov 25 --okno 160 --metka vsel1_2026-10-08 \
  --porog 2.0 --bilety 0.3 --pered 0 --vselennaya 20
```

* `--s ГГГГ-ММ-ДДTЧЧ` и `--chasov` — начало и сколько часов читать;
* **`--okno 160`** — сколько слотов после сигнала писать в ряд пула. 160 выбрано потому, что
  удержание 108 плюс запас: выходы считаются офлайн по сетке до **300** слотов, а ряд длиннее
  160 слотов стоит памяти на каждом живом пуле;
* `--minty` — минты, чьи события пишутся целиком (для разборов вроде Pygoscelis);
* `--pered N` — писать, кто покупал тот же пул за 1…N слотов до нас;
* `--vselennaya N` — сито по всей вселенной: писать кошельки с ≥ N первых покупок от `--porog`
  (модель и события при этом не считаются — иначе сутки не влезают);
* `--ne-sol` — сигналы и в пулах с котировкой не SOL;
* `PODB_ARHIV_KESH=<путь>` — читать часы с локального диска (lab-miami); без переменной —
  потоком прямо с `replay.pumpapi.io`.

**Кэш сигналов для офлайн-пунктов:** `analysis/podbivka_paket_kesh.py` одним проходом
складывает плоские ряды сигналов (состояния входов и выходов, удержание, рисунок цены,
«перед нами», резерв) в `data/podbivka/paket/signaly.jsonl.gz`. После этого любой билет и
любой горизонт считаются формулой `podbivka_bilet.пп_по_состояниям` без повторного чтения
3.6 ГБ суточных файлов. Этот кэш в `.gitignore` — он производный.

## 5. Реализация стандарта выборки

Стандарт (слово владельца с 10.10): **подбор 7 суток → проверка 4, сдвиг 4, сутки подряд по
календарю**. Решение принимается ТОЛЬКО по прошлому: верхние K источников подбора торгуют
следующие четыре суток, окно сдвигается, правило применяется заново.

Порог прохождения окна: **n ≥ 100**, среднее > 0, нижняя граница ДИ > 0, усечённое-5 % > 0,
**≥ 60 % суток в плюсе**, обе половины окна в плюсе; знаковый тест по сутким точным
биномиальным; поправка на перебор — **на ВСЕ посчитанные сочетания** (`p < 0.05/сочетаний`,
число сочетаний печатается и лежит в выходном файле как `сочетаний_посчитано`).

Где это в коде: `analysis/podbivka_zabor_nabor.py` (`подряд()` требует календарных суток
подряд, `K_НАБОРА`, `СРЕЗЫ`, контроли на перемешанных знаках суток и на случайном выборе K
из той же вселенной), счёт п.п. — `podbivka_zabor_s0.py`.

Запуск:

```bash
python3 analysis/podbivka_zabor_nabor.py --srezy осторожный --k 5,10,20 --semya 20261010
```

Контроли обязательны: без них «проходит» любое сочетание из достаточно большого перебора.
На 44 сутках контроли дали 0 из 54 — это и есть доказательство, что порог не подогнан.

## 6. Калибровка по живым сделкам

Модель архива калибруется парами «живая сделка Code-1 + её сигнал в архиве»
(`docs/podbivka_2026-10-08_kalibrovka.md`: 1129 пар из 1645 сделок окна). Калибруются три
вещи:

* **место входа**: живое `S+0` → `S0_дно` (цена конца слота источника), `S+1` → `S1`, `S+2` → `S2`;
* **множитель наценки выхода** `к_g = 0.9908`;
* **издержки круга** `k = 0.989` (пропорциональная часть) плюс постоянный расход круга
  (медиана 0.002019 SOL, половина — чаевые покупки, половина — приоритет;
  `docs/podbivka_2026-10-05_rashod_sdelki.md`). На живых сделках набора 11.10 постоянный
  расход вышел 0.00301 SOL — проверять его надо по свежей выгрузке, а не брать из памяти.

Сверка живых сделок по цене внутри слота:

```bash
python3 analysis/podbivka_cena_v_slote.py --vhod <выгрузка Code-1> --gruppa <группа> \
    --sravnit data/podbivka/cena_v_slote_4vw.json
```

Даёт q при лаге 0, долю лага 0, число транзакций между источником и нами — по каждому
источнику отдельно.

## 7. Грабли (каждая стоила прогона)

1. **Сутки архива — 25 часов от 17:00Z.** Суточный файл покрывает 25 часов начиная с 17:00Z,
   поэтому календарные сутки собираются из ДВУХ файлов. Кто считает «один файл = одни сутки»,
   получает чужие часы в окне.
2. **Порог 18 часов для неполных суток.** Неполнота определяется по числу РАЗНЫХ прочитанных
   часов (`часов_в_сутках` в кэше пакета), а не по числу сигналов: тихие сутки 03–05.09 имеют
   мало сигналов, но прочитаны целиком, а 08.09 и 11.09 — настоящие обрывки. Порог — 18 часов
   (`неполные_сутки(часов_мин=18)`).
3. **`--vselennaya` не считает модель.** С ситом по вселенной события и модель не считаются
   вовсе — иначе сутки не влезают в память бегунка. Кто ждёт от такого прогона п.п., получит
   пустые поля.
4. **Дубли имён заданий матрицы.** Два маркера в одном пуше давали одинаковые имена работ
   (`podbivka_arhiv_den_0..29` дважды), и по списку работ было не разобрать, какие сутки
   закрыты. Исправлено: имя задания берётся из `--metka` (`podbivka_plan.имя_пакета`). Правило:
   **один маркер в один пуш** — и потому что GitHub держит только ОДНУ ожидающую работу на
   группу concurrency, второй пуш отменяет первую.
5. **100 МБ в ветке.** GitHub не принимает файл больше 100 МБ: доставка рядов Code-3 упала
   дважды (123 МБ), пока файл не разбили на `.partN.json.gz` плюс `.manifest.json`.
6. **`import podbivka_run` на бегунке.** На бегунке без `solders` этот импорт валит прогон:
   в доставке он был ради одной функции. Либо `pip install solders` в шаге venv, либо импорт
   в `try/except` (как в `podbivka_arhiv_glubina.py` и `podbivka_miami_inventar.py`).
7. **Вход считается по `sol_in`.** В выгрузке Code-1 вход сделки — поле `sol_in` (билет),
   а `vhod_sol_likvid_po_cepi` включает ренту и даёт q 5.08 и факт/модель 0.63. Порядок полей
   в `podbivka_cena_v_slote.py`: `sol_in` → `билет_sol` → ликвидные, и в выходе стоит счётчик
   `вход_по_sol_in` / `вход_по_ликвиду` — если он показывает ликвид, q врёт.
8. **Фильтр `1 <=` в «перед».** Столбец «источник первый» был артефактом: `--pered` писал
   только СТРОГО более ранние слоты (`1 <= s0 − бл`), поэтому покупки в том же слоте до
   источника в счёт не входили и источник всегда выходил первым. Правильное условие — `0 <=`;
   пока проход не повторён, столбца «источник первый» в отчётах быть не должно.
9. **403 на все внешние хосты из контейнера.** `replay.pumpapi.io`, `*.blob.core.windows.net`
   (журналы и артефакты Actions) и все источники трендинга закрыты сетевой политикой
   окружения: прокси отвечает `403 Forbidden` на CONNECT. Признак — `Tunnel connection
   failed: 403 Forbidden`. Лечится не кодом, а либо заданием Actions, либо открытием хоста в
   настройках окружения (Network access).
10. **`workflow_dispatch` работает только с ветки по умолчанию.** Запуск прогона с моей ветки
    по API даёт HTTP 404 — поэтому все прогоны идут маркером в пуше, а не диспатчем.
11. **`pgrep -f <шаблон>` находит сам себя.** Ожидалки в фоне никогда не выходили, потому что
    шаблон совпадал с их собственной командной строкой; `pkill -f <скрипт>` однажды убил мою
    же оболочку. Правило: ждать по файлам результата, убивать по явному PID.
