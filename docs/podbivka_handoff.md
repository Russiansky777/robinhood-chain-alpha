разбивка по методам того же порядка. Если медиана уехала -- разбирать причину, а

Файлы задания: `analysis/podbivka.py`, `analysis/podbivka_1b.py`,

## 1. Запуск

**Питон.** У системного `python3` на бегунке (и на NL-хосте) **нет `solders`**, а
`analysis/c2_swap_build.py` тянет его на импорте. Поэтому в облачных прогонах
всегда создаётся venv:

```yaml
python3 -m venv "$RUNNER_TEMP/pod_venv"
"$RUNNER_TEMP/pod_venv/bin/pip" install -q requests solders
echo "PY=$RUNNER_TEMP/pod_venv/bin/python" >> "$GITHUB_ENV"
```

Дальше все вызовы через `$PY`. Проверка перед доставкой кода на хост НЕ должна
импортировать `c2_swap_build` -- деплой сторожа 26.09 13:32Z упал ровно на этом.

**Секреты по именам** (значения нигде не печатать):

| имя секрета | во что кладётся | зачем |
|---|---|---|
| `HELIUS_API` | env `HELIUS_API_KEY` | узел для симулятора; `analysis/podbivka.py:узел()` читает `HELIUS_API_KEY`, а если его нет -- `HELIUS_API` |
| `VPS_SSH_KEY` | файл `~/.ssh/vps_key`, режим 600 | поток журналов с NL-хоста |
| `TELEGRAM_BOT_TOKEN` | только на хосте, в env службы | строки владельцу; в прогонах задания 2 не нужен |
| `GRPC_FEED_URL`, `GRPC_FEED_TOKEN` | env зонда фида | это **gRPC-фид Shyft**, не RPC |

Ключа RPC Shyft в прогонах пока НЕТ ни под каким именем: `grep -rn "SHYFT_"
.github/workflows/` пуст. Владелец 26.09 сказал, что ключ лежит в секретах и
тариф оплачен до 24.10 -- имя секрета взять из настроек репозитория (Settings →
Secrets) и **не выдумывать**. В коде обращение к узлу вынесено в одну функцию
(`podbivka.узел()`), поэтому переход на Shyft -- это правка одной функции плюс
имя секрета в прогоне.

**Прогоны.** Облачные (`runs-on: ubuntu-latest`) и хостовые
(`runs-on: ${{ fromJSON('["self-hosted","nl-host"]') }}`) отличаются тремя
вещами, и это не вкус:

* хостовой бегунок стоит НА боевом хосте: он бывает занят долгими замерами, а
  перезагрузка хоста убивает job вместе с собой. Всё измерительное -- облачное;
* у облачного нет доступа к файлам хоста: журналы идут потоком по ssh
  (`ssh "cat > /tmp/x.py" < deploy/checks/x.py`, затем `ssh "python3 /tmp/x.py"`,
  вывод -- в файл прогона);
* **предел одного job -- 6 часов**. Всё, что дольше, режется на пакеты (по
  кошелькам -- по 50 на прогон) и пускается параллельными прогонами.

Сейчас в задании 2: `run_podbivka_kontrol_ceny.yml` (контроль цены, п.1),
`run_podbivka_p1b.yml` (сквозная сверка, п.1б). Оба облачные, оба только читают.

## 2. Правила репозитория (нарушение каждого уже стоило прогона)

* **Только ASCII в именах переменных оболочки**, в YAML и в ключах JSON.
  Проверяет `analysis/check_shell_ascii.py` -- запускать ТОЛЬКО на `.yml` и `.sh`
  (на питоне он бессмыслен: там кириллица в именах разрешена и используется).
  Кириллическая переменная `ФАЙЛ` в прогоне уже ломала разбор.
* **Heredoc внутри YAML ломается.** Тело heredoc и многострочный inline-python в
  блочном скаляре съезжают за отступ, и GitHub отвечает «Workflow does not have
  'workflow_dispatch' trigger» -- то есть прогон вообще нельзя запустить. Решение:
  скрипт лежит файлом в репозитории и доставляется потоком (`ssh "cat > /tmp/..."
  < файл`), а в YAML остаются строгие однострочники.
* **Строки ошибок -- только через вычистку.** `podbivka_1b.чисто()` вырезает
  любой URL и `api-key=...`. Причина: 26.09 текст ошибки `requests` с полным URL
  узла попал в отчёт и в репозиторий вместе с ключом.
* **Результат по кошельку -- в файл сразу**, а не в конце прогона: job может
  упасть по пределу времени, и половина работы не должна теряться.
* Каждая правка -- отдельный коммит со своей самопроверкой; измерительный код
  тестами не обкладывается (слово владельца), денежный -- обязательно.
* Журналы в память не читать: только потоком (`deploy/checks/*_iz_zhurnala.py`).

## 3. Формулы: файл и функция по каждому типу пула

Вход симулятора всегда один: **транзакция источника** и наша трата в лампортах.
Ответ -- сколько токенов дал бы пул сразу после сделки источника.

| тип пула | где формула | как считается |
|---|---|---|
| обычный `x*y=k` (Pump AMM, Raydium CPMM, DAMM) | `c2_swap_build.min_out_from_reserves`, поверх `podbivka.резервы_после` | резервы ПОСЛЕ сделки источника берутся из pre/post хранилищ той же транзакции; доля траты, доходящая до пула, **калибруется на этой же сделке** и обязана лечь в рамку `podbivka.РАМКА_КОМИССИИ = (0.80, 1.0)`, иначе отказ с числом |
| кривая pump.fun (`6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`) | `c2_swap_build.bonding_min_out`, `pump_trade_event`, `pump_net_to_curve` | комиссии **95 bp + 30 bp берутся ИЗ траты** (ceil на каждой), до кривой доходит остаток; далее `floor(vt0*sol/(vs0+sol))` по виртуальным резервам из события сделки (`TradeEvent`, дискриминатор `bddb7fd34ee661ee`). Котировка **нативный SOL**, счёта WSOL у кривой нет вовсе |
| сосредоточенная ликвидность (DLMM, CLMM, Whirlpool -- `podbivka.СОСРЕДОТОЧЕННЫЕ`) | `podbivka.наша_покупка_по_симулятору`, ветка `concentrated` | резервы цену не дают: берётся **цена исполнения последнего свопа** источника, проскальзывание 0, ставится флаг `concentrated` |
| ничего из перечисленного | там же, запасной путь | цена исполнения свопа источника с флагом; если котировка не SOL -- отказ, а не число |

**Какие счета -- хранилища.** `c2_common.identify_pool(tx, источник, минт)`
возвращает `pool_vault` (хранилище базового токена) и `quote_vault` (хранилище
котировки); программу пула определяет
`c2_pool_programs.pool_program(tx, pool_vault, labels)`. У кривой pump.fun
хранилища котировки нет -- SOL лежит на самой кривой, поэтому `quote_mint`
приходит как `native_sol` (`c2_common.NATIVE_QUOTE`).

**Котировка обязана быть SOL** (`WSOL` или `native_sol`). Иначе наши лампорты
попадают в резерв другого токена с другими `decimals` -- см. ошибки ниже.

**Налог токена** берётся ИЗ МИНТА, а не из маршрута: `Helius.налог_минта(минт)`
(детектор, один `getAccountInfo`/`getMultipleAccounts` на минт, кэш на процесс);
для Token-2022 это `TransferFeeConfig` в расширениях минта. В симуляторе налог
вычитается из полученного количества, а не из траты.

**Decimals** -- только из строк балансов транзакции (`c2_common.token_rows` →
поле `dec`), никогда не из предположения «9» или «6».

## 5. Сделанные ошибки -- чтобы не повторять

1. **A3: выброшены сигналы без цены.** В разборе A3 из выборки молча уходили
   сигналы, по которым цену восстановить не удалось, и доля выброшенных нигде не
   стояла -- остаток выглядел как весь набор. Правило: отказ всегда с ПРИЧИНОЙ и
   числом, доля отказов -- в своде рядом с медианой (в `kontrol_ceny.json` это
   `сделок_на_входе` 258 / `сверено` 80 / `отказов` 178 и `причины_отказов`).
2. **Котировка не SOL в резервах.** Лампорты попадали в резерв другого токена с
   другими `decimals`: медиана 5.907 п.п. и выбросы до **1.6e10 п.п.** Лечение:
   отказ с названным минтом котировки плюс рамка калиброванной комиссии
   0.80–1.00. После этого медиана стала 1.272 п.п.
3. **Покрытие 1.0 при потерянных транзакциях.** Покрытие считалось как
   «посмотрено / подписей», а 540 транзакций узел не отдал вовсе -- отчёт
   показывал полноту 1.0 при реальной 0.918. Считать покрытие по РАЗОБРАННЫМ.
4. **429 прочитан как «покупок нет».** Один 429 на `getSignaturesForAddress`
   оставил Brez без истории, и в отчёте это выглядело как «у источника покупок
   нет». Лечение: отступ и повторы на 429 в ОДИНОЧНЫХ вызовах тоже, пакеты по 25
   с паузой, пропавшие внутри пакета переспрашиваются по одной.
5. **Кошелёк полосы определился как исполнительский.** Возврат продажи считался
   по кошельку исполнителя на всех позициях подряд, и у продаж полосы выходило
   ровно `+0.000000 SOL`. Кошелёк берётся ПО ПОЗИЦИИ (`bloom_seller.кошелёк_позиции`),
   а в сверке с цепью -- из самой транзакции (плательщик комиссии).
6. **`getTransactionsForAddress` без фильтров на нашем плане.** Метод отвечает
   ТОЛЬКО на один параметр-адрес: форма с настройками даёт
   `-32602 Expected end of params`, форма с одним словарём --
   `invalid type: map, expected a string`. Ни окна, ни страниц задать нельзя,
   поэтому путь по цепи -- `getSignaturesForAddress` (страницы по 1000) плюс
   **пакетные `getTransaction` по 25 в одном POST** (JSON-RPC массив).
7. **Имя файла суточного счёта** -- с дефисами и по Мадриду; поиск
   `pnl_20260926.json` давал пустой счёт, и это читалось как «учёт не пишется».
8. **UTC через `timegm`, а не `mktime`.** `mktime` читает время как местное, и на
   хосте в CEST окно съезжало на час: часть записей молча уезжала из выборки.
